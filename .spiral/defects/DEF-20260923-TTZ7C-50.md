# Late file reads need storage-failure semantics

Final review of the file-backed migration identified a changed failure boundary:
source reads can now fail inside a command or query after initialization. The
prior buffered runtime read source bytes before execution. DES-47 preserved
publication/storage failures but did not explicitly carry late read failures
through the ordinary command/query exception handlers.

Two new regressions on implementation bfeed2c fail (21 other focused tests pass):
a command's unread record raises Unexpected end of file without storageFailure;
a query that catches its unread-record error can return success, leaving future
command acceptance enabled. The fixtures truncate only disposable data files
after both query pools have initialized. This models unavailable backing bytes;
normal operation still requires immutable source files.

Required correction within the existing migration goal: the file parser records
read/decode/reference failures in host-owned session state. Commands must refuse
publication even if handler code catches that failure. Query workers consult
that host state, not a user-thrown storageFailure property; a spoofed flag must
remain an ordinary query error. The runtime marks storage failure and refuses
further commands. Preserve ownership/recovery evidence on failure.

This corrects the migration design's failure classification, not the sandbox or
remote query language. The baseline tests are committed before the repair.
