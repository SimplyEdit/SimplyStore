# Implementation: Command Crash Matrix And Commit Boundary

## Scope

Command update-cycle crash classification, independent reconstruction oracle tests, duplicate command-log replay de-duplication, and durable `done` as the commit-before-query-visibility boundary.

## Observable behavior

- Test-only fault points cover command acceptance, active marking, changeset writing, pre-`done`, and post-`done`/pre-query-update boundaries.
- Fault points remain inert outside `SIMPLYSTORE_ENV=test`.
- A crash after command log append but before accepted status is not committed.
- Accepted/active/pre-`done` crash boundaries replay to one committed state.
- A crash after durable `done` but before query-worker update recovers committed state without replay.
- Duplicate command-log records for the same accepted command ID do not cause automatic replay twice.
- Normal restart state is compared with an independent reconstruction from base data plus `done` changesets.

## Repository locations

| Path / symbol | Role |
|---|---|
| `src/server.mjs#checkCommand` | Adds acceptance-phase fault points. |
| `src/server.mjs#runNextCommand` | Adds active/done fault points, skips non-pending queued commands, and appends durable `done` before query visibility. |
| `src/command-worker-module.mjs#runCommand` | Adds command-worker changeset-write fault points. |
| `src/recovery.mjs#loadCommandLog` | De-duplicates accepted command IDs during replay scheduling. |
| `test/durability-helpers.mjs` | Shared process-fixture helpers and independent reconstruction oracle. |
| `test/durability-crash.mjs` | Process-level command crash matrix tests. |

## Effective provenance

This implementation realizes `CYC-010` and the `DES-001` durability invariants, especially committed-state recovery, no partial command visibility, command idempotency, deterministic reconstruction, and detectable corruption.

## Important implementation decisions

- The durable on-disk format is not changed.
- Existing REST endpoint names and JavaScript query API bindings are not changed.
- Durable `done` status is treated as the commit record; query-worker updates happen only after that append succeeds.
- Duplicate log entries are tolerated for replay scheduling by treating command ID as the logical command identity.
- The oracle reads durable records and changesets directly rather than using the server startup/query path.

## New dependencies / capabilities / permissions

No new package dependencies.

The durability test suite still starts local SimplyStore server processes and binds ephemeral localhost ports.

## Known limits

- The matrix proves process-crash behavior, not power-loss or directory-fsync behavior.
- It does not add cleanup/reset/recovery tooling.
- It does not define public documentation for every durable status.
- It does not fully classify duplicate conflicting command-log records.
- It does not prove non-deterministic command handler replay safety.
