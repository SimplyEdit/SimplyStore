# Implementation: Retried Command Status Reporting

## Scope

Retry/idempotency hardening for repeated `POST /command` submissions with the same command ID.

## Observable behavior

- A repeated command ID is not enqueued as a new command.
- A repeated command ID returns the current in-memory command status rather than a fresh `accepted` status.
- Retries after normal completion report `done` and do not apply a second transition.
- Retries while the original command is `active` report `active` and do not enqueue duplicate work.
- Retries after crash recovery reports `done` once recovery has committed the original command.
- Retries after repeated active crashes report `unsafe` and do not restart the unsafe command.
- Once an `accepted` status line has been durably appended, the in-memory status map is updated before the post-acceptance fault/response boundary.

## Repository locations

| Path / symbol | Role |
|---|---|
| `src/server.mjs#checkCommand` | Returns current status for duplicate command IDs and closes the accepted-status in-memory window. |
| `test/acid-baseline.mjs` | Covers normal committed retry and active retry behavior. |
| `test/durability-crash.mjs` | Covers retry after crash recovery and unsafe-command retry behavior. |

## Effective provenance

This implementation realizes `CYC-013` and strengthens the `DES-001` D3 command-idempotency invariant.

## Important implementation decisions

- The same command ID remains a single logical command and is not enqueued twice.
- Duplicate command submissions keep HTTP 200 behavior for existing command IDs, but the JSON body now reflects the current command status.
- The change does not compare duplicate request payloads with the original command body.
- The change does not add integrity metadata, handler contracts, or queue machinery.

## New dependencies / capabilities / permissions

No new package dependencies.

## Known limits

- The command log still does not store request metadata.
- A repeated command ID with a different body is treated as a status lookup for the original command ID, not as a conflict.
- This does not prove filesystem-level durability or power-loss behavior.
