# Implementation: Command And Load Worker Timeout Boundaries

## Scope

Parent-thread timeout handling for command and load worker threads, plus durability tests proving the timeout semantics selected in `DES-003`.

## Observable behavior

- `commandTimeout` configures the command worker boundary independently from query timeout.
- `loadTimeout` configures the load worker boundary independently from query timeout.
- `0`, `false`, `null`, or `Infinity` disables the corresponding worker timeout.
- A command worker that exceeds `commandTimeout` is terminated by the parent thread.
- The timed-out command is durably recorded as terminal `unsafe` with code `504`, message, details, and attempt.
- Retrying the same command ID returns the existing `unsafe` status and does not enqueue duplicate work.
- A later accepted command can commit after the timed-out command worker is terminated.
- A load worker that exceeds `loadTimeout` is terminated and causes startup to fail explicitly before the server listens.
- Accepted commands are not marked failed merely because another command runner is already draining the queue.

## Effective provenance

This implementation realizes `DES-003` and strengthens the `DES-001` durability invariants for command idempotency, committed-state recovery, no partial command visibility, and explicit failure over ambiguous state.

It also preserves the existing governed reasons for the revised command lifecycle:

- `IMP-001`: startup recovery only loads committed commands;
- `IMP-003`: active accepted commands are recovered or marked unsafe instead of replaying forever;
- `IMP-004`: durable `done` is written before query-worker visibility;
- `IMP-007`: repeated command IDs report current terminal or active status instead of enqueueing duplicate work.

## Important implementation decisions

- Timeout enforcement lives in the parent thread, not inside command handlers or the VM2 query timeout mechanism.
- Timeout status is `unsafe`, not `failed`, because the command may have performed arbitrary external effects before the worker was terminated.
- The existing durable status log format is reused; no OD-JSONTag format or command-log schema change is introduced.
- Command queue draining uses a small in-process guard rather than a general scheduler or job framework.
- Load timeout has no command status record because startup loading is not command execution.

## New dependencies / capabilities / permissions

No new package dependencies.

## Known limits

- Worker termination cannot roll back external side effects from user command code.
- The default timeout values are conservative starting points, not yet documented as a stable public contract.
- Timeout handling does not repair or clean uncommitted changeset files left by interrupted work.
- The command failure catch path still belongs to the older command lifecycle structure; this cycle changes only the behavior needed for accepted queued commands and timeout outcomes.
