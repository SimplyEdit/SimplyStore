# Implementation: Store Runtime And Express Shell

Implements DES-20260919-TTZ7C-32 by introducing `StoreRuntime` as the owner of an
opened store's state and lifecycle. It transforms the server/worker portion of
IMP-20260919-TTZ7C-26 without changing the accepted durability and recovery
semantics implemented there.

`src/store-runtime.mjs` now owns normalized store configuration, ownership,
startup inspection and loading, dataset buffers and metadata, command status and
queue state, query pools, storage failure and closing state. Its coordinating
methods describe opening, accepting, executing, publishing and closing in domain
order. Repeated status persistence is one named operation; lower-level append,
sync, fault, worker and pool mechanisms are supplied through one closed mechanism
object with concrete production defaults.

Command acceptance remains serialized through log append, accepted status and
queue insertion. The queue runs one command at a time in command-log order.
Active persistence precedes worker execution; required-file synchronization and
done persistence precede query publication. Safe handler failures receive their
terminal status, while storage uncertainty closes mutation and retains ownership.
The optional `onStorageFailure` mechanism reports that transition to an embedding
policy when supplied. Its absence requires no placeholder callback; the runtime
still enters the failed state and stops mutation.

`src/server.mjs` retains the package's default Express application plus `run()`
contract. It now owns only route/content negotiation, HTTP translation, static
resources, the listening socket, signals, logging and process exit. Command
handlers pass raw command text to the runtime, send its plain result and then
start queue draining, retaining the previous response/execution boundary.

`src/execute-worker.mjs` exposes the common one-shot worker protocol through
`runWorker`. Load timeout remains a rejected startup error. The existing
`executeWorker` command adapter converts that same timeout into the established
`unsafe` command result, preserving administrator assessment behavior. Query
workers remain in their long-lived pool abstraction.

`test/store-runtime.mjs` directly covers open/close ownership, durable acceptance,
duplicate IDs, delayed concurrent acceptance and execution order, terminal
handler failure, query publication and storage-failure admission closure using a
real temporary store plus narrow worker/query doubles. Existing process suites
remain the evidence for actual HTTP, workers, crashes and durable I/O.

No file format, migration, endpoint, command input, recovery policy, generic
container or framework is introduced.

The final abstraction review removed a one-use result wrapper, named the
serialized inner operation `acceptCommandInOrder`, and kept the direct content
negotiation check local where another helper call obscured it. Other supporting
methods remain because they hide worker/filesystem detail or express recurring
store operations used by the high-level lifecycle.

Query pool and timeout selection now happen together in the runtime. Normal
queries pass the configured `timeout`; slow queries pass the configured
`slowTimeout`. Both GET and POST send the chosen value through the worker's
`timeout` task property. This is the narrow semantic correction authorized after
evaluation exposed that the historical slow-query options were ineffective. The
direct runtime test covers both methods on both endpoints.

`src/store-inspection.mjs` retains `inspectStore(options)` as its public entry
point and delegates the stateful workflow to a module-local `StoreInspector`.
Its `inspect()` method now states the ordered story: validate paths, inventory
files, read commands and status history, validate order and integrity,
reconstruct committed data, validate artifacts, verify a stable snapshot and
return the existing report. Detailed record parsing and per-command dataset
classification remain methods on the same cohesive owner of inspection state.

`src/admin-recovery.mjs` retains all exported functions and plain result shapes.
`RecoveryApplication`, `BackupRestoration` and `OfflineLockRelease` own the three
substantial stateful workflows that previously occupied 234, 123 and 124-line
functions. Their coordinating methods now express administrator validation,
ownership, workspace preparation, durable attempts, verification, completion
and intentional lock release in domain order. Supporting methods hide durable
I/O and worker details without introducing a generic recovery framework.

The structural move preserves error text, report and audit fields, operation
ordering, source freshness checks and recovery eligibility. Failed recovery and
restore candidates retain their locks and audit evidence; source ownership is
released under the same conditions. Existing duplicate reads and later-dataset
queries in inspection are retained to avoid mixing race or performance semantics
into the readability refactor.

## Cycle 36: complete lifecycle contracts

DES-20260919-TTZ7C-40 supplements the existing architecture. All close callers
now await one completion promise, including cleanup rejection. The server can
await it from both signal handlers without prematurely exiting. Acceptance
rechecks storage health after persistence and before queueing/acknowledgment.
Command preparation recognizes an existing valid ID before applying new-command
name requirements, restoring ID-only retry compatibility.

StoreInspector groups log/status interpretation in loadCommandHistory() and
initializes prefix validity inside reconstruction. RecoveryApplication groups
attempt numbering, audit persistence and active-status serialization in
markCommandActive(). The coordinating methods stay at workflow level; the order
of checks, writes, parsing, audit and cleanup remains unchanged. No new classes
or dependencies are introduced.

The preceding implementation version added six failing regression cases before
product changes. Those tests now pass: overlapping closure waits for execution
and shares cleanup failure; both persistence-boundary failures reject acceptance;
known ID-only retries return status while incomplete new commands fail; and a
real process receiving both shutdown signals commits, unlocks and restarts.
EVD-20260919-TTZ7C-41 preserves the baseline and records final suite results.

## Cycle 44: File-backed runtime and reader lifetime

DES-20260923-TTZ7C-47 changes the internal runtime representation to ordered file
sources, with file paths, sparse offsets, immutable file identity and SHA-256.
FileDataset owns parser and descriptors; scanDataFile validates framing and
hashes with a 64 KiB buffer. Startup builds IDs from final records without
requiring trustworthy sidecars. Runtime/query/command messages contain sources,
not dataset bytes. Query and command ID lookups use the complete record catalog.

The worker pool queues updates ahead of new queries, independently for each
worker, and initializes replacements with the current source list. Failed source
updates reject further queries and stop command acceptance. Shutdown awaits
termination (including workers already being replaced) before ownership release.

A QueryParser specialization gives raw query arrays a non-configurable undefined
constructor before proxy wrapping. Local vm2 3.12.2 recognizes this as its
already-neutralized array-species case. Tests cover map, JAQT, and refused array
mutation/definition. This preserves the query API without weakening immutable
traps or changing the sandbox implementation. It is not a sandbox safety claim.

Existing tests were adapted only where internal messages/report fields changed;
remote results, recovery eligibility, ordering and failure expectations remain.
New tests cover unread IDs, sparse overlays, corrupt framing, short reads/EOF,
file changes and closure, byte-free messages, index loaders, real runtime restart,
failed publication, worker replacement, and asynchronous update ordering.
