# Implementation: Startup Recovery Selection And Replay Classification

## Scope

Startup reconstruction applies only committed command changesets, refuses recovery when a committed changeset file is missing, and shares durable command-status/command-log parsing between server startup and tests.

Malformed or structurally invalid durable command-status and command-log records are classified as recovery integrity failures.

## Observable behavior

- A status entry whose latest status is `accepted` is not selected for startup reconstruction.
- A status entry whose latest status is `done` is selected for startup reconstruction.
- If a selected committed changeset file is missing, the load worker throws an explicit recovery error.
- Durable `command-status.jsontag` files are parsed into latest status by command ID.
- Durable `command-log.jsontag` files replay only commands whose latest status is `accepted`.
- Malformed command-status and command-log lines raise `RecoveryIntegrityError` with file, line number, and record kind.
- Command-status records without string `command` or `status` fields raise `RecoveryIntegrityError`.
- Command-log records without string `id` fields raise `RecoveryIntegrityError`.

## Important implementation decisions

- `done` remains the current committed status term. This repair does not rename durable status vocabulary.
- The loader remains a low-level component: it trusts the caller to pass committed command IDs, but now treats every supplied command ID as required.
- The status-selection and command-log replay rules live in `src/recovery.mjs` so tests and server startup use the same policy.
- The repair does not introduce crash fault points, hashing, handler phases, or post-commit extension seams.
- The corruption classification is intentionally structural: it validates durable record parseability and required identifier/status fields without yet defining every cross-file consistency rule.
- The `npm test` script now sets tap coverage thresholds to `0` explicitly. Node-tap's effective default was enforcing 100% thresholds, causing green assertions to exit with code 1. Coverage remains reported; it is not currently used as the acceptance gate.

## Known limits

- The harness exercises durable status/log parsing and the load worker, not a full HTTP server process restart.
- Missing base dataset behavior is not changed by this slice.
- Command log/status writes were later made awaited in `IMP-002`; filesystem sync ordering beyond those awaits remains future work.
- Real `SIGKILL` fault injection now exists for the first process-level boundary in `IMP-002`.
- Cross-file inconsistency classes beyond missing committed changesets and malformed status/log records remain future work.
