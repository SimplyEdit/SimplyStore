# Implementation: Accepted Command Replay Safety

## Scope

Durable active-command attempt tracking and unsafe-command classification for repeatedly crashing accepted commands.

## Observable behavior

- A command is marked `active` durably before its worker starts.
- `active` records include an `attempt` number.
- On startup, an active command below `maxCommandCrashAttempts` is moved back to `accepted` for replay.
- On startup, an active command at or above `maxCommandCrashAttempts` is marked `unsafe`.
- `unsafe` commands are not replayed by `loadCommandLog`.
- The default `maxCommandCrashAttempts` is `2`.

## Repository locations

| Path / symbol | Role |
|---|---|
| `src/recovery.mjs#activeCommandStatus` | Durable status value for commands that were being run. |
| `src/recovery.mjs#unsafeCommandStatus` | Durable status value for commands that should not be replayed automatically. |
| `src/recovery.mjs#recoverActiveCommands` | Classifies active commands during startup as retryable accepted commands or unsafe commands. |
| `src/recovery.mjs#nextActiveCommandStatus` | Computes the next active attempt record before command worker start. |
| `src/server.mjs#main` | Runs active-command recovery before command-log replay. |
| `src/server.mjs#runNextCommand` | Appends active status before starting the command worker. |
| `test/durability-startup.mjs` | Unit-level active/unsafe recovery tests. |
| `test/durability-crash.mjs` | Process-level repeated-crash unsafe-command test. |

## Effective provenance

This implementation realizes `CYC-008`, caused by the human-identified restart-loop risk for accepted commands that repeatedly crash during automatic replay.

## Important implementation decisions

- The command-status file remains the lifecycle authority and now also carries active-attempt records.
- The command-log file remains replay material; only latest `accepted` commands are scheduled.
- `unsafe` is a terminal non-replay status for automatic startup replay.
- The threshold is configured through `server.run({ maxCommandCrashAttempts })` and defaults to `2`.

## New dependencies / capabilities / permissions

No new package dependencies.

## Known limits

- No cleanup/reset/operator tool exists yet for unsafe commands.
- No public documentation exists yet for `active` or `unsafe` statuses.
- The repeated-crash process test uses the existing server-side `before-command-done-status` fault point; command-worker internal fault points remain future work.
- Cross-file inconsistency cases such as accepted status without command log remain future work.
