# Design: Finalize Offsets After Conversion

The converter owns the final output bytes. Its custom index hook can mutate
canonical objects after calling the built-in index writer. Positions captured
before that hook completes cannot describe the final serialized file.

Keep invoking the existing custom hook once. Serialize its completed result,
write the output, parse that exact serialization with a fresh lazy OD-JSONTag
parser, then use the existing offset writer with the fresh result array. This
overwrites provisional offsets, includes newly serialized records, and retains
the current JSON sidecar and CLI formats. The extra pass is linear in the data.
Inspection of the installed parser shows that reading its position symbol
materializes the entity body, so the current offset writer adds a full readback
pass. Conversion already materializes its input; this bounded repair accepts
that cost and makes no laziness-preservation claim for offset finalization.

Changing the writer alone cannot fix later mutations by a caller. Introducing
a new create/finalize hook contract would expand the compatibility surface for
this bounded repair. Reuse the existing parser/writer at the point where the
final bytes are known. This design makes no new atomic multi-file publication
or crash-safety claim for the conversion command.

Verify through the actual CLI with an independent byte-framing oracle. Cover
default indexing, a hook that calls base indexing before changing lengths and
adding an anonymous record, and a custom hook that writes no offset sidecar.
Include multibyte text and a reused output directory. Run the normal startup
suite in addition to these conversion regressions.
