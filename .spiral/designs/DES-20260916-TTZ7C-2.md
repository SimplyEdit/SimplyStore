# Design: Prospective Provenance Repair And Historical Validation

## Intent and boundary

Correct `DEF-20260916-TTZ7C-1` while preserving historical evidence and the
accepted integrity runtime. This is a bounded process correction inside the
reopened integrity cycle. It does not start a new durability feature.

## Validation responsibilities

Use Python rdflib (already required by the pinned core) for Turtle parsing.
Keep `node scripts/validate-spiral-provenance.mjs` as a thin entry point; remove
the CYC-016-specific assumptions and handwritten Turtle parser. The validator
reads only the project's `.spiral/**/*.ttl`, including vocabulary documents.
It complements the pinned core's identity/coherence/integration validator.

- Default: validate the committed `HEAD` snapshot. Determine each Turtle file's
  source version from Git, not the current wall clock or tip alone.
- `--staged`: read the Git index, not unstaged files. New/changed staged
  references may target current HEAD; persisted unchanged files retain strict
  ancestor checks. Use this before semantic causal commits.
- `--tree <commit>`: validate that committed snapshot and reference origins.
- `--range <base>..<head>`: check changed Turtle versions at every introduced
  commit, including merge changes and versions later deleted or repaired.
  Accept `--range <head>` to audit all reachable history. Report old violations
  as failures; do not introduce a historical allowlist.

Every versioned reference must have exactly one artifact IRI and one full Git
hash, resolve to a real commit, and name an artifact definition and repository
path present at that commit. Local references must point backward through Git
ancestry (or to HEAD for new staged content). Resolve references semantically
through the ontology's historical-reference hierarchy, including custom
subproperties in the project graph; do not depend on prefixes or formatting.

The two existing external namespaces (Muze culture and Spiral process artifacts)
are resolved only through the explicitly pinned `.spiral-core` submodule.
Verify the target artifact at its external hash and that hash's inclusion in
the source version's pinned core history. Do not compare hashes from separate
repositories as if they shared local ancestry, or silently skip external links.
An unavailable process checkout causes an actionable validation failure.

## CI and local prevention

Run the validator's regression tests and reference-range validation for pull
requests and merge groups, using event hashes passed through environment
variables. Check the candidate tip/prospective merge snapshot too. Preserve the
existing core integration check for acceptance, identity, and convergence.

Document a repository hook that runs staged validation, installed explicitly
per checkout; keep CI authoritative for introduced commit ranges. A hook is an
optional local convenience, not evidence that historical commits were checked.

## Prospective lineage correction

The original integrity artifact is a new concern, but it also changed existing
loader verification and the changeset/pre-done boundary. Update the affected
`IMP-001`, `IMP-004`, and `IMP-006` projections with the integrity design as an
additional effective cause, their exact immediate predecessors, and this
correction as transition cause. Preserve their still-valid durability reasons.
Explain that this metadata revision records the already-existing runtime change;
it does not pretend that the original implementation commit carried the links.

Update the integrity projection with its own immediate predecessor and references
to the governed units extended by that original change. Mark this metadata-only
revision behavior-preserving. Preserve the original design as effective cause.
Likewise revise `IMP-010` and the CYC-018 process-tooling projection when replacing

## Verification and acceptance

Use disposable Git repositories to test valid prefix/format variations, staged
vs unstaged content, malformed references, missing target versions/paths,
non-ancestor targets, and a bad intermediate commit repaired later. Validate the
real repaired snapshot and the branch's introduced range. Audit the old snapshot
separately and show the seven original failures remain detectable.

Run the pinned integration check with the real Active correction status: rejection
until human acceptance is expected. A disposable prospective Accepted tree can
check the remaining integration constraints, but must not change or imply actual
acceptance. The user reviews the completed correction; only explicit acceptance
closes the reopened cycle. No runtime test claims are manufactured by this work.
