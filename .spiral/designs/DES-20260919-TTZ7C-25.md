# Design: Administrative Recovery And Consistent Restore

## Status and scope

Step 2 of CYC-20260919-TTZ7C-17. Implements the recovery intent in
REQ-20260919-TTZ7C-20 at design level, using the durable operations and ordered
history of DES-20260919-TTZ7C-24. EVD-20260919-TTZ7C-23 supplies the baseline gaps.
No recovery tool or new runtime guarantee is implemented by this document.

Ordinary recovery preserves the meaning/order of the existing history. Rebuild
is the separately retained option to execute selected history using changed code
into a new dataset. It must not become a `--force` bypass in ordinary recovery.
The maintainer's design-only correction retains current store files and schemas,
with no migration. This revision removes the earlier dependence on v2 records,
stored sequence/profile fields, and special recovery status types.

Recovery plans, audit journals, and backup/completion reports are new outputs of
the administrative tools, kept outside the canonical store. Normal loading does
not need to parse them. They bind administrator actions and interrupted-tool
resumption, not ordinary dataset reconstruction. Temporary ownership locks are
operational exclusion, not a format-version marker. No required store descriptor,
new commit log, or runtime dependency on an administrative manifest is introduced.

## Read-only inspection

Proposed entry point: `node scripts/recover.mjs inspect --store <config> --out <plan>`.
The store config identifies the base, log/status paths, integrity settings and
deployment information, so non-default paths are not silently replaced by CLI
defaults. Accept declarative configuration; do not execute server configuration
modules merely to discover paths.
This command parses data and metadata without invoking command handlers, custom
workers, custom index modules, or their top-level imports. Existing load-worker
behavior that imports a custom index is not an acceptable inspection mechanism.

Source must be quiescent or an immutable copy for an actionable plan. Inspection
may diagnose a live store but must label that output non-actionable. It records
source identity, file inventory, sizes and cryptographic hashes, expected missing
paths, enabled integrity state, and code/profile identity. Check inventory and
hashes before and after inspection; that check detects change but is not a
substitute for quiescence. Write plans outside the source tree; do not create
lock files, rewrite statuses, truncate logs, or generate indexes during inspection.

For each command report ID, authoritative order/evidence, original logged inputs,
acceptance and execution attempts, final status, expected dataset path, artifact
condition, and external-effect uncertainty. Report the last verified committed
prefix and commands whose effects cannot currently be reconstructed. Failed or
unsafe commands with a valid terminal outcome have no committed delta and do not
by themselves break the canonical prefix. Missing done data does break it.

Validate complete newline-terminated records, required fields, duplicate-ID
consistency, acceptance/attempt history, established order, base identity,
OD-JSONTag framing,
and enabled integrity. A malformed tail remains evidence requiring intervention;
do not discard it merely because it is last. A syntactically valid log is not
proof that missing history never existed. If coverage cannot be established,
report unknown coverage and block assertions about rerun eligibility.

Use command-log position, first-acceptance order, and active/done records as the
ordering evidence described in DES-20260919-TTZ7C-24. There is no stored ordinal
to fill in retroactively. An old concurrent-acceptance disagreement must be
reported with the relevant records; never sort IDs or filenames to invent order.
Independent retained logs/backup evidence may resolve the disagreement. If they
cannot, retain the diagnosis and offer evidence-qualified backup restoration.
Allow consistent committed reads only where the preceding state is established.

Reading a command cannot establish that its implementation used no hidden input.
The plan records the administrator's evidence about the chosen code and complete
command contract. Historical request-dependent handlers cannot be repaired by
supplying a transient request or modifying the logged command during ordinary
recovery. If verified saved data is unavailable, report that rerun is blocked.

## Classification and decisions

| Evidence | Default recovery decision |
|---|---|
| Done with verified dataset and prerequisites | Reconstruct from bytes; never execute the handler |
| Done with missing dataset | Needs recovery; assess later-dataset rule and external effects |
| Accepted only, no active attempt or dataset | Apparently waiting work; on restart require administrator assessment because the format cannot prove the write protocol or absence of prior execution |
| Active, any uncertain attempt, or uncommitted dataset present | Administrator diagnosis; no automatic retry or automatic promotion to done |
| Failed/unsafe terminal outcome | No automatic rerun; report attempts and any surviving uncommitted artifacts |
| Existing corrupt/partial dataset | Diagnose or restore verified artifacts; do not pretend the file is missing |
| Missing/inconsistent command inputs or order | Block rerun; independent evidence may establish order or confirm existing inputs, but this cycle does not inject missing inputs or rewrite a command |
| Valid data with missing default derived indexes | Rebuild default indexes from committed bytes on the destination; do not run mutation-capable legacy hooks |

Restoring a missing file from a verified matching backup is not execution. It can
repair an interior gap when its identity, bytes, and corresponding commit evidence
match. A matching command ID alone is insufficient. Existing data without a
trustworthy commit outcome is not automatically committed just because it parses.

## Exact ordinary-rerun predicate

Use the preserved source's accepted history and complete artifact inventory,
not a target directory after files have been removed:

1. Establish the command's position and the later accepted commands, retaining
   acceptance history even if their latest status is failed/unsafe/active.
2. For an execution candidate with a missing dataset, **every later accepted
   command must also have no dataset**. Presence includes zero-byte no-op files,
   corrupt files, files belonging to accepted-but-not-done commands, and files
   whose validity is uncertain. Unknown presence/order fails the predicate.
3. Establish a valid preceding committed state. Keep original order across the
   selected trailing missing/waiting commands. Do not skip an unresolved earlier
   command and execute a later command against a different starting state.
4. Require explicit approval identifying commands and assessed secondary effects.
   The predicate establishes eligibility, not evidence that execution is safe.

Thus A:data / B:missing / C:data blocks B regardless of C's current status.
A:data / B:missing / C:waiting / D:missing can admit B/C/D in order after approval.
Known terminal no-transition commands can remain terminal; an administrator must
explicitly select a rerun if reconsidering them. If an earlier failed command is
selected for rerun, the same later-dataset restriction applies.

There is no ordinary option to delete/quarantine a later source dataset to make
an interior command eligible. Selecting an earlier backup is an explicit rollback
with its own known-loss report, not a claim to have recovered all existing history.
The full changed-code rebuild exception is described separately below.

## Preview and apply

The plan contains the source snapshot fingerprint, source/base and backup
identities, captured order and inputs, code/profile fingerprints, intended target,
commands to reconstruct/restore/rerun, preserved terminal commands, expected
artifacts, unresolved issues, and known/unknown loss. It states which decisions
require administrator judgment. It contains no assertion that side effects are
safe merely because a checkbox can be selected.

Proposed application:

```text
node scripts/recover.mjs apply --plan plan.json --to recovered-store --audit-dir recovery-audit \
  --approve-rerun B,C,D --operator <identifier> --reason <assessment>
```

1. Require a quiescent source and acquire the ownership locks specified by the
   storage design. No live server queue may advance concurrently. Acquire target
   ownership too; target must be new and outside the source. Reject symlink/path
   overlap and destination overwrite. Plan paths do not grant arbitrary writes.
2. Rescan the full inventory, including absent expected paths and newly appearing
   datasets, and verify source/backup/profile hashes. Any mismatch invalidates the
   plan before command code is loaded. Recompute the later-dataset predicate;
   an administrator approval cannot override it.
   Recognized ownership locks are excluded from content fingerprints so acquiring
   the tool's own lock is not a false mismatch; no data/log files are excluded.
3. Copy/preserve source evidence and construct the verified preceding state in
   the target. Never hard-link mutable source logs/files into the target. Preserve
   both original records and the plan rather than editing history to look clean.
4. Publish a durable recovery authorization in the external audit directory before
   invoking any selected command. It binds plan fingerprint, operator/reason,
   ordered IDs and command hashes, source/target locations, and deployment
   evidence. No missing business inputs are supplied through the tool. Keep the
   immutable source copy, plan, and audit together as the recovery evidence bundle;
   make all these writes durable before execution, outside canonical store paths.
5. Execute sequentially with the same worker/handler inputs as normal execution.
   Mark each recovery attempt durably active before invoking it, and commit using
   DES-20260919-TTZ7C-24. Use the existing active/done/failed/unsafe status values,
   command IDs and attempt fields; append outcomes without erasing earlier records.
   Only the offline approved tool can reopen a terminal command. Link each attempt
   to authorization and original order in the external audit, not through new
   status fields/types. Record the planned attempt durably there before the active
   append; if either write is uncertain, stop without invoking the command. No HTTP
   server or ordinary queue runs on the candidate during apply. Since reopening
   status is not a new schema, older readers may parse it but must not be used to
   operate an unfinished candidate; they lack the new exclusion/recovery policy.
6. Stop on uncertain execution, I/O error, handler failure, or timeout. Leave the
   candidate and audit record for inspection; never automatically resume an active
   recovery attempt. A new plan and fresh external-effect decision are required
   before a retry. Completed attempts can be reconstructed without executing them.
7. Verify that every selected restore/rerun has completed as approved, with no
   unresolved commands or unexplained artifacts. Validate the candidate's complete
   committed state and required files, sync them,
   and publish the external completion report durably before releasing candidate
   ownership. Unfinished candidates retain the ordinary ownership lock; normal
   startup refuses that lock. Lock removal is never the generic stale-PID action:
   it requires an offline assessment, and for a recovery candidate that includes
   its bound plan/audit, remaining commands, and completion report. If that bundle
   is lost, the tool cannot certify or automatically resume the attempt. Preserve
   the candidate for diagnosis or start a new approved recovery from the source.

The source inventory remains the guard throughout a plan. As B, C, D are recovered
in order, B's newly created target data is a predecessor, not a later source
dataset that would invalidate C. On interruption, revalidate the preserved source
and audit plus current candidate before any renewed approval. A durable target
done record with valid data can be reconstructed without rerun even if writing
its external audit outcome failed; an audit claim alone cannot establish commit.
Do not mark failed after a possibly durable done. Retrying an uncertain attempt
with an existing partial dataset remains blocked pending separate diagnosis;
automatic cleanup must not turn that artifact into apparent absence.

Where a retained digest identifies the missing committed changeset, compare the
recreated bytes to that expectation before appending a new integrity record or
done status. A mismatch requires diagnosis; do not erase the old expectation by appending a new
digest and then claim the original state was recovered. Preserve the candidate
bytes and uncertainty. Without such a witness, structural reconstruction and a
complete-command contract cannot independently prove byte-identical historical
output; report that verification limit.

Ordinary recovery uses the original command meaning and compatible deployment.
There is no execution-profile field in the command log. The administrator supplies
retained deployment/source/package evidence in the external plan, and the tool
binds the selected code to prevent changes after preview. A current hash proves
only what is selected now, not what executed originally. Unresolved code identity
blocks a confident ordinary rerun; a materially changed handler must not silently
become a changed-code rebuild. The engine's request-removal fix is compatible with
handlers that already obeyed the complete-command contract. It is not proof that
historical handlers which used request context can be rerun correctly.

## Backup, restore, and promotion

First implement offline consistent backup rather than live incremental snapshots:
stop the writer, acquire ownership, inventory configured base/log/status/integrity
and required artifacts, and copy them to a new destination. Record configuration
and code-profile identity without copying unrelated secrets. Durable-publish all
files, validate their hashes and committed reconstruction, and write a backup
completion manifest last in the external backup evidence bundle, syncing its
directory. The copied store retains its original format and does not require
that manifest for ordinary loading; the restore tool requires it to verify this
backup procedure completed. Reject incomplete backups for automatic restore.
A backup that merely parses may already contain data loss;
record its source coverage and integrity limits honestly.

Restore accepts a verified completed backup, writes a separate candidate, validates
it, and reports its recovered commands and differences from retained source
history. Unknown source history yields explicit unknown loss. Additional surviving
committed changesets may be applied only when order, base lineage, commit evidence,
and required predecessors are verified; never guess that two backups share a base.

Keep original command/status records as a byte-preserved prefix of a candidate
when they are complete and valid; recovery appends use existing schemas. Preserve
all originals separately in every case. Malformed logs, unresolved order, or
missing command inputs are diagnostic/backup-restore cases in this cycle, not an
automatic log-repair or migration facility. Selecting a completed older backup
can be a useful deliberate rollback, but cannot be called recovery of all later
accepted work. Missing or corrupt saved data need matching backup evidence or
an eligible rerun; the design offers no lossless solution when neither exists.

Promotion remains a separate explicit administrator operation. Stop the existing
service, revalidate the completed candidate/report, and switch the deployment's
store configuration to the new location while preserving the old directory and
configuration. Document a reversible service-specific sequence; do not claim
that swapping several directories is one atomic operation. The new server must
validate the chosen store before listening; the promotion tool verifies the
external completion report. Normal loading does not need that report. After new
commands are accepted, rolling back to the old directory can lose those commands and requires
another explicit coverage/loss assessment.

Lock release after a crash is offline and explicit; stale ownership does not
authorize removing data or re-executing commands. The administrator guide must
cover lock diagnostics alongside missing/corrupt artifacts and interrupted apply.

## Rebuild exception retained for follow-up

A future rebuild operation takes an explicit starting dataset, chosen history,
and chosen code profile, producing a new store and regenerated derived/integrity
artifacts. Its execution context communicates `mode: rebuild` and
`sideEffectsAllowed: false` to commands and relevant hooks. Ordinary recovery
does not silently set this flag, because skipping an effect that never happened
can be just as incorrect as repeating one that did.

The flag is cooperative; audit commands/hooks and test effect suppression before
calling a profile rebuild-safe. External reads, clock/randomness, and omitted
inputs still affect reproducibility. Rebuild can deliberately differ under new
code. Full rebuild CLI, execution, and activation are outside this cycle.

## Verification mapping and implementation sequence

| Design boundary | Required evidence |
|---|---|
| Read-only inspection | Byte-identical source before/after, no module/handler effects, malformed-tail and missing-history diagnostics |
| Rerun predicate | PL13 both status variants, zero-byte/corrupt later files, failed/unsafe acceptance history, missing order, permitted B/C/D suffix |
| Apply binding | Changed source file, newly appearing dataset, changed code/backup, path alias/overlap, stale plan and competing writer all rejected before execution |
| Execution | PL12 effect witness unchanged until approval; approved sequence preserves inputs/order; no live queue overtake; every active/done barrier fault exercised |
| Interrupted apply | Originals intact, incomplete candidate blocked, completed attempts not repeated, active attempt requires renewed decision |
| Inputs/order | PL14/16, replacement for PL15 proving request context is unavailable, ambiguous old order, incomplete historical commands, and changed/unknown deployment identity |
| Existing format | Unchanged command/status/integrity schemas, no descriptor or conversion, prior command bytes retained, accepted-only restart requires assessment |
| Audit separation | Final store loads without tool reports; apply/promotion requires its external evidence; faults between audit/active/done/report writes stop safely |
| Recreated state | Existing expected digest matches or recovery stops; absent digest reports verification limits; incomplete approved plans cannot be promoted |
| Backup/restore | Consistent backup under exclusion, incomplete backup rejection, verified reconstruction, coverage/loss report, interrupted copying, restore without rerunning handlers |
| Promotion | Candidate validation, explicit configuration switch, retained original, failures before/after activation and honest rollback limits |

Implement inspection/classification first, then plan validation and reconstruction
on a copy, then guarded execution and interruption records, then offline backup/
restore and operator documentation. Reuse the same ordered record decoder and
durable operations as normal execution. Keep the reference oracle independent.
Do not convert expected failures to passing tests by weakening these decisions.
The exception is PL15's input-retention assertion: its historical failure remains
evidence, but its interpretation is corrected by the maintainer's complete-command
boundary. Document that change and add the discriminating removal/equivalence test.

Still required for acceptance: implement and execute the above tests, record
latency and the Linux/storage envelope, run the disposable block-level power-loss
exercise, and obtain human evaluation of the entire active cycle. This step is
design only. Unknown historical inputs/order, unavailable backup evidence, and
irrecoverable history remain explicit limits, not reasons to introduce migration.
