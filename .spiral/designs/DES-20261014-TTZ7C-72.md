# Design: lazy committed-version views

## Role

Define the internal committed-version catalogue and the controlled query API
that expose successful commands, per-record object history and same-version
objects without changing SimplyStore's durable formats or current dataset view.

## Why this exists

REQ-20261014-TTZ7C-71 requires queryable audit history from data SimplyStore
already persists. The current file-backed loader has one ordered source per
global version, while the query bridge deliberately exposes only current data,
ID lookup and schema. The design adds a version dimension to that bridge rather
than copying history into the stored objects or creating another database.

## Cultural influence / constraints

The Muze preferences for simplicity, inspectability, bounded assumptions and
correctable boundaries favor a small catalogue derived from existing sources.
The design keeps complete historical snapshot switching behind a later optional
query-view capability instead of prematurely making it part of the public API.

The existing file-backed and isolated-query designs constrain implementation:
records remain lazy file views, host paths and parser state stay private, access
grants remain host-owned, and only copied primitives/descriptions cross into a
fresh isolate.

## Behavior / responsibilities

### Global versions

The ordered loaded source list is the version order:

- source zero is version zero, the base dataset;
- source `n` is version `n`, produced by the `n`th successfully committed
  command;
- no-op successful commands still have a version and an empty changed-object
  collection;
- commands without terminal `done` status have no version.

The version timestamp is `new Date(source.identity.modified).toISOString()`.
It is explicitly a dataset-file modification timestamp. It is not a new durable
commit-time claim and may change when files are copied or restored.

### Committed version catalogue

Construct one catalogue from the verified startup inspection, ordered sources
and per-source ID entries. Retain only successfully committed command references.
The catalogue maps command IDs to versions and record numbers to the versions
whose sparse offset maps contain that record. It does not decode record payloads
during startup.

The loader retains each source's own ID entries, already obtained from its
verified ID sidecar or reconstruction. A version's peer objects are the unique
record numbers in those entries; this excludes root/internal records without an
ID while retaining deleted entity records.

The command catalogue retains only compact metadata for each successful command:
ID, name, author, message, dataset-file timestamp and version. Query workers do
not receive command-log paths, byte ranges or original payloads. Separate tools
can inspect the authoritative command log if richer input analysis is needed.
Live publication adds the compact descriptor after `done`.

### Historical record resolution

For `(record, version)`, select the last source at or before `version` whose
offset map contains that record. Parse through an immutable version-aware record
view whose line references resolve by the same rule. The selected record and
all records reached from it therefore represent the dataset immediately after
that version, rather than combining an old record with current linked records.

Reuse the query worker's already open, identity-checked source readers. A query
may create lightweight version-specific parser/view state lazily, but the worker
must not retain a complete parser, root graph or decoded dataset for every
version. Drop per-query version views after serialization. Existing parser cache
limits and access modules apply to historical reads. Any historical lazy-read
storage failure participates in the same host-owned fail-stop signal as current
data reads.

Nested query views inherit the owning record's history. Record number is private
lineage identity and never becomes a query-visible property. A string lookup is
resolved through the current ID index, so ID reuse intentionally follows the
current owner; a retained historical object continues to identify its own record.

### Query API

Extend the guest-created `meta` with host-backed, read-only facades:

```js
meta.commands.all
meta.commands.get(commandId)
meta.versions.get(versionNumber)
meta.history.get(objectOrCurrentId)
```

`meta.commands.all` is in ascending committed version order. `get` returns
`undefined` for an unknown command/version. `meta.history.get` returns an empty
array when the value does not identify a current stored record.

A command view provides:

```js
{
    id,
    name,
    author,
    message,
    timestamp,
    version
}
```

`author` and `message` are convenience projections with no additional trust
claim. `timestamp` is the same dataset-file timestamp as its version.

A version view provides:

```js
{
    version,
    timestamp,
    command,
    objects
}
```

Version zero has `command: null`. `objects` is a lazy immutable array of that
source's ID-bearing record views at that version. No `data` or `dataset` property
is defined in this cycle; those names remain available for later complete
historical dataset switching.

An object-history entry provides:

```js
{
    version,
    timestamp,
    command,
    object
}
```

Entries are oldest to newest. The command object is shared with the command and
version catalogues inside one query. Query serialization retains ordinary
JSON/JSONTag behavior and is bounded by the existing deadline and result limit.

### Startup and live publication

`StoreRuntime` retains the committed command/version descriptors produced by
inspection and passes them with sources to both query pools. After a command's
changeset and indexes are synchronized and its `done` status is durable, the
runtime appends its source and descriptor to its catalogue and sends one ordered
update to each pool. Replacement workers initialize from the complete current
catalogue. A query sees either the preceding version or the new complete version,
never command metadata without its source or vice versa.

## Boundaries

What belongs here:

- successful command/version metadata;
- source-derived record lineage;
- compact command metadata and lazy historical record views;
- query guest facades and live update ordering;
- focused documentation and verification of the public query surface.

What must remain outside:

- complete historical root/dataset selection;
- UI, REST proxy changes, author validation and new authorization;
- replay/rebuild, workspace history or command semantics;
- new persistent indexes, migrations or changeset formats.

What change should this boundary protect us from:

Future historical snapshot support should reuse the version-aware resolver and
expose a version root without changing object-history identity or command
metadata. Alternative storage/parser implementations should be replaceable
behind the same query-facing concepts.

## Supporting / intrinsic work

| Support | Why necessary |
|---|---|
| Preserve per-source ID entries during loading | Identify version peers without eagerly parsing changeset records. |
| Version-aware record-location resolver | Return correct old record contents and version-consistent links. |
| Virtual query references for commands, versions and history | Keep host objects, paths and parser internals outside the isolate. |
| Live catalogue update | Make new commits observable without restart while preserving publication order. |

## Alternatives considered

| Alternative | Why not now | Evidence / trade-off |
|---|---|---|
| Store command/version metadata on every data object. | Duplicates audit data, changes formats and couples domain objects to storage history. | Existing source order and offsets already derive the relationship. |
| Build and retain one full parser/dataset per version. | File handles and metadata scale roughly with history times dataset size. | Only selected records and links are needed for the first slice. |
| Resolve old records but all links against current data. | Produces misleading mixed-time objects. | History must describe the object as it existed in that version. |
| Expose original command inputs in query workers. | It adds range/digest/file-handle machinery for data the query history does not need. | The maintainer selected compact metadata and separate future tooling for original inputs. |
| Implement whole-dataset time travel first. | Expands API, performance and evaluation scope before the audit trail is proven. | Explicitly deferred by the maintainer. |

## Complexity / maintainability check

- Concepts introduced: global committed version, version catalogue, historical
  record view, virtual command/version/history query references.
- Dependencies introduced: none.
- Expected change radius: inspection record descriptors, file/source loading,
  runtime/query-worker initialization and update, query view/guest, tests and
  query-runtime documentation.
- Replaceability considerations: catalogue and resolver consume existing source
  descriptors; no domain object or disk format depends on their implementation.
- What would make this harder to change: leaking record numbers/source paths into
  query results, caching complete snapshots, or conflating changesets with full
  historical datasets. The design forbids those shortcuts.

## Verification plan

1. Add failing real-worker queries for command enumeration/lookup, version
   lookup, history lookup and peer objects.
2. Cover base, multiple edits, new object, deletion/restoration, ID mutation or
   reuse, multi-object commands, no-op and unsuccessful commands.
3. Prove historical scalar properties and linked records resolve at the selected
   version, with shared identity inside one query and immutable guest views.
4. Prove access grants, reflection, result size, timeout and actual storage-read
   failure behavior remain enforced.
5. Compare startup reconstruction with live publication and worker replacement.
6. Run the complete test suite and focused lint.
7. Measure a representative long history for startup decoding, history-query
   latency, worker heap and file descriptors. Report the bounded scope; do not
   infer universal production capacity.

## Deferred decisions

- Exposing `meta.versions.get(n).data` or another complete historical root.
- Selecting an entire query's default `data`/`root` version.
- History-specific authorization or redaction.
- Stable timestamps independent of filesystem copy/restore metadata.
- A user interface and curriculum-store dependency/integration cycle.
