# Design: Cohesive Store Runtime With Mechanism Boundaries

## Design objective

Represent the running store as one `StoreRuntime` instance. Its methods tell the
store lifecycle story at one abstraction level. Express remains the compatibility
and transport shell. Existing storage, inspection, recovery and worker mechanisms
remain replaceable collaborators instead of being reproduced inside the runtime.

This is primarily a boundary change. Command-log authority, durable
acceptance/completion, startup refusal and administrative recovery retain their
accepted semantics and file formats. The design also includes the authorized
correction of the ineffective slow-query timeout.

## Why this representation

The current representation is one nested `main()` closure. It hides related state
reasonably well from other modules, but it also makes HTTP, persistence, workers,
process policy and domain sequencing one indivisible unit. Splitting each nested
function into a module would create many names while leaving that relationship
implicit.

A runtime instance gives the mutable state an explicit owner and supplies one
domain vocabulary across startup, commands, queries and shutdown. Plain adapter
functions/objects preserve mechanism replaceability. This follows the Muze
preference to move a boundary and cut assumption threads rather than add a
framework.

## Runtime boundary

Add `src/store-runtime.mjs` exporting `StoreRuntime`. Its static `open()` creates
one instance from options and optional mechanism overrides, then opens the store.
The instance owns:

- normalized store and worker configuration;
- store ownership and the inspected committed state;
- loaded dataset buffers and metadata;
- command status, acceptance serialization, command queue and active runner;
- normal and slow query worker pools;
- healthy, storage-failed and closing state.

The instance does not own Express requests/responses, route negotiation, static
web files, the listening socket, OS signals or process exit. It does not implement
raw filesystem calls or worker-thread event handling.

The default mechanism set is a small plain object constructed in the runtime
module from existing operations. Tests may replace only the mechanisms needed
for direct evidence. This is ordinary late binding, not a service locator: runtime
methods use named properties and no mechanism is discovered dynamically.

## Story-level operations

Public or coordinating runtime methods should read in domain order:

### Open

1. acquire exclusive ownership;
2. inspect the store and explain why it cannot open;
3. synchronize retained committed prerequisites;
4. load committed data;
5. initialize status and query workers.

If any step fails, release ownership before propagating the error. Detailed
inspection selection, file synchronization and worker protocol remain named
lower-level operations.

### Accept a command

1. reject mutation when failed or closing;
2. serialize acceptance;
3. parse and validate the complete command;
4. return an existing command's current status for a duplicate ID;
5. durably record the command and accepted status;
6. place the exact logged command snapshot onto the queue;
7. return a plain acceptance result.

The HTTP adapter sends the result and then asks the runtime to drain the queue,
preserving the current ordering between acceptance response construction and
execution start. Runtime callers can make the same explicit call without HTTP.

### Execute queued commands

For each command in command-log order:

1. durably mark the command active;
2. execute the command worker against the current store state;
3. durably record a safe terminal failure, or continue with success;
4. synchronize every required committed file;
5. durably mark the command done;
6. publish new data and metadata to the query workers.

The coordinating method should contain these domain operations, not JSONTag
serialization, worker event handlers or individual filesystem calls. Existing
fault points stay at the same semantic boundaries.

### Query and close

Query methods select the pool and its timeout together. `/query/` selects the
normal pool and configured `timeout`; `/slowquery/` selects the slow pool and
configured `slowTimeout`. Both GET and POST tasks pass the selected duration as
`timeout`, which is the property consumed by the query worker, and return the
worker's plain result.

Close stops admission, waits for serialized acceptance and the command runner,
closes both query pools and releases ownership when storage remains trustworthy.

Storage uncertainty changes runtime state once, reports through the configured
failure callback and retains ownership evidence. The server shell supplies the
existing logging and deferred process-exit policy.

## HTTP compatibility shell

`src/server.mjs` continues to default-export an Express application with a
`run(options)` method. Route handlers are ordinary adapter functions that:

- perform content negotiation and create plain query input;
- pass the raw command text to the runtime;
- translate returned result values to the existing HTTP response shape;
- serve static/query UI resources;
- own listener errors, signals and process exit.

The module may export a server/app factory as an additive testing or embedding
seam, but the documented default export remains unchanged. Store state must not
remain in module globals. Calling code should not need to know the runtime's
mechanism overrides.

## Worker boundary

Retain the distinction between one-shot workers and long-lived query pools.
Consolidate one-shot load and command worker event/timeout/termination mechanics
only if one small runner can preserve their different timeout outcomes clearly.
The runtime converts a command timeout into the existing `unsafe` result, while a
load timeout remains a startup error. Do not force query pools into the same API.

`workerPool.mjs` is an existing long-lived adapter. Style cleanup or correctness
work in it is included only when required by runtime integration or demonstrated
by focused tests; its age and formatting alone do not justify expansion.

## Function and naming discipline

Use these extraction tests while implementing:

1. Does the containing function now read at one abstraction level?
2. Does the new name communicate a stable domain operation or hide meaningful
   lower-level detail?
3. Will a reader encounter the operation often enough to justify learning it?
4. If related methods share state, do they belong on `StoreRuntime` or an existing
   cohesive collaborator rather than another helper?
5. Is a long name revealing excess responsibility, or is it the clearest precise
   name for an irreducible operation?

Avoid forwarding methods which merely rename one call. Keep short parsing or
projection logic local when extraction would make the story harder to follow.
Order class methods so the public lifecycle can be read before its supporting
details where practical.

## Direct verification seam

Add focused runtime tests using a temporary real store plus small worker/query
test doubles. Exercise at least:

- open and close ownership;
- accepted command persistence and returned status;
- duplicate ID behavior without a second append or execution;
- concurrent acceptance preserving command-log/execution order;
- successful completion and query publication only after `done`;
- handler failure producing its terminal status without publishing data;
- storage uncertainty stopping subsequent mutation.

These tests validate decisions cheaply. Existing child-process and HTTP tests
remain authoritative for integration, crash and actual worker behavior. Do not
duplicate the complete power-loss suite at the runtime seam.

## Dependency correction

After implementation import/use verification:

- remove root `codemirror`, `write-file-atomic` and `process` if shipped code and
  package contents confirm they are unused;
- update the `vm2` declared range to the installed supported patch;
- upgrade ESLint, `@eslint/js` and `globals` to current Node-compatible majors and
  adapt configuration only as required;
- update example JSONTag and UUID, remove unused example ESLint, and resolve the
  unused vulnerable transitive UUID declaration from `jsontag-types` only with a
  verified compatible override or equivalent narrow correction;
- regenerate the locally ignored root/example locks so installed verification
  uses manifests whose package versions and dependency graphs agree. The
  repository intentionally does not track either lock file.

Do not replace a well-fitting dependency to satisfy visual symmetry. Audit output
is evidence, not authority to introduce an incompatible override.

## Compatibility and failure risks

| Risk | Control |
|---|---|
| Moving queue start changes response/execution timing | Preserve explicit send-then-drain order and retain ordering tests |
| Runtime error handling releases ownership after uncertain storage | Centralize the one-way storage-failed transition; close releases only while healthy |
| Injected mechanisms form a generic container | Keep one closed, named mechanism object with concrete defaults |
| Runtime becomes a god object | It owns only opened-store lifecycle/state; HTTP, filesystem primitives, worker protocol and admin recovery stay outside |
| Direct tests pass while process behavior changes | Run all existing durability, power-loss, handler and recovery suites |
| Package upgrade changes example semantics | Build, start, query and command the example after a clean install |

## Complexity and replaceability

The design adds one central concept: `StoreRuntime`. A small one-shot worker
runner revision is allowed only if it removes both existing protocol copies.
No hierarchy, container or broad interface layer is added.

Expected code movement is substantial from `server.mjs` into the runtime, while
net code reduction is secondary. Success is less knowledge per component:
Express knows transport, the runtime knows store sequencing, storage modules know
durable I/O, and worker adapters know worker protocol.

The runtime boundary makes future query sandbox replacement, rebuild execution
and post-commit extension work cheaper without implementing them now.

## Store inspection workflow

Keep `inspectStore(options)` as the exported compatibility entry point. It
constructs a module-local `StoreInspector` and returns its inspection result.
The inspector owns configuration, diagnostics, initial inventory, command
history, integrity state, parser state, reconstructed buffers/data and committed
prefix validity.

Its coordinating method reads in inspection order:

1. validate configured canonical paths;
2. capture the initial file inventory;
3. read logged commands and apply their status history;
4. validate committed execution order;
5. load integrity evidence;
6. reconstruct the committed dataset prefix;
7. validate required and unexplained artifacts;
8. verify that the inspected snapshot stayed stable;
9. construct the existing plain report.

Keep stateless, reused operations such as `storePaths`,
`mutableDirectories`, `inventory`, `validCommandId` and `hash` as module
functions. Preserve current reads, ordering, errors and report fields during the
structural move. Duplicate changeset reads and repeated later-dataset queries may
be reviewed separately after equivalence is established.

## Administrative recovery workflows

Keep every exported recovery function and its arguments unchanged. Represent the
three substantial stateful operations with module-local workflow classes:

- `RecoveryApplication` owns authorization, source/candidate ownership,
  workspace and audit paths, reconstructed state, command attempts and completion;
- `BackupRestoration` owns manifest rebasing, source comparison, workspace
  ownership, candidate validation and completion reporting;
- `OfflineLockRelease` owns lock discovery, retained owner evidence, completion
  checks, preview data and change-before-release verification.

The exported `applyRecovery()`, `restoreBackup()` and
`releaseOfflineLocks()` functions remain small entry points. Each workflow's
`run()` or `preview()` method describes its phases at one abstraction level.
Supporting methods should correspond to administrator-visible concepts such as
approval validation, workspace preparation, committed-prefix loading, one
approved command attempt, candidate verification and completion publication.

`planRecovery()`, `backupStore()`, `finishRecovery()` and
`verifyCandidate()` remain functions unless implementation review finds a
specific mixed abstraction that cannot be clarified locally. Do not introduce a
generic recovery base class, service container or filesystem wrapper.

Failure cleanup is part of compatibility. Source ownership is released in the
same circumstances as today. Candidate/root locks and audit evidence remain on
failed recovery or restore operations, and are released only after successful
completion. Returned reports and lock previews remain plain serializable data
apart from the existing `finish()` capability.
