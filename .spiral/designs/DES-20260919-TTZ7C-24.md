# Design: Durable Publication And Ordered Command Records

## Status, scope, and evidence

Design step of CYC-20260919-TTZ7C-17, following REQ-20260919-TTZ7C-20 and the
failures in EVD-20260919-TTZ7C-23. This document specifies intended behavior;
it does not claim implementation or cycle acceptance. It continues the active
cycle's agreed refinement of the durability roadmap.

The storage primitives can be implemented without changing OD-JSONTag bytes.
The versioned command-record proposal below is an explicit compatibility
decision for review before that format is implemented or deployed. There is no
authorization here to migrate existing user data silently.

## Durable file operations

Introduce a small storage module, shared by runtime, conversion, and recovery:

| Operation | Completion condition |
|---|---|
| `writeAll(handle, bytes)` | Loop over bytesWritten until complete; reject zero progress, invalid counts, and errors; never equate one successful write callback with a complete file |
| `publishFile(path, bytes)` | Create a unique temporary file in the same directory, write all bytes, sync file, close, rename to destination, sync parent directory, close directory |
| `appendRecord(path, bytes)` | Serialize writes per file; append a complete newline-terminated record, sync file data, close, sync parent directory, close directory |
| `syncDirectory(path)` | Open and sync the directory, await completion and close; propagate unsupported-operation and I/O errors |

The initial implementation syncs the append parent on every completed append.
This avoids relying on a fragile existence check or process-local cache to infer
that a filename was previously durable. Optimize only after measurement and tests.
For nested new directories, make each containing entry durable up to an already
established directory. File permissions should follow existing behavior.

File sync does not itself persist a directory entry: see the
[Linux fsync contract](https://man7.org/linux/man-pages/man2/fsync.2.html).
Use [Node FileHandle writes](https://nodejs.org/docs/latest-v24.x/api/fs.html#filehandlewritebuffer-offset-length-position)
and check their reported byte count. The design does not assume `writeFileSync`
or an atomic rename alone constitutes a persistence barrier.

Temporary-file cleanup is best effort and must not obscure the first I/O error.
A failed open must not be masked by closing an undefined handle. Propagate close
failures as well as write/sync/rename failures. Preserve uncertain final artifacts
for inspection; do not delete a published file in an attempt to prove rollback.

`publishFile` alone is not a multi-file transaction. Commit sequencing below
establishes which complete files belong to canonical state. Initial conversion
should publish into a new directory, with a completion descriptor written last;
do not overwrite an operating store's base independently of its other artifacts.

## Ownership and serialization

All mutation runs under exclusive store ownership. For the first dependency-free
implementation use atomically created lock directories, one per canonical mutable
directory, acquired in sorted path order. This deliberately treats stores sharing
the default index/log directory as conflicting. Resolve existing parent paths;
do not allow symlink aliases to create independent locks on the same directory.

Write owner diagnostics (random token, PID, host, start time) and sync the lock
entry before any store mutation. The token must match on release; clean shutdown
removes the lock and syncs its parent. Crash leftovers require an explicit offline
administrator release after confirming no writer remains. PID age, a timeout, or
a failed signal probe alone must never authorize automatic stealing. A crash
between mkdir and metadata publication is still a lock, not an empty slot.

This is cooperative exclusion, not protection against arbitrary file writers.
Read-only inspection does not create source lock files. Backup and recovery apply
require a stopped/quiescent source plus ownership; verify source fingerprints
after acquiring it. Tests must demonstrate competing startup/apply exclusion and
crash-leftover handling. Kernel advisory locks are an alternative, but would need
a proven Node integration; no new native dependency is chosen in this step.

Within the owner process use one acceptance FIFO and one serialized status writer.
Worker messages do not release the command-runner slot until the parent finishes
persisting the outcome. Only one command handler runs at a time. Acceptance may
continue during a healthy running command, but storage uncertainty closes both
acceptance and execution queues.

## Input-complete, versioned command log proposal

Keep the HTTP command body and handler command object unchanged. Capture the
serializable execution request before logging, and deliver exactly that captured
record to both initial execution and recovery. The default fields are the current
method, original URL, and parsed query; configured capture adapters must declare
any additional required inputs. Do not serialize live request/socket objects or
indiscriminately add credentials. Missing required input rejects acceptance.

Proposed v2 record (one JSONTag record per line; values below are illustrative):

```json
{
  "recordVersion": 2,
  "sequence": 1,
  "command": {"id": "A", "name": "addPerson", "value": {"name": "Ada"}},
  "request": {"method": "POST", "url": "/command", "query": {}},
  "executionProfile": "deployment-revision-and-context-contract"
}
```

`command` is the original complete JSONTag value, not a merge with transport
metadata. Preserve tagged values. Workers retain their existing task.command,
task.request, data, and meta interface: the dispatcher unwraps the log record and
uses the same serialized command/request snapshot for initial and recovered work.
The default worker forwards request to runCommand; existing handler argument
positions stay unchanged. Persisted profile identity names the chosen code and
input-capture contract; recovery verifies the operator-selected deployment against
it. A hash of one entry-point file is not proof of dependency/code equivalence.

Sequence is allocated under the acceptance FIFO and grows monotonically (safe
integer, reject overflow). Allocation, log append, accepted-status append,
in-memory status, and queue insertion share that FIFO. Only after both appends
are durable may HTTP 202 be sent. Response delivery order across clients is not
the authoritative order; durable sequence is. Append accepted/active/terminal
statuses with matching command ID and sequence. Never reorder through Map keys.
Reconstruction orders committed changesets by this sequence; queued work uses
the same order. Failed/unsafe commands can have no canonical transition without
forcing later sequences to be contiguous committed numbers.

Duplicate IDs are checked inside the FIFO. Matching command/context retries
return the known status without another transition; conflicting retries return
an explicit conflict in v2. A log entry without accepted status is an orphan,
not executed work. An I/O error during acceptance halts admission; restart must
classify the orphan rather than silently reuse its ID/sequence. A valid durable
accepted record with a lost HTTP response is still accepted.

## Explicit compatibility and initialization

Versioned log records are a format extension, not a backward-compatible claim.
The choice is an envelope rather than reserved command fields or a second
request-input sidecar: it avoids field collisions and keeps execution inputs in
the command log. The tradeoff is explicit reader/writer version coordination.

Proposed managed-store initialization writes a small versioned descriptor last,
after base, empty or imported logs/status, and required integrity metadata are
durable. It identifies format, base identity/digest, configured artifact paths,
and execution profile. Required declared files must exist at startup; do not
recreate missing logs merely because the base parses. A missing descriptor for
an explicitly configured v2 store is an error, never automatic fallback to v1.
The descriptor is static layout/initialization evidence, not another per-command
commit log or a signature against deliberate whole-store replacement.

Reader/writer behavior for the proposed rollout:

- Existing v1 stores remain inspectable and can serve validated reads. Do not
  implicitly rewrite their logs or synthesize request context.
- V2 mutation requires explicit initialization/migration into a separate
  destination and explicit activation. Enabling the v2 writer against a legacy
  store fails with a migration diagnostic. Legacy mode must not advertise the
  complete new durability/replay guarantee.
- The byte/directory fixes can apply to v1 writes without format change. V1
  remains a compatibility path during rollout, with the known input/replay limits
  disclosed; the complete P1-P12 claim requires v2 adoption. Removing that legacy
  write path or making migration mandatory is a separate public-behavior decision.
- Migration copies retained original evidence, verifies committed data, derives
  order only when legacy status/execution evidence supports it, and explicitly
  records unknown historical inputs. Missing request inputs must never become
  invented empty objects. Incomplete historical commands cannot be rerun until
  the administrator supplies independently justified inputs in the recovery plan.
- Downgrade requires restoring the untouched original or a compatible backup.
  Old binaries are not claimed to understand or safely reject a v2 store; pin
  the binary/configuration at activation. Do not mix v1 and v2 writes in one log.

The migration/default-mode tradeoff needs explicit maintainer review before the
log-format rollout. It does not block implementation of byte-complete publication
and directory barriers against the existing format.

## Command execution and completion

1. Select the earliest eligible accepted sequence. Append/sync active before
   invoking a worker, so accepted-only v2 work can be distinguished from uncertain
   started work when evidence is intact.
2. Execute command and current pre-serialization index mutations. Await required
   hooks, including returned promises, before final serialization; test ordering
   and rejection behavior rather than silently changing handler permissions.
3. Publish the complete changeset through the durable primitive. Preserve sparse
   OD-JSONTag numbering and zero-byte no-op changesets.
4. Await index finalization; publish required built-in sidecars durably. The
   current default loader can rebuild ID/offset indexes, as PL05 shows, but that
   is not a reason to leave promised output files half-written. Custom finalizers
   that promise required external files must use equivalent barriers; awaiting
   a hook alone cannot certify arbitrary external I/O.
5. If integrity is enabled, append/sync its changeset digest, including the
   manifest directory barrier. Validate manifest/base requirements at startup.
6. Append/sync done. Only then update live status, publish buffers to queries,
   and release the runner slot. A query-publication failure cannot undo done;
   stop/reload query service from committed state instead of appending failed.

Any required persistence failure enters a storage-failed state: close admission,
terminate active execution if necessary, stop queue advancement, and report an
uncertain outcome. Do not append a misleading failed record after a possibly
durable done. The error path must not try to keep operating through the same
failed status writer. Safe reads require separately established committed state;
the simplest first implementation may exit after surfacing the diagnostic.

Handler errors and timeouts remain distinct from storage faults. If terminal
failed/unsafe status can be durably recorded, no canonical transition is published
and normal subsequent work may continue under the existing timeout contract.
Such commands are never automatically rerun; existing uncommitted files and
external effects still require diagnosis before administrative action.

## Startup and implementation order

Parse and cross-check descriptor, input log, status transitions/order, required
files, framing, and enabled integrity without changing command state. Reconstruct
only committed transitions. Missing or inconsistent committed data fails before
any recovery status append. Active or artifact-bearing uncommitted commands are
uncertain; route them to the administrative procedure, never active-to-accepted
rewrites. V2 accepted-only work can run normally only when complete validated
evidence proves it never started and no unresolved earlier work is bypassed.
Legacy uncertainty is never resolved by assuming the new protocol held then.

Implement byte-complete publish/append and directory barriers first (PL02/03/04/
10 plus conversion/integrity variants), then parent error handling and queue
ownership. Implement v2 logging/order only after its compatibility decision is
settled. Follow with administrative recovery under DES-20260919-TTZ7C-25.

New tests must cover initial creation, zero-byte/short writes, close/open error
masking, every barrier, optional integrity, concurrent acceptance/duplicates,
terminal-status persistence failures, query-update failure after done, lock
exclusion, and explicit migration/downgrade behavior. The baseline harness must
trace any newly used filesystem API before it can claim barrier coverage.
Measure fsync latency and run the disposable filesystem exercise; documentation
alone establishes none of those runtime guarantees.
