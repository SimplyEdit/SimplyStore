# Design: Durable Publication And Ordered Command Records

## Status, scope, and evidence

Design step of CYC-20260919-TTZ7C-17, following REQ-20260919-TTZ7C-20 and the
failures in EVD-20260919-TTZ7C-23. This document specifies intended behavior;
it does not claim implementation or cycle acceptance. It continues the active
cycle's agreed refinement of the durability roadmap.

The maintainer's subsequent correction in SRC-20260919-TTZ7C-18 constrains this
earlier revision to design only, using the existing store formats without migration.
It supersedes this document's earlier v2 envelope/descriptor proposal. The subsequent authorization in SRC-20260919-TTZ7C-18 permits completing the
whole cycle with this corrected design; the no-format-change constraint remains.

Retain OD-JSONTag base/changeset bytes, filenames, command records, status records,
and the optional integrity-record schema. No envelope, sequence field, execution
profile field, required store descriptor, log conversion, or mixed-format decoder
is introduced. Existing stores receive prospective write hardening after validated
opening; historical loss or uncertainty cannot be repaired by upgrading software.
Operational locks and external recovery plans/reports are described explicitly
below and in DES-20260919-TTZ7C-25; they are not a new canonical store format.

## Durable file operations

Introduce a small storage module, shared by runtime, conversion, and recovery:

| Operation | Completion condition |
|---|---|
| `writeAll(handle, bytes)` | Loop over bytesWritten until complete; reject zero progress, invalid counts, and errors; never equate one successful write callback with a complete file |
| `publishFile(path, bytes)` | Create a unique temporary file in the same directory, write all bytes, sync file, close, rename to destination, sync parent directory, close directory |
| `appendRecord(path, bytes)` | Serialize writes per file; append a complete newline-terminated record, sync file data, close, sync parent directory, close directory |
| `syncDirectory(path)` | Open and sync the directory, await completion and close; propagate unsupported-operation and I/O errors |

The initial implementation syncs the append parent on every completed append.
This avoids relying on a fragile existence check or process-local cache to infer
that a filename was previously durable. Optimize only after measurement and tests.
For nested new directories, make each containing entry durable up to an already
established directory. File permissions should follow existing behavior.

File sync does not itself persist a directory entry: see the
[Linux fsync contract](https://man7.org/linux/man-pages/man2/fsync.2.html).
Use [Node FileHandle writes](https://nodejs.org/docs/latest-v24.x/api/fs.html#filehandlewritebuffer-offset-length-position)
and check their reported byte count. The design does not assume `writeFileSync`
or an atomic rename alone constitutes a persistence barrier.

Temporary-file cleanup is best effort and must not obscure the first I/O error.
A failed open must not be masked by closing an undefined handle. Propagate close
failures as well as write/sync/rename failures. Preserve uncertain final artifacts
for inspection; do not delete a published file in an attempt to prove rollback.

`publishFile` alone is not a multi-file transaction. Commit sequencing below
establishes which complete files belong to canonical state. Initial conversion
should publish into a new directory under ownership and validate all output before
releasing ownership; do not overwrite an operating store's base independently of
its other artifacts. No completion descriptor is added to the store.

## Ownership and serialization

All mutation runs under exclusive store ownership. For the first dependency-free
implementation use atomically created lock directories, one per canonical mutable
directory, acquired in sorted path order. This deliberately treats stores sharing
the default index/log directory as conflicting. Resolve existing parent paths;
do not allow symlink aliases to create independent locks on the same directory.

Write owner diagnostics (random token, PID, host, start time, purpose) and sync
the lock entry before any store mutation. The token must match on release; clean
shutdown removes the lock and syncs its parent. PID age, a timeout, or a failed
signal probe alone must never authorize automatic stealing. A crash between
mkdir and metadata publication is still a lock, not an empty slot.

Revised 2026-09-26 for REQ-20260926-TTZ7C-66: the owner also proves it is alive.
Before publishing its diagnostics, it listens on a Unix socket `owner.sock` in
the lock and records `liveness: "socket"`; release closes and removes it. The
kernel refuses connections to a socket whose process has ended, however it
ended. A server start (`purpose: "runtime"`) that finds such a runtime lock
connects to it: a refused connection proves the owner is gone. Any other
outcome, including success, a missing or partial lock, a lock without
`liveness`, another purpose, an error or a timeout, is no proof and startup
refuses as before. Paths too long for a socket or filesystems without sockets
publish no liveness and keep administrator release.

Takeover serializes on an atomically created `.simplystore-lock.takeover`
directory beside the lock. Holding it, the starter re-reads the lock, requires
the same token and a refused connection again, writes a takeover audit record
with the previous owner's diagnostics into the store directory, moves the dead
lock aside, creates its own lock as usual, removes the old one and then the
takeover directory. A leftover takeover directory blocks takeover and is
removed by the administrator release. Ownership taken this way proves only
that no writer remains: the unchanged strict startup assessment still refuses
unfinished commands, and the new owner's failed start releases its ownership
as any failed start does. Other crash leftovers, including administrative
locks, still require an explicit offline administrator release. The proof
assumes one machine uses a store directory.

This is cooperative exclusion, not protection against arbitrary file writers.
Read-only inspection does not create source lock files. Backup and recovery apply
require a stopped/quiescent source plus ownership; verify source fingerprints
after acquiring it. Tests must demonstrate competing startup/apply exclusion and
crash-leftover handling. Kernel advisory locks were the named alternative; a
listening socket provides the same kernel-held evidence of process death in
Node without a native dependency.

A server handles stop signals from its start. A stop that arrives while the
store is opening lets opening finish (or fail), then closes and releases
ownership normally.

Within the owner process use one acceptance FIFO and one serialized status writer.
Worker messages do not release the command-runner slot until the parent finishes
persisting the outcome. Only one command handler runs at a time. Acceptance may
continue during a healthy running command, but storage uncertainty closes both
acceptance and execution queues.

## Complete commands; no transport execution inputs

The logged command value is the complete invocation input beyond the preceding
dataset. Keep one JSONTag command per line, with existing `id`, `name`, and
application fields. Serialize once after validation; use that exact command
snapshot for logging and initial execution, and its retained value for recovery.
Preserve tagged values; do not add server metadata or HTTP fields to the command.

Remove request context from the server's command-worker messages and remove the
request parameter from `runCommand`. The handler call becomes
`handler(dataspace, command, undefined, metaProxy)`: keep the fourth argument's
position for compatibility, leaving the former request slot empty. Dataset and
index access remain. Queries and HTTP admission/access checks can still use the
request; command execution cannot. Applications needing a value must supply it
as part of the complete command before acceptance/logging, not through a worker
request side channel. Never infer or silently inject omitted application inputs.

The default worker already omits request when calling `runCommand`; PL15 exposes
a configured-worker escape route, not a requirement to preserve that route.
The revised P8 test must prove that HTTP query/method/URL context is unavailable
even through a configured worker, and that command fields and dataset/index
access are equivalent during initial execution and authorized recovery. Keep the
original baseline as historical evidence; its proposed request-retention assertion
is superseded by this corrected input contract, not accepted as a product need.

Removing transport context does not sandbox arbitrary configured code. Required
timestamps, random choices, or external lookup results must also be command data
if they affect the intended repeatable transition; application validation and
tests establish that contract. The engine cannot detect every omitted semantic
input or certify arbitrary hooks. Historical request-dependent commands remain
defective and may be unrecoverable by rerun; this cycle will diagnose them, not
invent replacement inputs or rewrite their logs. Restoring verified data can still
avoid execution. A future rebuild-mode control is separate from business inputs.

## Ordering with existing records

**Command-log position is the sole authoritative command order**, as confirmed
by the maintainer in SRC-20260919-TTZ7C-18. Acceptance, live execution, committed
reconstruction, restart queues, and the administrative later-dataset predicate
must all follow that order. Status records describe outcomes and attempts; their
insertion order and client response timing cannot redefine the command sequence.

The acceptance FIFO includes duplicate-ID checking, command-log append,
accepted-status append, in-memory status, and queue insertion. Both appends and
their required directory entries must be durable before HTTP 202. The resulting
log order is also first-acceptance order and handler execution order for new work.
An in-memory ordinal can aid checks; no sequence number is stored. Response
delivery order across clients is not the order of accepted commands.

Retain existing status fields and values: `command`, `code`, `status`, and existing
attempt/message fields where applicable. Serialize all status appends, including
active and terminal outcomes. Reconstruct and queue by command-log position,
not incidental latest-status Map iteration. Failed/unsafe terminal
commands with no committed delta remain in that history without applying data.

For existing history, compare first-acceptance and active/done execution evidence
against the command log to detect violations, never to choose another authority.
Older records may disagree (PL16). Keep repeated status/attempt records for
inspection. Identical duplicate command-log entries reference one logical ID at
its first occurrence; conflicting values for one ID require diagnosis.

If only waiting-queue or acceptance-status order differs, the command order is
still known: use the complete log. That disagreement alone does not make the log
order ambiguous. Pending work still follows the administrator-assessment policy
below. If commands actually executed out of log order, their positional changesets
may encode an incompatible preceding state. Do not simply reorder those files
and claim a correct reconstruction. Diagnose the affected history, serve only a
verified unaffected prefix where appropriate, and use the guarded recovery or
backup path. Status evidence can reveal the defect; it cannot legitimize a
different command order. A missing/corrupt/incomplete command log is a separate
loss of authoritative evidence: other records cannot silently replace it.

The revised ordering test must compare actual handler starts, completed state,
and restarted pending execution with command-log order. Exercise an A append
whose asynchronous completion is delayed while B is submitted; B must not overtake
A. Include a sequential control and the waiting-at-crash case. PL16's historical
assertion requiring restart to preserve the old B/A queue is superseded: with an
A/B log, restarting A/B is correct and the live B/A queue is the defect. Retain
that observation as evidence; do not fix the test by making restart follow B/A.

Keep the existing client retry contract: an existing ID returns its known status
without another append or execution; fixing the concurrent duplicate race is in
scope. A new payload-conflict response policy is unnecessary for this cycle.
A log record without acceptance is an orphan; a status without its command is
inconsistent evidence. Neither may be silently executed, discarded, or reused.
Storage uncertainty halts admission even if acceptance might already be durable.

## Opening and initialization without a descriptor

Separate opening an existing store from explicit new-store initialization.
Opening requires the configured base, command log, and status log, plus the
manifest when integrity is configured as required. Missing files are errors,
never an invitation to create empty logs. Empty log/status pairs remain valid
for a fresh store when consistent with its other evidence; one empty log with
nonempty accepted history or unexplained changesets requires diagnosis.
Inventory configured artifact locations, including unexpected changesets.

Initialization/conversion targets new output, acquires ownership before writing,
and writes the base, empty logs/status, required indexes and any configured
integrity manifest in their current formats. Sync and validate all output before
releasing ownership or serving requests. Crash leftovers retain the ownership
lock and require offline inspection. Release never makes an incomplete output
ready merely because some files parse. A pre-existing base with absent logs needs
an explicit administrator assessment; normal open cannot prove it has no history.

For an existing validated store, establish file/directory barriers for the retained
base and required committed artifacts before admitting new writes, so subsequent
completion does not depend on old cached prerequisites. This syncs existing bytes;
it does not rewrite formats or prove no earlier data was lost. Custom required
artifacts must be covered. Startup cost is measurable work in P11.

There is no on-disk flag proving a store was written by the hardened implementation.
The guarantee is prospective for operations performed by that implementation,
from a validated starting state, under its documented filesystem/ownership
envelope. Keep the deployed binary/configuration as operational evidence. An old
binary can still read these formats, but it does not provide the new ordering,
sync, or recovery safety policy; downgrading does not preserve those guarantees.

Integrity must be explicitly configured if its continued presence is required;
the existing existence-based autodetection alone cannot detect a lost manifest.
Current digests detect covered byte mismatches, not loss of all history or a
coherent older snapshot. Without an independent retained witness, syntactically
valid truncation or replacement of a whole history may be undetectable. Neither
new software nor a static descriptor could reconstruct that missing information.

## Command execution and completion

1. Select the earliest eligible accepted command in established order. Append/sync
   active before invoking a worker. Eligibility on restart is conservative as
   specified below; absence of active is not retrospective proof of never started.
2. Execute command and current pre-serialization index mutations. Await required
   hooks, including returned promises, before final serialization; test ordering
   and rejection behavior rather than silently changing handler permissions.
3. Publish the complete changeset through the durable primitive. Preserve sparse
   OD-JSONTag numbering and zero-byte no-op changesets.
4. Await index finalization; publish required built-in sidecars durably. The
   current default loader can rebuild ID/offset indexes, as PL05 shows, but that
   is not a reason to leave promised output files half-written. Custom finalizers
   that promise required external files must use equivalent barriers; awaiting
   a hook alone cannot certify arbitrary external I/O.
5. If integrity is enabled, append/sync its changeset digest, including the
   manifest directory barrier. Validate manifest/base requirements at startup.
6. Append/sync done. Only then update live status, publish buffers to queries,
   and release the runner slot. A query-publication failure cannot undo done;
   stop/reload query service from committed state instead of appending failed.

Any required persistence failure enters a storage-failed state: close admission,
terminate active execution if necessary, stop queue advancement, and report an
uncertain outcome. Do not append a misleading failed record after a possibly
durable done. The error path must not try to keep operating through the same
failed status writer. Safe reads require separately established committed state;
the simplest first implementation may exit after surfacing the diagnostic.

Handler errors and timeouts remain distinct from storage faults. If terminal
failed/unsafe status can be durably recorded, no canonical transition is published
and normal subsequent work may continue under the existing timeout contract.
Such commands are never automatically rerun; existing uncommitted files and
external effects still require diagnosis before administrative action.

## Startup and implementation order

Parse and cross-check the input log, status transitions/order, required files,
framing, and configured integrity without changing command state or importing
mutation-capable modules. Reconstruct only established committed transitions.
Missing or inconsistent committed data fails before any recovery status append.
Active or artifact-bearing uncommitted commands are uncertain; no automatic
active-to-accepted rewrites, even below the former crash-attempt threshold.

Because old and new records are indistinguishable, this design also requires
administrator assessment for pending accepted-only commands found on restart.
They may have run under the old retry protocol or lost old unsynced evidence.
They cannot be labeled certainly never-started solely from their current status.
The administrative plan includes waiting work explicitly and enforces the same
later-dataset predicate. Fully terminal, consistent stores can restart normally;
freshly accepted work in a healthy uninterrupted process runs normally. Recovery
of a pending suffix blocks new mutations that would overtake it. Automatic restart
resumption with durable proof of the protocol is deferred, not smuggled into a
new checkpoint format. This conservative availability tradeoff needs tests and
operator documentation; it does not require data migration.

Implementation sequence when runtime work resumes: byte-complete publish/append
and directory barriers first (PL02/03/04/10 plus conversion/integrity), then parent
error handling/ownership, the acceptance FIFO and command-only worker boundary,
read-only startup validation, and administrative recovery under DES-20260919-TTZ7C-25.
The maintainer has now authorized that implementation sequence through evaluation.

New tests must cover initial creation versus open, unchanged stored schemas,
existing-store operation without conversion, short/zero writes, close/open error
masking, every barrier, optional integrity loss, concurrent acceptance/duplicates,
terminal-status persistence failures, query-update failure after done, locks,
ambiguous historical ordering, and conservative pending-command startup. PL15's
replacement must test removal of unlogged inputs, not their retention. The harness
must trace newly used filesystem APIs before claiming coverage. Measure write and
startup sync latency and run the disposable filesystem exercise. None of these
future passing results is claimed by the design.

## Reach within this cycle

| Acceptance rows | Design achievable with existing store formats | Boundary |
|---|---|---|
| P1-P3 | Complete writes, ordered durable acceptance/completion, explicit uncertain errors | Prospective protocol guarantee; hardware must honor the tested barriers |
| P4, P11 | Independent witness, fault matrix, named filesystem exercise, latency | Implementation and actual filesystem evidence still required |
| P5-P7, P10 | Read-only inspection, source-bound suffix recovery, preserved evidence and deliberate promotion | Unknown history/order blocks rerun; restart pending work requires administrator assessment |
| P8 | Commands are the complete invocation input; remove worker request context | Arbitrary code needs conformance testing; omitted historical inputs are not repairable by assumption |
| P9 | Offline consistent backup and restore using unchanged store files | Report backup coverage and any unknown/lost history; no guarantee of lossless repair |
| P12 | Retain separate rebuild/effect-suppression contract | Full rebuild tooling remains follow-up |

The P1-P12 goals need no new canonical data format on this design. Acceptance
remains contingent on implementation/evidence within these stated bounds. If a
required behavior cannot be achieved within them, record the gap and revisit the
cycle with the maintainer; do not quietly introduce a format extension/migration.
