# Design: Optional Durable File Integrity Manifest

## Role

Define the first narrow integrity-detection behavior for durable OD-JSONTag files.

## Why this exists

`DES-001` requires detectable corruption, and `EVD-20260819-09ZEF-6` shows that current OD-JSONTag framing validation does not detect a same-length payload alteration. The project needs a small integrity mechanism that improves developer-evaluable durability without silently changing the public API or forcing existing datasets through an implicit migration.

## Behavior / responsibilities

### I1 - integrity manifest is explicit and compatible

SimplyStore may be configured with an integrity manifest file. If an integrity manifest exists or integrity checking is explicitly enabled, startup verifies the base data file and every committed changeset against the manifest before parsing them as durable state.

Existing datasets without an integrity manifest remain loadable by default. This avoids silently converting the on-disk format contract for existing users.

### I2 - committed writes update integrity metadata

When integrity is enabled, creating a committed changeset also records that changeset file's digest before the command is marked `done`. This preserves the existing commit-before-query-visibility invariant: a `done` status should not be written until the durable data needed for restart, including integrity metadata, exists.

### I3 - altered committed bytes fail explicitly

If a manifest entry exists and the durable file's current bytes do not match the recorded digest, startup fails with an explicit recovery/integrity error rather than silently exposing altered state.

### I4 - missing manifest entries fail only when integrity is required

If integrity is explicitly enabled, missing digest entries for required durable files fail startup. If integrity is not enabled and no manifest exists, startup keeps legacy behavior.

## Boundaries

What belongs here:

- SHA-256 digest verification for base data and committed changeset files;
- a simple append-readable manifest file;
- tests for well-formed altered committed durable data;
- explicit startup failure when required integrity metadata is missing or mismatched.

What remains outside:

- automatic repair;
- Merkle trees or streaming root proofs;
- command log/status integrity;
- schema/index artifact integrity;
- a migration tool for existing datasets;
- changing REST or JavaScript query APIs;
- changing OD-JSONTag syntax validation beyond existing framing checks.

## Design choices

| Choice | Reason |
|---|---|
| Use SHA-256 from Node's built-in `crypto` module. | Avoids a dependency and is adequate for a first byte-integrity check. |
| Store integrity metadata in a sidecar file. | Keeps existing OD-JSONTag durable data files readable and makes the new format implication explicit. |
| Verify before parsing. | Prevents altered bytes from becoming normal recovered state. |
| Treat the manifest as append-readable latest-wins records. | Matches the existing simple log style and keeps the first version easy to inspect. |
| Write changeset integrity before `done`. | Preserves the existing committed-state recovery boundary. |

## Compatibility / migration position

This cycle does not require all existing datasets to have integrity metadata. The first supported path is opt-in integrity for new or explicitly configured stores. A later cycle may add a reset/clean/rebuild command or migration strategy if developer evaluation shows that is the right next step.

## Verification plan

1. Unit-test digest manifest read/write and mismatch behavior.
2. Startup-test an integrity-enabled store whose base data is altered after manifest creation.
3. Startup-test an integrity-enabled committed changeset altered after its manifest entry is recorded.
4. Preserve existing malformed-framing behavior and normal durability tests.

## Open questions / deferred decisions

- Whether integrity should become default for newly initialized stores.
- Whether command log/status files should receive the same digest treatment.
- Whether a future manifest should include file size, command ordering, previous digest links, or a root digest.
- Whether recovery tooling should be able to rebuild or deliberately accept a new manifest.
