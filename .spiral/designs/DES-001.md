# Design: Durability Invariants And Evidence Order

## Role

Define the durability invariants and implementation order that future SimplyStore durability work must be tested against.

## Why this exists

The current production-readiness priority is not to add broad database machinery. It is to make narrow durability claims explicit and falsifiable before hardening implementation.

## Cultural influence / constraints

No formal culture profile has been adopted yet. The design is shaped by explicit human constraints: preserve simplicity, add no machinery until an invariant or demonstrated use case requires it, and prefer evidence over feature count.

## Behavior / responsibilities

### D1 - committed-state recovery

After ungraceful process termination, restart must produce exactly the last valid committed state or an explicit detectable recovery/integrity failure. It must never silently expose an ambiguous partially committed state.

### D2 - no partial command visibility

A logical command may not become partially visible as a committed transition.

### D3 - command idempotency

A command ID represents one logical command. Retrying the same command, including after a lost response or crash, must not create the transition twice.

### D4 - deterministic reconstruction

Given an earlier complete dataset plus ordered committed partial datasets after it, SimplyStore can reconstruct the same later logical dataset without rerunning command handlers or other semantic behavior.

### D5 - laziness preservation

Recovery, indexing, replay, and later integrity checking must not materialize unrelated OD-JSONTag objects merely to establish durability.

### D6 - detectable corruption

Malformed, missing, truncated, or inconsistent durable artifacts must not silently become valid state. Refusing to start is acceptable when safe recovery cannot be established.

## Boundaries

What belongs here:

- durability invariants;
- crash/fault-injection harness before hashing;
- independent reconstruction oracle;
- adversarial storage cases;
- idempotency evidence;
- later after-change handler contracts;
- later integrity root as optional derived/finalizing capability;
- later property/randomized and destructive soak testing;
- minimal post-commit extension seam.

What must remain outside:

- Kafka, queue, webhook, topic, consumer-group, event-sourcing, database, or transaction-manager frameworks;
- automatic repair not justified by evidence;
- claims outside SimplyStore's intended operating envelope.

What change should this boundary protect us from:

Turning durability proof work into a broad platform rewrite.

## Supporting / intrinsic work

| Support | Why necessary |
|---|---|
| Baseline archaeology | The checked-out behavior is authoritative and may contradict the plan. |
| Fault-injection boundaries | Crash safety cannot be inferred from code inspection alone. |
| Independent reconstruction oracle | Restart success should not be proven only by the normal startup/query path. |
| Durable evidence documents | Claims should remain reviewable by future agents and humans. |

## Alternatives considered

| Alternative | Why not now | Evidence / trade-off |
|---|---|---|
| Start with integrity hashing. | Hashing before commit/replay semantics are clear can certify ambiguous behavior. | `SRC-001` explicitly says do not begin with hashing. |
| Build a general plugin/event framework. | The goal is optionality, not machinery or feature count. | Explicit non-goals in `SRC-001`. |
| Patch individual crash symptoms immediately. | Spiral asks us to fix the producing design/process when a test reveals an incorrect assumption. | `SRC-001`, `.spiral-core/AGENTS.md`. |

## Complexity / maintainability check

- Concepts introduced: durability invariants, fault boundaries, independent reconstruction, after-change phases, post-commit observer.
- Dependencies introduced: none at this design stage.
- Expected change radius: initially tests and test-only hooks; later command lifecycle and indexer/handler lifecycle.
- Replaceability considerations: integrity and derived-store capabilities should be replaceable handlers rather than core policy.
- What would make this harder for a future agent/human to change: hidden commit boundaries, implicit handler mutation permissions, unrecorded crash classifications, or premature framework abstractions.

## Verification plan

1. Record current lifecycle and write semantics as baseline evidence.
2. Add test-only fault points around actual durability boundaries.
3. For each boundary, execute command, kill process, restart, and classify state.
4. Build an independent reconstruction oracle from base dataset plus committed changesets.
5. Add adversarial storage tests for truncated, missing, duplicate, malformed, stale, and failed durable artifacts.
6. Add idempotency tests for lost response and crash/retry cases.
7. Add handler-contract failure tests before broadening extension behavior.
8. Add integrity-root tests only after replay/crash behavior is understood.

## Deferred decisions

- Exact fault-point names.
- Exact command outcome record format.
- Whether directory fsync or alternate append/replace primitives are needed.
- Exact after-change handler API names.
- Exact post-commit observer interface.
- Whether a future Merkle/tree structure is needed for integrity roots.
