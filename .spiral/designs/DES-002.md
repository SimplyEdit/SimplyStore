# Design: Minimal After-Change Handler Contract Direction

## Role

Define the smallest contract direction needed to make SimplyStore's current indexer lifecycle explicit and prepare for future derived stores and integrity finalizers without turning SimplyStore into a plugin framework.

## Why this exists

The current `index.update()` hook runs after command handlers mutate canonical OD-JSONTag state and before the command changeset is serialized, written, and marked `done`. Focused CYC-015 characterization shows that this hook is pre-commit, failure blocks canonical commit, it can mutate canonical state, and it can leave external derived files behind when it writes before throwing.

Integrity roots are supposed to become a finalizing capability later. That work needs explicit handler ordering and mutation permissions first.

## Current legacy lifecycle

Current command execution has this effective order:

1. Parse command.
2. Run command handler with mutable `dataspace`.
3. Collect current changed OD-JSONTag objects.
4. Run `index.update(dataspace, meta, changes)`.
5. Serialize changed canonical OD-JSONTag state.
6. Write per-command changeset.
7. Main thread marks command `done`.
8. Query workers receive the changeset.

The existing `index.update()` hook is therefore a legacy required pre-commit after-change hook with ambiguous permissions:

- it may mutate canonical state;
- it may write external derived files;
- its failure aborts the canonical command commit;
- external files it wrote before failure are not rolled back by SimplyStore.

## Desired minimal contract shape

Future handler APIs should make the current implicit phases explicit:

| Phase | Canonical mutation | External writes | Required for commit | Purpose |
|---|---|---|---|---|
| `mutate` | Allowed | Avoid by default | Yes | Normalize or enrich canonical OD-JSONTag state before it is frozen. |
| `derive` | Forbidden | Allowed | Configurable | Build external indexes or projections from frozen canonical state. |
| `finalize` | Forbidden | Metadata only by default | Configurable | Produce command outcome metadata such as future integrity roots. |

Once processing leaves `mutate`, canonical state is frozen for that command and later handlers must not alter it.

## Compatibility direction

Existing `index.update()` should not be silently reclassified as non-mutating. Until a new explicit handler API exists, treat it as a legacy pre-commit hook whose mutation permission is part of current behavior.

A future migration can adapt the built-in ID/offset indexers into explicit `derive` handlers only when SimplyStore can enforce non-mutation for that phase and document any compatibility impact.

## Failure semantics direction

- Required `mutate` failure: command is not committed.
- Required `derive` failure: command is not committed, but external partial writes may remain unless the handler uses atomic replace/cleanup conventions.
- Optional `derive` failure: candidate future behavior; do not add until a real use case requires it.
- Required `finalize` failure: command is not committed.
- Post-commit observer failure: out of scope for this design; later post-commit seams must not retroactively uncommit a command.

## Non-goals

- General plugin framework.
- Kafka, queues, topics, webhooks, consumer offsets, or event-sourcing machinery.
- Integrity hashing/root implementation.
- Automatic rollback of arbitrary external files written by handlers.
- Breaking the current indexer API in this cycle.

## Verification hooks

Near-term handler evidence should cover:

- legacy index failure blocks commit;
- legacy index mutation is currently committed;
- external derived files can remain after failed legacy index update;
- future `derive` handlers cannot mutate canonical state once that phase exists;
- required handler failures have explicit commit behavior.

## Deferred decisions

- Exact handler registration syntax.
- Whether legacy `index.update()` becomes an adapter around `mutate` or is kept as a compatibility-only hook.
- How required versus optional derived handlers are configured.
- Whether SimplyStore should provide helper utilities for atomic external derived file writes.
- How finalizer metadata is represented in command outcome records.
