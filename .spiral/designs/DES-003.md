# Design: Command And Load Worker Timeout Semantics

## Role

Define the timeout semantics needed to keep SimplyStore's command and load worker lifecycle from hanging indefinitely while preserving the project's simplicity and durable-state guarantees.

## Why this exists

`EVD-017` showed that query execution already has timeout guards, but command and load workers do not. A command handler can hang after the command has been durably accepted, and a restart can hang while replaying that active command before the server starts listening. A load worker can likewise hang during startup. These cases are not process crashes, so the crash/restart durability evidence does not fully cover them.

This design records the current effective justification for adding bounded worker behavior. It does not change the durable OD-JSONTag format, public endpoint names, or JavaScript query API.

## Confirmed semantics

### Command worker timeout

- Timeout is enforced by the parent thread at the worker boundary.
- Query-worker timeout behavior remains unchanged and VM2-specific.
- When a command worker exceeds the configured command timeout, the parent terminates that worker.
- The timed-out command receives a durable terminal `unsafe` command status.
- The timed-out command is not automatically replayed.
- Retrying the same command ID returns the terminal `unsafe` status and does not enqueue duplicate work.
- Any changeset written by a timed-out command before `done` remains uncommitted because only `done` command IDs are loaded as committed changes.
- The command queue may continue after the timed-out worker is terminated.

### Accepted command queue behavior

An accepted command should not be marked failed merely because another command worker is already running. Once a command is durably accepted, it should remain queued until the runner reaches it, unless it later receives its own terminal status.

This preserves the existing intended meaning of accepted commands and avoids turning normal concurrent submissions into false command failures.

### Load worker timeout

- Timeout is enforced by the parent thread at the worker boundary.
- When load exceeds the configured load timeout, the parent terminates the load worker.
- Startup fails explicitly instead of starting from ambiguous recovered state.
- No command status record is written for a load timeout because no command is being executed.

## Configuration direction

Command and load worker timeouts should be configurable independently from query timeout. A value of `0`, `false`, `null`, or `Infinity` disables the corresponding worker timeout for deployments that need explicit opt-out behavior.

Default timeouts should be conservative enough for developer evaluation while still proving that SimplyStore has bounded behavior when command or load workers hang.

## Non-goals

- General job queue, scheduler, cancellation framework, or worker orchestration machinery.
- Integrity roots or hashing.
- Automatic repair/reset tooling for dirty datasets.
- Automatic rollback of arbitrary external side effects performed by user command handlers.
- Changes to durable OD-JSONTag framing or command log/status record format beyond ordinary command status records.

## Verification plan

- A hanging command is accepted, then durably marked `unsafe` after the timeout.
- Retrying the same command ID returns `unsafe` and does not enqueue duplicate work.
- A later accepted command can complete after the timed-out command worker is terminated.
- Query state and independent reconstruction exclude timed-out command effects.
- A hanging load worker causes startup to fail explicitly before the server listens.
- Existing durability, ACID, and handler tests still pass.

## Deferred decisions

- Whether future reset/recovery tooling should remove uncommitted changeset files left by failed, unsafe, or interrupted commands.
- Whether default timeout values should become part of documented stable API after more production feedback.
- Whether command timeout status should later include structured diagnostic metadata beyond code, message, status, and attempt.
