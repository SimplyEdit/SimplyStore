# Design: Complete Lifecycle Contracts

Keep DES-20260919-TTZ7C-32 as the broader runtime architecture. This design adds
explicit contracts where its refactor lost ordering and completion semantics.

## Corrections

Close owns one completion promise. The first call synchronously stops admission
and starts resource closure; all subsequent calls await the same outcome,
including rejection. A separate closeResources() holds the existing ordered
acceptance/runner/pool/ownership cleanup. Preserve retention after storage
failure. Do not add another server-only shutdown guard: it would mask a broken
runtime contract for other callers. The server may safely await close from both
signal handlers.

After persisting acceptance and passing its existing fault point, check storage
health again before queue insertion and success return. A concurrent command's
failure may invalidate admission while an append is awaited. Retain any records
already written; never roll back evidence or automatically rerun. Reject later
admission through the existing failed state.

Command preparation parses and validates identity, then recognizes an existing
ID before validating a new command's name or serializing it. Move the existing
duplicate-result branch into that position rather than adding a second lookup
path or weakening validation of new commands.

## Readability

StoreInspector.inspect() coordinates path validation, inventory, command
history, integrity, reconstruction, artifact checks and stable-snapshot/report
creation. loadCommandHistory() groups reading log/status records, constructing
commands and validating committed order. Prefix validity is initialized where
reconstruction begins, after integrity/history diagnostics are available.

RecoveryApplication.runApprovedCommand() coordinates freshness, selection,
activation, execution, result assessment and commit. markCommandActive() owns
attempt numbering, audit-before-status ordering and status serialization. Keep
recordAttempt() as the existing audit operation. No new classes or generic
workflow engine; no changes to ordering, reports, locks or integrity checks.

## Verification and risk

Reproduce regression tests before changing product code. Use controlled promise
barriers for command execution and ownership release, test concurrent close
success/failure, and prove rejection of admission while closing. Inject failure
at the acceptance persistence boundaries and assert no enqueue or success,
retained records and ownership. Verify known ID-only retries before and after
execution while rejecting unknown incomplete commands.

Use a subprocess with a command blocked on an explicit release file to deliver
both shutdown signals before allowing completion. Observe signal handling, then
release the command, require done status and released locks, and restart/query
the committed state. Bound test waits and release barriers during cleanup.

All existing runtime, offset, startup, ACID, crash, handler, power-loss and
administrator/storage suites remain required. Read the final coordinator code
as well as running lint; method length alone is not proof of useful abstraction.

The observed failure is composition risk (adopted WPF-HUMAN-001-W4); verify the
server/runtime interaction, rather than treating isolated final-state tests as
sufficient evidence. The existing acceptance/integration clarification controls
authority drift locally; no process-core or culture changes are required.
