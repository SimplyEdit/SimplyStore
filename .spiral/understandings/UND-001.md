# Understanding: Durability First, Extensibility Second

## Current interpretation

SimplyStore should move from experimental toward production-ready by proving narrowly scoped durability claims first. The durability claim is not "database-grade ACID" in general; it is that SimplyStore can record sparse OD-JSONTag state transitions, survive injected process crashes inside its documented envelope, recover the last valid committed state, or explicitly refuse unsafe/corrupt state.

Extensibility is a secondary direction. The intended path is to expose enough lifecycle structure for larger systems and derived stores without adding Kafka, queues, message buses, event-sourcing frameworks, or database machinery to SimplyStore core.

## Sources considered

- `SRC-001`: human-provided durability and extensibility direction.
- Existing README and ROADMAP statements about command history, changesets, ACID stress testing, VM2 risk, and future larger-system automation.
- Baseline source inspection recorded in `EVD-001`.

## Current effective behavior / evidenced gap

Baseline archaeology found current behavior that does not yet establish the intended durability claim:

- existing automated tests do not currently exercise SimplyStore command durability;
- command-log and command-status appends were asynchronous calls that were not awaited at the call sites that accept and finish commands; `IMP-002` now awaits those calls in the command path, while deeper filesystem sync assumptions remain future work;
- startup reconstruction currently passes all status keys to the data loader, not only successfully committed commands;
- the loader silently skips missing per-command changeset files;
- accepted commands with existing changeset files appear able to be loaded and then re-queued for execution;
- malformed log/status lines throw during startup parsing rather than producing a documented recovery classification;
- index updates can write external files before the changeset is written and before command outcome is recorded.

## Provenance confidence

Evidenced.

## Remaining uncertainty

- Exact expected behavior for each crash boundary still needs to be turned into tests.
- Current downstream compatibility expectations for command log/status formats are unknown.
- The intended minimum post-commit extension interface is not yet designed against current code.

## Consequence

Begin with a baseline/evidence cycle and then plan the first implementation slice around a crash/fault-injection harness for the current command update lifecycle.
