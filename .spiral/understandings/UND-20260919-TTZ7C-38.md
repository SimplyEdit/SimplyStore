# Understanding: Reliable Runtime Contracts

The maintainer wants to retain the useful runtime/recovery boundaries, repair
the three reproduced compatibility/lifecycle regressions, and complete the
identified readability improvements. The preceding review established the
effective behavior and gaps; the instruction to start this cycle confirms them.

The shared cause is incomplete contracts at moved boundaries: awaiting close
must mean closure completed for every caller; acceptance must recheck storage
health after asynchronous persistence; duplicate lookup must precede validation
that applies only to new commands. Passing final-state tests did not establish
these ordering properties. Verify the interleavings and the process composition.

Keep inspection and approved-recovery coordinators at one abstraction level.
Use existing cohesive classes and a few meaningful supporting methods. Avoid
new frameworks, public APIs or broad renaming. Preserve disk records, replay
eligibility, audit evidence and lock-retention policies.

Assumptions: restoring ID-only duplicate lookup is compatibility, not permission
to execute incomplete new commands. Overlapping close calls must share failure
as well as success. Storage failure remains terminal and retains ownership.
Inspection/recovery cleanup must remain unchanged by readability-only changes.
