# Understanding: object history from committed file sources

## Current interpretation

The maintainer wants object-level audit history available inside the existing
JavaScript query environment. Starting from a current object or its current ID,
a query must be able to follow every persisted version of the underlying record.
Each history entry identifies the global dataset version and the successful
command that produced it, including the submitted author and message and the
modification time of that version's dataset file. A query must also be able to
inspect the other entity records written in the same version.

The first slice is an audit/history view, not whole-dataset time travel. A
historical object must represent its record at that version; its references
must not silently resolve against unrelated current record contents. The future
ability to run an entire query against a complete historical snapshot should be
possible without treating a changeset as that complete snapshot now.

## Clarifications / reframing

| Question / assumption | Alternative or clarification | Evidence / resolution |
|---|---|---|
| Which timestamp is exposed? | Use one dataset-file timestamp, not new accepted/started/committed timestamps. | Explicit maintainer choice; every loaded source already carries `identity.modified`. |
| Is author authenticated provenance? | No extra validation is required; expose the command's submitted author. | Explicit maintainer choice. |
| Is a version a complete snapshot? | A successful command is one global version and its `objects` are its ID-bearing changed records. Complete snapshot switching is later. | Explicit maintainer clarification and existing changeset storage model. |
| Does history need separate authorization? | No; historical views use the existing query access boundary. | Explicit maintainer choice. |
| How is object identity followed? | Follow the OD-JSONTag record number, not only the current string ID. | Existing record identity survives changesets and ID changes; current ID lookup selects the current record. |

## Current effective behavior / evidenced gap

SimplyStore already retains most required evidence:

- `StoreInspector` parses the exact command log, status history and changeset
  files, and produces an ordered list of successfully committed command IDs.
- `loadFileData` returns the base source followed by one source per successful
  command. Each source contains verified sparse record offsets and an immutable
  file identity whose `modified` value is its filesystem modification time.
- A changeset offset index identifies every record written by that command.
  Iterating those sparse offsets in source order is sufficient to derive a
  version chain for each record without a disk-format change.
- The active parser overlays record locations, so ordinary record lookup returns
  only the latest version. Earlier file locations remain in the source catalog
  but have no query-facing source/version address.
- `StoreRuntime.initializeLoadedState` keeps loaded sources and current indexes
  but discards the inspected command catalogue except for terminal statuses.
- The isolated query guest constructs `meta` with only `meta.index.id` and
  `meta.schema`; commands, versions and history are not available.
- Live query-worker updates append the new source and current ID index, but send
  no command/version metadata.

The intended behavior is therefore genuinely absent even though the durable
inputs needed to derive it already exist.

## Remaining uncertainty

The cheapest maintainable mechanism for resolving historical record references
must be established during implementation. Building and retaining a parser for
every version would be simple but may scale poorly; extending the host view with
version-aware record locations may be preferable. Evidence must cover history
length, lazy reads, file handles, memory and query limits before selecting a
permanent boundary.

The dataset-file modification time can change when a store is copied or restored.
It must be described as that file timestamp, not as independently immutable
proof of when the command committed.

## Commitment / disposition

Accepted as the basis for execution. The maintainer explicitly confirmed the
intent and design choices and instructed the project to start this cycle.

## Consequence

Define and implement a lazy, immutable query history surface over verified
committed sources, preserving current disk formats, grants and query limits.
