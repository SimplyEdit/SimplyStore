# Understanding: A Store Runtime Whose Code Reads As A Story

## Intended outcome

Refactor SimplyStore so its main execution paths express the domain story at a
consistent level of abstraction. Opening a store, accepting a command, executing
the ordered queue, publishing committed data and closing safely should be
readable without simultaneously reasoning about Express response objects,
worker events, JSONTag framing, filesystem handles or process termination.

Related long-lived state and behavior should form a cohesive runtime class used
throughout the server. Lower-level mechanisms remain behind explicit boundaries.
Pure data transformations may remain functions. Extraction is not a goal by
itself: a new function or method must hide detail or name a useful domain idea.
Numerous forwarding helpers would increase rather than reduce cognitive load.

Names should communicate intent. An unusually long name is a reason to inspect
whether the operation has too much responsibility, but shortening a precise name
is not an improvement when the result is harder to understand.

Dependency maintenance is part of the same correction. Installed packages should
match the mechanisms the code actually uses, and supported upgrades should retain
the same compatibility and verification standards as the refactor.

Evaluation exposed one behavior that should not be preserved. The query worker
reads `task.timeout`, but the old slow-query path either supplied the normal
timeout or placed the slow timeout in `task.slowTimeout`. Both GET and POST
requests to `/slowquery/` should instead pass the configured `slowTimeout` value
through `task.timeout`. Ordinary `/query/` requests should continue to pass the
configured `timeout` value through that same property.

## Current effective behavior

At baseline `e31e07c9bc8d4fc6458da1d213609dbf1aa4a7a2`, `src/server.mjs` is a
738-line module that creates one Express application at import time and retains
dataset buffers and metadata in module globals. Its `main()` function configures
routes, acquires store ownership, inspects and loads storage, constructs worker
pools, owns command state and queues, defines failure policy, installs process
signals and starts listening.

Nested command functions combine HTTP admission, JSONTag parsing, duplicate
checks, durable appends, status transitions, queue management, worker execution,
file synchronization, failure classification and query-pool updates. These rules
have strong process-level durability tests, but few can be tested directly
without starting a server and sending HTTP requests.

The default export is both an Express application and the object that supplies
`run(options)`. That public shape is documented and used by the example and test
fixtures. The command log and existing serialized acceptance queue establish one
authoritative live command order; the accepted durability behavior must remain
unchanged.

Worker lifecycle logic currently exists in `workerPool.mjs`, `execute-worker.mjs`
and an inline loader implementation. Administrative recovery also contains both
decision and filesystem work, but its size alone does not establish that it
belongs in this cycle's first refactor boundary.

Dependency inspection established that root runtime dependencies `codemirror`,
`write-file-atomic` and `process` are not imported by application code. The web UI
ships its own CodeMirror files, durable writes use `src/storage.mjs`, and process
imports use `node:process`. Root lint packages have supported major upgrades.
The example has outdated JSONTag, UUID and unused ESLint dependencies; its UUID
9 and the UUID 8 dependency declared by `@muze-nl/jsontag-types` produce the two
current moderate audit findings. The installed type package does not itself use
UUID, but package compatibility still requires verification rather than an
unexamined override.

## Evidenced gap

The current code makes independently changing concerns share state and control
flow. A reader cannot follow the command lifecycle without also interpreting HTTP,
filesystem, worker and process details. Tests protect the external result but do
not provide a small direct seam for the lifecycle decisions. Module singleton
state also makes construction, cleanup and isolated testing implicit.

This is a boundary and representation problem rather than a line-count problem.
Splitting large modules or extracting every block would preserve the coupling and
add vocabulary. The useful correction is a runtime that owns the store story,
with adapters for mechanisms that change for different reasons.

## Material assumptions and boundaries

- Preserve the documented Express application plus `run(options)` API.
- Preserve disk formats and REST, query, command and handler behavior except for
  the authorized slow-query timeout correction described above.
- Preserve command-log authority, serial execution and all accepted durability
  and administrative recovery guarantees.
- Prefer one cohesive runtime over numerous stateful helper functions or classes.
- Keep infrastructure adapters small and based on plain functions/objects; do not
  introduce a dependency-injection framework or interface hierarchy.
- Keep high-level methods at one abstraction level and reject extractions that do
  not reduce the reader's working set.
- Use JAQT when it makes selection/projection intent clearer, not as a blanket
  replacement for straightforward JavaScript.
- Treat VM2 replacement, full rebuild tooling and broad administrative-recovery
  restructuring as separate concerns unless implementation evidence makes a
  narrowly necessary change unavoidable.
- Verify dependency removals/upgrades through imports, package contents, tests,
  example build/start behavior and audit results.

## Plan continuity and commitment

This cycle deliberately deviates from the remaining randomized/soak and extension
slices in SRC-001, REQ-001 and DES-001. The accepted durability work exposed a
central coupling point whose correction lowers the cost and risk of those later
changes. It does not replace the remaining roadmap.

The maintainer confirmed the investigated checkpoint, added the function-scope
rule and explicitly started this refactor cycle. Execution can proceed through
evaluation. Evidence that the proposed runtime would merely relocate coupling or
require public/disk-format changes would reopen the design decision.
