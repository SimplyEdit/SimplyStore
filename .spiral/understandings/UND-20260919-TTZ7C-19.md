# Understanding: Durable Commits With Recoverable Failure

## My understanding

The durability objective includes both preventing acknowledged data loss under
the supported power-loss model and giving administrators a practical recovery
route when automatic reconstruction fails. Refusing startup remains appropriate
for ambiguous storage, but refusal alone no longer satisfies the outcome.

Reconstruction applies surviving committed changesets without executing command
code. Rerunning a command is different: its external effects may already have
happened. Missing data does not authorize automatic re-execution.

For ordinary recovery, a command may be rerun only with administrator approval
and only when no later accepted command has a dataset. The eligible trailing
commands are executed in their original order from the verified preceding
state. This predicate must consider all accepted commands, not just current
`done` statuses. Corrupted or ambiguous files are not silently treated as absent.

Logged commands must preserve all execution inputs required beyond the preceding
dataset. Any demonstrated omission is a defect, not an acceptable recovery
limitation. Missing inputs in historical records cannot be invented by tooling.

Full rebuild is a separate operation: execute selected history using selected
code against a starting dataset and write a new store. It may deliberately
produce different data and bypass ordinary recovery's later-dataset restriction.
Commands and hooks must receive a context instructing them to suppress external
side effects; canonical and derived output writes are still required. A flag
alone does not prevent arbitrary code from making external changes. The contract
is retained now; the full rebuild workflow follows this cycle.

## Material assumptions and boundaries

- First persistence envelope: a named Linux/local-filesystem configuration with
  storage honoring flush requests. Record actual filesystem/mount/virtual-disk
  settings in evidence; do not claim arbitrary hardware or remote filesystems.
- The intended ownership model is one writer. Verify it or enforce an appropriate
  exclusion mechanism; administrator recovery cannot race ordinary queue writes.
- Recovery works on a copy and preserves the original command log and artifacts.
  Revalidate a preview's inputs before applying it so a stale plan cannot bypass
  the ordering guard. Promotion is a separate explicit administrator decision.
- A consistent backup plus surviving committed data supplies a recovery route
  when rerunning is unsafe or disallowed. Report verified coverage, loss, and
  uncertainty; do not promise to reconstruct irretrievably missing information.
- A failed sync can leave commit status uncertain. Prevent false success and
  further mutations until recovery establishes a safe state; do not invent a
  definitive failed outcome merely because persisting `done` returned an error.
- Preserve disk/query/REST compatibility by default. Any required durable-format
  change must explicitly cover migration and legacy-store behavior.
