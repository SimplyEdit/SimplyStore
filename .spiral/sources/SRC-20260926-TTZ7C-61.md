# meta.schema fails in isolated queries

Retained source: maintainer conversation on 2026-09-26.

The maintainer reported that curriculum-store, which uses SimplyStore 0.11 with
isolated-vm queries, fails when a query asks for `meta.schema`, "even in the
slowquery (10s) it timesout". The maintainer's hypothesis: "meta.schema is a
full graph. It might be that the host boundary doesn't preserve object
identity, so the graph results in an infinite walk."

The assistant reproduced the failure and reported the schema as an acyclic
graph with shared objects rather than a cyclic one. The maintainer confirmed
the resulting understanding and the proposal to open a defect cycle, adding:

> I think each object should get a stable id, not just for a single query.
> That id shouldn't be exposed to the query side. If an object already has a
> stable id, we can reuse that, but I don't mind if we don't.

This settles the correction direction: identity for non-record query objects
is a stable identifier that outlives one query, and it stays private to the
host/guest bridge. Reusing an existing identifier is permitted, not required.
The maintainer also confirmed that the target is the pre-0.11 behavior:
JSONTag responses keep shared objects as links; JSON responses expand them.
