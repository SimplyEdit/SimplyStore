# meta.schema fails in isolated queries

Retained source: maintainer conversation on 2026-09-26.

The maintainer reported that curriculum-store, which uses SimplyStore 0.11 with
isolated-vm queries, fails when a query asks for `meta.schema`, "even in the
slowquery (10s) it timesout". The maintainer's hypothesis: "meta.schema is a
full graph. It might be that the host boundary doesn't preserve object
identity, so the graph results in an infinite walk."

The assistant reproduced the failure and reported the schema as an acyclic
graph with shared objects rather than a cyclic one. The maintainer confirmed
the resulting understanding and the proposal to open a defect cycle, adding:

> I think each object should get a stable id, not just for a single query.
> That id shouldn't be exposed to the query side. If an object already has a
> stable id, we can reuse that, but I don't mind if we don't.

This settles the correction direction: identity for non-record query objects
is a stable identifier that outlives one query, and it stays private to the
host/guest bridge. Reusing an existing identifier is permitted, not required.
The maintainer also confirmed that the target is the pre-0.11 behavior:
JSONTag responses keep shared objects as links; JSON responses expand them.

## Schema metadata decision

During the cycle the assistant reported that schema objects reach query workers
by structured clone, which keeps sharing but drops JSONTag metadata such as
`id`. Under VM2 JSONTag responses therefore used random UUID link ids from
Node's crypto, which the isolate does not provide. Offered either preserving
the schema's ids for query workers or matching 0.10's generated ids, the
maintainer chose "Preserve schema ids". Query responses should use the ids from
the schema file. Command workers are unchanged by this decision.

## Identity across all query data

After the schema correction the maintainer raised: "this fixes meta.schema.
But is the same problem not also in the normal data? That data should also
work with graphs, so object identity should be fixed across the whole system,
not just meta.schema".

The assistant probed stored data through the runtime. Records keep identity
across paths and cycles, because the record number is a stable identity. Three
gaps remained: JSONTag responses fail for shared objects without an `id`
(stored or query-built), because JSONTag writes a generated id onto the object
using `crypto`; shared arrays are stored inline by od-jsontag and return as
distinct arrays even on the host; tagged scalars are fresh copies on each read
in the isolate, while the host returns one object.

The maintainer decided: "I think using the record number is probably fine. And
yes, fix 1 and 3. We'll address 2 later, and jsontag also later." Output ids
for shared stored objects without an `id` derive from their record number.
Shared-array identity (an od-jsontag storage-format question) and the jsontag
`createId` fallback bug are deferred.
