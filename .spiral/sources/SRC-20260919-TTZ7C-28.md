## Origin and availability

Maintainer conversation on 2026-09-19. The operative human statements are
retained below. There is no external conversation locator. This source follows
the accepted power-loss recovery cycle and supplements the durability roadmap.

After accepting the preceding cycle, the maintainer requested:

> please check the package.json in simplystore and example, and update any dependencies that need updating

Inspection found current dependencies, unused packages and outdated development
and example dependencies. Before that work began, the maintainer expanded the

> No, this cycle needs a bit more, it will also be a refactor cycle. Please read the linked chapters folder in the workspace. It describes a software architecture philosophy. That and the muze engineering approach should inform you what the refactor should accomplish. But I might have some extra advice as well.

The linked source is the Programming for Wizards chapter set at commit

## Refactor direction

After investigation, the assistant proposed a behavior-preserving refactor that
makes the ordered command lifecycle explicit, moves HTTP concerns to an adapter,
places long-lived store state in a cohesive runtime, binds filesystem/worker/
process mechanisms at its boundary, retains the current Express application plus
`run()` public API, and removes or updates dependencies according to actual use.

The proposal preserves disk, REST, query, command and handler compatibility. It
does not include a VM2 replacement, full rebuild tooling, a dependency-injection
framework or arbitrary file splitting. Existing process, durability and recovery
tests remain the external behavioral evidence.

The maintainer responded:

> This is a good start. Where I would extend this is in a rule about function code scope. I like to be able to read code as almost a story, each line in it should be at about the same level of abstraction, low level code should be wrapped in functions or methods so the containing function reads clearly, without the reader having to think about low level details in higher level functions. But there is a limit, creating numerous extra function also increases the cognitive load by having the reader learn those new function or method names. So combining similar concerns in a single class that is used throughout the codebase is a better approach. Long names are a sign that the code is doing too much, but sometimes they are the correct name. Don't force short names if it makes the code less readable.

This makes abstraction-level consistency and cognitive load explicit acceptance
concerns. Extractions must earn their names by hiding detail or expressing a
domain concept. Related stateful operations should be cohesive instead of
scattered across numerous helpers. Name length is evidence to inspect, not a
mechanical limit.

## Cycle commitment

After the assistant restated that target and suggested a cohesive runtime with

This authorizes the refactor and dependency maintenance through evaluation.
Human acceptance of the completed cycle remains a separate decision.

## Slow-query correction during evaluation

Evaluation found that preserving the old query worker task shape would retain a
bug: slow GET requests received the normal timeout, while POST requests used a
`slowTimeout` property that the query worker does not read. After this was made
explicit, the maintainer instructed:

> Please fix the slowquery, you dont need to keep a bug

This authorizes a narrow semantic correction in the active cycle. Normal queries
must pass the configured normal timeout through the worker's `timeout` property;
slow-query endpoints must pass the configured slow timeout through that same
property. The endpoint shape and query language remain unchanged.

## Inspection and recovery scope refinement

During final review, the maintainer identified `inspectStore()` as another place
where low-level operations obscure the high-level story and requested analysis
before implementation. After reviewing a plan to express inspection as cohesive
phases on a module-local inspector, the maintainer responded:

> Agreed. And do a similar job on the admin-recovery, it has a few function with the same problem I think.

This expands the active refactor boundary to the store-inspection and
administrative-recovery workflows. The goal remains readability at a consistent
abstraction level, with related workflow state kept together instead of passed
through numerous free helper functions. Public functions, plain report shapes,
audit artifacts, lock retention, recovery eligibility, filesystem guarantees
and failure behavior must remain compatible.
