That and the muze engineering approach should inform you what the refactor should accomplish. But I might have some extra advice as well.

## Refactor direction

After investigation, the assistant proposed a behavior-preserving refactor that
makes the ordered command lifecycle explicit, moves HTTP concerns to an adapter,
places long-lived store state in a cohesive runtime, binds filesystem/worker/
process mechanisms at its boundary, retains the current Express application plus
`run()` public API, and removes or updates dependencies according to actual use.

The proposal preserves disk, REST, query, command and handler compatibility. It
does not include a VM2 replacement, full rebuild tooling, a dependency-injection
framework or arbitrary file splitting. Existing process, durability and recovery
tests remain the external behavioral evidence.

The maintainer responded:

> This is a good start. Where I would extend this is in a rule about function code scope. I like to be able to read code as almost a story, each line in it should be at about the same level of abstraction, low level code should be wrapped in functions or methods so the containing function reads clearly, without the reader having to think about low level details in higher level functions. But there is a limit, creating numerous extra function also increases the cognitive load by having the reader learn those new function or method names. So combining similar concerns in a single class that is used throughout the codebase is a better approach. Long names are a sign that the code is doing too much, but sometimes they are the correct name. Don't force short names if it makes the code less readable.

This makes abstraction-level consistency and cognitive load explicit acceptance
concerns. Extractions must earn their names by hiding detail or expressing a
domain concept. Related stateful operations should be cohesive instead of
scattered across numerous helpers. Name length is evidence to inspect, not a
mechanical limit.
