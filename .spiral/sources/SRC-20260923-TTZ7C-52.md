# Mandatory file integrity authorization

After accepting file-backed operation, the maintainer discovered that the
example had no manifest. The assistant explained the inherited optional
integrity setting, missing initialization for existing stores, and mandatory
creation/startup/publication rules. It explained that data bytes are already
hashed at startup, queries have no per-query hashing, and command overhead
includes durable manifest appends that can be batched and reuse known digests.

The maintainer said: “It would make the data much more reliable I think”.
The assistant proposed making integrity mandatory, with one-time initialization
for existing stores and measurement of added command latency. The maintainer
confirmed: “Lets do that”. This is the execution commitment after the concrete
intent/current-behavior/gap discussion; no repeat confirmation is needed.

Understanding: every normal store verifies persisted hashes, new stores and
commits always publish them, and existing stores have an explicit stopped-store
initialization path. Hashing detects changes after the baseline; it cannot prove
historical correctness or repair corruption. No merge or deployment is authorized.
