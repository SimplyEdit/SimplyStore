# Source: Roadmap Interview And Risk-Based Selection

## Origin and scope

Maintainer conversation on 2026-09-19, after acceptance of the runtime contract
corrections. The maintainer requested a keyword-by-keyword interview followed
by an updated SimplyStore roadmap. Relevant quotations are retained below;
the other statements summarize the clarified answers. No external conversation
locator is available. This authorizes a documentation update, not implementation
of the roadmap's features or selection of the next product cycle.

## Resilience

> rebuild from command history, then easier operations, using cli scripts, the other options are a long range option, not near term.

Rebuild the full history initially, into a separate dataset, retaining the
earlier changed-code and cooperative external-effect-suppression direction.
Selecting a history endpoint is not needed initially. CLI improvements should
make commands easy to find and run, with decent Unix-style help. Broader failure
testing and availability improvements remain long range.

## File-backed retrieval and compatibility

> Two things: larger datasets with reduced memory use, also easier switch to another javascript runtime, since we don't need to support shared memory if we use direct file access.

> the remote API is the important part, internal API can change where needed

The maintainer chose file-backed retrieval only, without retaining an in-memory
mode. They report having run performance tests with no noticeable slowdown.
No benchmark artifact or configuration was supplied in this interview; this is
a maintainer report, not a newly reproduced benchmark or a mandate to use mmap.

## Object history

> No, I want to be able to write a javascript query to show previous versions of a specific object. And then its previous version, recursively. The goal is to allow a UI to show an audit trail. The version information should give access to its command, author and message.

Deleted objects must remain findable. Restoration must preserve the deleted
version in the history. Explicit reuse of an ID identifies a new version of
the same object. This replaces the older roadmap's whole-dataset time-travel
proposal as the current requested versioning scope.

## Workspaces and the merge clarification

Temporary workspaces isolate changes from main, can be shared read-only or
read-write, and can be removed or merged. A merge is possible only if commands
can be replayed on current main. If conflicts exist, apply current main to the
workspace, resolve conflicts, then merge.

The conversation first considered validating replay and publishing its result
without executing commands on main. The maintainer then clarified:

> That answers your previous question. I agree, workspace commands should not allow external side effects. Then the merge can trigger those on merge.

After actual execution on main was suggested, the maintainer said:

> I think that might be the cleanest solution. My main goal is to keep SimplyStore simple. So when we get to this point we should investigate which solution carries the least added complexity, and the best option for future enhancements staying simple as well

Thus neither merge mechanism is settled. Preserve the no-workspace-effects
requirement and investigate how accepted merges perform effects. Approval is
optional per SimplyStore instance, with a list of accounts allowed to accept
merge requests. A different-person approval rule was not requested.

## Query sandbox

Replace VM2 with a system sufficiently fast and isolated to consider an
internet-facing JavaScript query interface. QuickJS and V8 isolates are
candidates, not selected solutions. Anonymous versus authenticated access is
configurable. The maintainer confirmed read-only queries, no filesystem/network
access except controlled dataset reading, and enforced execution-time, memory
and result-size limits. Internet suitability still requires evaluation.

## UI audiences, navigation and implementation

The current UI was a placeholder. Redesign it after carefully analyzing what
users need to do easily. Use Metro, SimplyFlow, Helene and other Muze libraries
where they make sense; their precise roles are not fixed.

Audience order: developers testing queries and exploring data; administrators
checking status and doing standard maintenance; developers/administrators
extending commands or schema, managing grants/accounts and inspecting history.
Systems extending SimplyStore must be able to extend or overhaul the UI simply.

The landing page introduces the system and dataset, and links to querying and
browsable exploration. Other features are available through a grants-based menu.
When reading is protected, an unauthenticated first request shows only login.
Exploration supports finding objects, inspecting properties, following links
and history without writing code. Defaults should be readable but may remain
technical, and downstream systems should be able to override them easily.

## Schema, command documentation and fixtures

Use curriculum-store's implementation as the schema basis. Investigate what
other users/datasets need before deciding extensions. Authorized users can
create/edit schema through the UI; externally authored schema files must also
be usable. Whether and how to generalize validation remains design work.

Initially document available commands and usage. A command creation/testing IDE
is a later exploration. Fixtures mean saved queries with selected output
visualizations, not regression-test inputs/expected outputs. Start with personal
fixtures; adding them to a workspace or main dataset is a later addition.

## AI and automation

Initially provide conversation in the UI for data exploration and answering
natural-language questions through the query interface. Users bring their own
AI. Provider/credential integration is not specified. Assistance with authoring
queries, visualizations, schema and commands comes later; investigate MCP later.
Keep scheduled commands and webhooks from the earlier roadmap as long-range work.

## Ordering and authorization

The assistant proposed this order, confirmed by the maintainer:

1. Full-history rebuild, then CLI usability.
2. File-backed retrieval and sandbox replacement.
3. Object history and audit trails.
4. UI redesign: landing page, queries, exploration and maintenance.
5. Schema editing, personal fixtures and conversational AI.
6. Workspaces and merge approval.

The maintainer's final instruction was:

> You can put them in that order in the roadmap. The spiral developer risk analysis should be in charge of actual next task selection.

The order is a presentation of direction, not a mandatory task queue. Preserve
the earlier durability invariants and recovery restrictions while revising
priorities. Early UI analysis was proposed as possible parallel discovery; no
implementation task or additional cycle was selected in this interview.
