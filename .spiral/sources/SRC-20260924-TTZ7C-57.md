# isolated-vm selection and authorization

Retained source: maintainer conversation on 2026-09-24.

The maintainer requires query JavaScript to have no Node filesystem, network,
or database access, and no imports. Supplied JavaScript libraries and the
permitted dataset view remain available. A failed or malicious query may be
terminated; preserving its computation is not an objective.

After comparing QuickJS and Secure Exec, the maintainer requested:
“Lets do a performance test against isolated-vm as well, if it is substantially
better, I will prefer that.” The assistant reported actual od-jsontag benchmark
results: approximately 4.8–5.0 times faster scans, 4.6–5.0 times faster result
serialization, and 25–27 times faster arithmetic. Static and dynamic imports
failed in the tested script embedding, and an infinite loop was stopped by its
timeout. The report distinguished these probes from production integration and
recommended proceeding without snapshots.

The maintainer then instructed: “Lets register this choice and continue with
isolated-vm.” This settles engine selection and authorizes the next integration
step after the concrete capability/performance discussion. No repeated engine
approval is required. Human evaluation and integration remain separate.

Current effective behavior is evidenced in src/query-worker-module.mjs: VM2
executes queries using a host-owned FileDataset, JSONTag and JAQT helpers. The
worker pool sequences committed file-source updates with queries. The requested
isolated-vm boundary is not implemented. Existing access modules run in Node;
preserving their authority is an integration requirement, not something proved
by the raw-byte benchmark. Timeouts currently cover VM2 evaluation, while
serialization and outer worker termination need explicit coverage in the new
boundary.

Understanding: continue ROADMAP section 2, replacing VM2 for query execution
with isolated-vm while preserving file-backed data, grants, query helpers,
response formats, committed update ordering and storage-failure handling.
Add bounded execution, memory and result handling at this boundary. Queryable
object history/audit metadata follows; its user interface can come later.
Commands and persistence remain trusted Node operations. No new disk format,
deployment, package release, merge, or public-access safety certification is
implied.

The benchmark report, source and raw results are retained in
benchmark/query-engines/. Those measurements motivate selection; integration
must be tested independently, especially when adapting the data/grant bridge.
