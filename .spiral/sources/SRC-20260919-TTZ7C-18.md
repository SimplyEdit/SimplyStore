# Source: Power-Loss Recovery And Administrative Replay

## Origin and availability

Maintainer conversation on 2026-09-19. The operative human statements below
are retained verbatim; the proposed cycle boundary is summarized separately.
There is no external conversation locator. This source supplements SRC-001.

## Retained human direction

> If we fail to recover the committed state, we need to have a plausible way for an administrator to recover.

> We have a command log, if that is complete, shows an accepted command, but its data files are missing.... we can't just assume we can run the command again, it might have secondary effects. But an administrator should be able to judge whether it can be rerun.

> The commands stored in the log should have all required information. If that is not so, that is a bug. Another thing, I don't think we should allow a command to be rerun, unless there are no accepted commands with their datasets after it. If all commands after it are either waiting or also miss their datasets, then the administrator can run them again.

> There is one exception. I designed the system to theoretically be able to rerun all commands, useful if you alter the code the command executes and want to create a new dataset consistent with that new code. So I think we should have an option the adminstrator could set to signal to the commands not to trigger side effects, only update the data.

After a proposed next-cycle plan, the maintainer committed:

> Lets make a cycle to do all this work.

## Proposal to which the commitment responded

The assistant proposed one cycle for durable commits and an administrative
recovery path, explicitly revising the immediate roadmap order:

- failure matrix and baseline tests before runtime hardening;
- durable acceptance and completion, including file/directory sync ordering;
- simulated lost/reordered/partial writes and sync failures, with acknowledgment
  evidence outside the damaged store;
- inspection and administrator-authorized ordered recovery on a copy, preserving
  the original store and preventing automatic replay from bypassing the rules;
- command-log input completeness and fixes for demonstrated omissions;
- a tested consistent backup/restore procedure;
- a specified Linux/local-filesystem envelope, latency measurements, and a
  disposable block-level power-loss exercise before claiming that envelope;
- recording the rebuild-mode contract now, with the full rebuild workflow in
  a following cycle. That mode produces a new store using selected code and
  communicates that external side effects must be suppressed.

This boundary is the assistant's proposal confirmed by the final human message;
it is not a quotation authored by the maintainer. The side-effect flag is a
cooperative command/hook contract, not proof that arbitrary code is sandboxed.

## Subsequent design correction — 2026-09-19

After the first design proposed a versioned log envelope and migration, the
maintainer clarified the intended input boundary:

> The original design goal was that commands would be the complete set of information. I think we might fix the issue by removing extra information in the command worker, instead of adding it to the log.

The maintainer then authorized a design revision:

> Lets see how far we can get in this cycle without a new dataformat and migration. Design only.

This authorizes revising the cycle design, not runtime implementation in this
step. The interpretation to explore is complete command values as the execution
inputs beyond the existing dataset, removal of transport request context from
command execution, and retention of the current store file/record formats.
The assistant's earlier envelope, sequence fields, and mandatory v2 activation
were design choices, not explicit maintainer requirements. New recovery-tool
plans/reports are administrative output; they must not become a disguised
required store format or migration. Remaining limits must be stated explicitly.

## Command-log authority clarification — 2026-09-19

The maintainer requested verification of the intended ordering rule:

> The current system should have a single sequence of commands being processed according to the order in the command log. You should be able to rely on that order. Unless I have missed something. Please verify.

After verification exposed a concurrency gap between append and queue insertion,
the maintainer confirmed:

> That is a problem, the command log should be authoritive

The command log defines the order. Status records, client responses, and queue
timing are not alternative authorities. Their disagreement is evidence of a bug
or damaged history. The previous design-only and no-migration boundary remains;
the immediate work is to correct the designs and future verification expectations.

## Authorization to complete implementation — 2026-09-19

Following explanation of serialized acceptance through queue insertion, the
maintainer authorized continuing the entire cycle:

> Ok, that sounds like a good fix, I'll let you continue the whole cycle with this design. Only stop when I need to accept the cycle, or you cannot resolve a question in a sensible direction yourself.

This supersedes the earlier design-only execution limit. Continue implementation,
tests, recovery tooling, documentation and evaluation under the current designs,
with unchanged store formats and command-log authority. Cycle acceptance remains
the maintainer's decision. Routine implementation choices require no new approval.

## Remaining acceptance evidence

Exact recovery CLI syntax, durable command ordering, log-format implications,
filesystem test configuration, and handling of ambiguous/corrupt evidence need
design and executable evidence. No runtime outcome or cycle acceptance is
claimed by this source. Creating the cycle is distinct from completing it.
