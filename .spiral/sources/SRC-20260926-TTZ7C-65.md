# Store lock left after Docker shutdown; self-healing request

Retained source: maintainer conversation on 2026-09-26.

Testing SimplyStore 0.11.1 in curriculum-restapi-dev's curriculum-store, the
store lock remained after shutdown. The maintainer: "What I'd like is for
shutting down docker compose to clear the lock. Currently that appears not to
happen."

Investigation on a disposable copy found two SimplyStore gaps: a stop during
startup always leaves the lock, because `run()` installs its SIGTERM/SIGINT
handlers only after `StoreRuntime.open` has taken ownership; and a running slow
query delays close to about 10 s, Docker's default grace period. After startup,
SimplyStore released the lock within about 1 s.

The maintainer then asked: "What I'd like is for the system to self-heal. So if
the it crashed, it should restart automatically and check if the lock can be
safely released." The assistant reported that DES-20260919-TTZ7C-24 forbids
automatic stealing on PID age, timeouts or signal probes, and that it names
kernel-backed exclusion as the alternative. A cross-container probe showed a
Unix socket in a bind-mounted directory accepts connections while its owner
runs and refuses them (ECONNREFUSED) after the owner is killed with SIGKILL.
The assistant proposed a liveness socket in each lock, automatic takeover only
when the socket refuses, fallback to administrator release otherwise, and
retained administrator assessment for unfinished commands; with the stated
assumption that one machine uses a store directory. Asked "How much complexity
does this add?", the assistant estimated about 150 lines of code and 250 of
tests, and named takeover races, recovery locks, unsupported filesystems and
the single-machine rule as the conceptual cost.

The maintainer asked to investigate the actual incident first ("I pressed
ctrl-c once in the docker compose process, which should have started normal
shutdown"). Docker's event log showed every service was killed after 10 s
because `sh` stayed PID 1; that was corrected in curriculum-restapi-dev
(CYC-20260926-1ZG1H-6). The maintainer then kept that cycle open: "I think the
self healing part should be included in it", chose a chain of cycles with the
mechanism in SimplyStore, and declined a restart policy because the Docker
environment is only for development.

This settles the commitment: SimplyStore proves a crashed owner is gone and
takes over its lock on the next start; otherwise it refuses as before. Starting
again remains the operator's action.
