# File-backed migration authorization

The maintainer first requested file-backed data before client-visible version
metadata and audit trails, and agreed to harden od-jsontag first. After reviewing
the dependency changes and the explanation of required SimplyStore integration,
the maintainer stated on 2026-09-23:

> Read through it, and the code is readable and well supported by tests. Lets continue with simplystore and switch to filebased data instead of shared memory.

The preceding explanation covered file sources and offset indexes, descriptor
lifetime, ID lookup independent of the proxy cache, index loaders, integrity,
command isolation, and streamed large output. This is explicit authorization to
implement that integration. It continues the roadmap file-only direction, with
priority ahead of rebuild as previously requested. It does not authorize a merge,
release, production-data mutation, new sandbox, or audit feature.

Reviewed dependency: od-jsontag commit
24f47eb616c3a24391487197496804ed1c56837b, available on its upstream indexedParsing
branch. The library keeps format/API compatibility and has bounded clean-record
caching; indexes and mutable sessions still grow with their contents.

## Persisted-index completion, 2026-09-23

After the assistant explained that startup still scanned canonical files and
rebuilt IDs, and that persisted index loading with validation/fallback remained
unimplemented, the maintainer replied:

> I think that needs to be in this version. I verified that SimplyStore still works with the example folder.

This authorizes finishing persisted offset/ID loading in the active file-backed
cycle. The example check is maintainer-reported evidence, not acceptance of the
still-incomplete cycle or an independently reproduced agent test.

## Trust committed indexes, 2026-09-23

The maintainer challenged reconstructing IDs on every startup: “If we do that,
we don't need the index.id.json, right?” and “Why would we not trust
index.id.json?” The assistant acknowledged redundant validation and identified
two actual consistency gaps: ID publication before final hook mutations and
stale mappings after ID removal/rename. The assistant proposed making committed
indexes reliable, loading them directly, and reserving reconstruction for
missing indexes or explicit validation/recovery. The maintainer confirmed:

> Agreed, lets do that

This revises the earlier same-cycle scan-and-compare design. It does not accept
the cycle or authorize integration.

The maintainer further clarified:

> There is no legacy index compatibility to worry about, this is not yet used.

> Duplicate ID's are an error

These explicit corrections remove legacy index support and duplicate-ID winner
selection from the intended contract. Replacing the same record may retain its
ID; two distinct current records may not share an ID.
