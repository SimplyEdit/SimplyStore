# Request: Explicit And Readable Store Runtime

## Operationalized intent

Refactor SimplyStore around a cohesive runtime whose methods express the store
lifecycle at a consistent level of abstraction. Keep HTTP, worker, filesystem and
process mechanics behind clear boundaries, while preserving all public and
durable behavior. Update package dependencies so the manifests describe the
implementation and supported tooling that remain after the refactor.

## Acceptance requirements

### R1 — public compatibility

The package default export remains an Express application with `run(options)`.
The documented query and command endpoints, response/status behavior, options,
custom command/index modules and example startup continue to work. No disk format
or migration is introduced.

### R2 — cohesive runtime ownership

One runtime instance owns the mutable state of an opened store, including loaded
data and metadata, command status and queue state, query workers, ownership and
closing/failure state. The module-level Express compatibility export does not
make this store state global.

### R3 — story-level lifecycle code

The main paths for opening, accepting commands, executing the queue, publishing
committed results and closing can be read without following HTTP response details,
worker event wiring or low-level filesystem operations. Statements within each
method operate at approximately the same abstraction level.

Helper extraction must reduce cognitive load by hiding detail or naming a stable
domain operation. Related stateful behavior belongs in the runtime or an existing
cohesive mechanism rather than a proliferation of one-use forwarding functions.
Names optimize clarity rather than length.

### R4 — explicit adapters and plain boundaries

Express handlers translate between transport values and plain runtime inputs and
outputs. Worker, storage, logging, fault and process policy are selected at a
small composition boundary. No dependency-injection framework or generic service
container is introduced.

### R5 — preserved command and durability semantics

Command-log order remains authoritative. Acceptance through queue insertion and
execution remain serialized, file barriers still precede completion, storage
uncertainty still stops mutation, and query workers see data only after durable
completion. Startup inspection and administrative recovery behavior are unchanged.

### R6 — direct evidence for the runtime seam

Focused tests exercise the runtime's lifecycle decisions without requiring HTTP
or a child server for every case. Existing end-to-end command, crash, power-loss,
handler, recovery, conversion, storage and startup tests remain the compatibility
and durability evidence.

### R7 — accurate and supported dependencies

Remove root packages no longer used by shipped code. Upgrade supported root
tooling and example dependencies, keep lock data consistent, and remove example
tooling that the example does not use. Resolve known package-audit findings when
the resolution is compatible and supported by build/start tests; document any
finding that cannot responsibly be resolved in this cycle.

### R8 — maintained readability conventions

Changed JavaScript follows the repository's brace layout, restrained ternary use,
named intermediate values and approximately 80-column lines. JAQT is used where
selection/projection reads more clearly and avoided where ordinary JavaScript is
simpler.

## Evaluation evidence

Acceptance requires:

- a structural review mapping high-level runtime methods to their lower-level
  adapters and showing the remaining public compatibility shell;
- focused tests for runtime state and command ordering/failure behavior;
- all relevant existing test scripts passing;
- lint results with pre-existing unrelated findings distinguished from changes;
- example install/build/start/query/command verification;
- root and example package audit results and an import/use inventory for removed
  dependencies;
- a net complexity review covering concepts, files, functions/methods and code
  movement rather than relying on line count alone.

## Non-goals

VM2 replacement, full rebuild tooling, new storage formats, REST/query/command API
redesign, generic event or dependency frameworks, arbitrary splitting of large
modules, and broad recovery-tool restructuring. Publishing, deployment and remote
integration are outside this cycle.
