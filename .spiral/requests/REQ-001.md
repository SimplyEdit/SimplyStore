# Request: Durability Evidence

## Operationalized intent

Make SimplyStore's durability guarantees explicit, mechanically testable, and credible to a skeptical senior developer while preserving the project's deliberately small architecture.

The first useful outcome is evidence for crash behavior across the current command update lifecycle. Later slices may harden retry/idempotency, after-change handlers, integrity roots, property testing, soak testing, and post-commit extension seams.

## Upstream understanding

This request follows `UND-001`: durability proof is the first production-readiness priority; extensibility for larger systems follows only through minimal lifecycle seams justified by evidence.

Prospective provenance repair: this version records the current effective request as derived from the current `UND-001` interpretation. It does not claim that the first `REQ-001` version historically contained a machine-readable `sd:derivedFrom` link.

## Intended audience

- SimplyStore maintainer.
- Future SimplyStore contributors.
- Skeptical technical reviewers evaluating whether SimplyStore's limited durability claims are supported by executable evidence.

## Observable desired outcomes

### durability-claims-explicit

SimplyStore has explicit durability invariants that distinguish committed state, uncommitted/interrupted commands, idempotent retries, deterministic reconstruction, laziness preservation, and detectable corruption.

### crash-boundaries-testable

The current update cycle has fault-injection boundaries that can kill the process and classify restart behavior as not committed, fully committed, or unsafe/inconsistent.

### independent-reconstruction

Tests can compare restarted SimplyStore state against a simple reconstruction from base dataset plus ordered committed changesets, without rerunning command handlers.

### evidence-first-hardening

When current behavior fails an invariant, the failure is preserved as evidence before implementation changes try to fix it.

### minimal-extensibility-path

After durability is better understood, SimplyStore can expose enough lifecycle structure for derived stores and post-commit observers without adopting a broad plugin/event framework.

## Non-goals

- Kafka.
- Event-sourcing framework.
- Semantic event taxonomy.
- General message bus.
- Topics or consumer groups.
- Distributed transactions.
- Global schema registry.
- Merkle tree unless streaming root computation is measured as insufficient.
- Multiple read databases.
- Aggregate, saga, or arbitrary transaction frameworks.
- Claims outside SimplyStore's intended operating envelope.

## Nearest important uncertainty

What does the checked-out command update lifecycle actually do at each durability boundary, and which observed behaviors already contradict the intended durability invariants?

## Risks

| Risk | Horizon | Why it matters | Evidence/action |
|---|---|---|---|
| Startup may silently expose state inconsistent with command status. | blocker | This would directly violate committed-state recovery and detectable-corruption goals. | Baseline evidence in `EVD-001`; needs executable regression tests. |
| Accepted commands may be partially applied or re-applied after crash. | blocker | This threatens no-partial-visibility and command idempotency. | Baseline evidence in `EVD-001`; needs fault harness. |
| Index/external file writes may define accidental commit boundaries. | near-term | External indexes currently write before command outcome and without explicit contract. | Baseline evidence in `EVD-001`; handler contract later. |
| Integrity hashing could hide lifecycle ambiguity if implemented too early. | deferred | Hashes over ambiguous commit semantics produce confidence theater. | Defer until crash/replay tests exist. |

## Acceptance shape

This request is satisfied when a developer can run a focused durability test command and see evidence for the documented invariants, including known gaps. The first acceptance slice is not a production-safety claim; it is a baseline plus crash/fault-injection harness that can reveal true commit-boundary behavior.

For the current developer-evaluation audience, the evidence should make clear:

- which durability invariants are claimed;
- which durable artifacts and crash boundaries are covered by executable tests;
- which corrupt or inconsistent artifacts cause explicit recovery failure;
- which risks remain unresolved and should not be hidden behind production-ready language.
