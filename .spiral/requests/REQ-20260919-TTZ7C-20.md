# Request: Power-Loss Durability And Administrative Recovery

## Outcome and audience

Developers and administrators need a bounded, executable power-loss durability
claim and a practical recovery route when committed storage cannot be loaded.
Complete this as one cycle, from fault evidence through sync hardening,
administrative recovery, and a verified backup/restore exercise.

This supplements REQ-001 and refines its failure-only allowance: refusing unsafe
startup remains necessary, but a tested administrative route is also required.
It does not retrospectively invalidate the earlier bounded test results.

## Required behavior and acceptance evidence

| ID | Requirement | Discriminating evidence |
|---|---|---|
| P1 | Durable command acceptance | The complete execution record and acceptance survive supported power-loss cuts after `202`; a retained command is not mistaken for proof of safe re-execution |
| P2 | Durable completion | Before `done` is observable, the changeset and every required recovery artifact, including new/replaced directory entries, are durable; acknowledged completed state survives modeled cache loss |
| P3 | Explicit I/O uncertainty | Write, short-write, sync, rename, and close failures never report false acceptance/completion; uncertain commit failures halt further mutation pending recovery |
| P4 | Independent crash oracle | Keep issued-command order and observed acknowledgments outside the damaged store; independently reconstruct surviving committed data and detect silent rollback, duplication, and partial state |
| P5 | Read-only recovery inspection | Identify relevant command order/status/attempts, missing/corrupt/ambiguous artifacts, verified preceding state, and known/unknown external effects; produce a preview without changing original evidence |
| P6 | Administrator-authorized ordered recovery | Rerun only when explicitly authorized and no later accepted command has a dataset; execute eligible trailing missing/waiting commands in original order from verified preceding state; do not infer the rule from `done` alone |
| P7 | Recovery cannot be bypassed | Automatic retry and normal queue processing cannot bypass P6 or overtake recovery; revalidate evidence before applying a plan; corrupt/unknown files are not treated as absent |
| P8 | Complete execution inputs | Verify original and recovered invocations have all required logged inputs beyond the preceding dataset, including relevant configured-worker behavior; fix actual omissions, and diagnose incomplete legacy records rather than inventing values |
| P9 | Consistent backup and restore | Provide and test a usable consistent backup procedure and restoration into a separate store; show recovered command coverage, known loss, and uncertainty when reruns are prohibited or unsafe |
| P10 | Preserved evidence and deliberate promotion | Recovery preserves the original store/log and records administrator decisions and execution outcomes; validation precedes explicit promotion; recovery interruption itself must leave an inspectable safe state |
| P11 | Bounded filesystem claim | Name the tested Linux filesystem, mount options, storage/cache assumptions, and writer ownership; validate with a disposable block-level power-loss exercise, distinguish simulation from physical hardware evidence, and measure commit latency |
| P12 | Rebuild exception retained | Document separate new-store rebuild using selected code/history and context instructing commands/hooks to suppress external effects; this cannot become an ordinary recovery override |

## Mandatory recovery examples

In established command order, `A:dataset, B:missing, C:dataset` blocks rerunning
B, including when C is accepted but not currently marked done.

`A:dataset, B:missing, C:waiting, D:missing` permits an administrator-authorized
ordered recovery of B/C/D after checking secondary effects. It is permission
eligibility, not a claim that replay is safe or automatically approved.

A file that exists but is corrupt requires diagnosis. A later dataset appearing
after preview invalidates that plan. Missing command-log evidence also prevents
asserting eligibility from filenames alone. Failed/unsafe/duplicate records and
concurrent acceptance must receive explicit design/test dispositions, not a
silent choice of a convenient map iteration order.

## Implementation direction and compatibility

Start with a failure matrix and baseline tests. Reuse the current file-based
architecture and reconstruction oracle; choose small durable-write primitives
and explicit sequencing over a new storage framework. Determine which indexes
must persist before commit and which can be rebuilt safely from canonical data.
Include initial base/log creation and recovery writes in the persistence audit.

The supported first envelope assumes a single writer and storage that honors
flushes on a named Linux/local-filesystem configuration. If that envelope cannot
be established in the test environment, report the missing evidence and keep
the power-loss claim outstanding. Do not relabel process-kill tests as proof.

Preserve public REST/query APIs and disk formats by default. Any necessary log
or recovery format extension must explicitly address old stores, migration,
failure behavior, and downstream compatibility before implementation.

Full rebuild tooling is follow-up work under P12's retained contract. Side-effect
suppression is cooperative unless separately enforced; actual command and hook
implementations need verification before being called rebuild-safe. Changes to
command code are explicit rebuild inputs, not ordinary recovery assumptions.

## Scope exclusions

- General randomized/destructive soak campaigns beyond the focused fault matrix
  and disposable filesystem acceptance exercise.
- Full rebuild CLI/workflow implementation in this cycle.
- Automatic rollback or exactly-once guarantees for arbitrary external effects.
- General message buses, transaction frameworks, remote-filesystem guarantees,
  sandbox replacement, package publishing, or production data recovery/deployment.

## Evaluation

Each P1-P12 row needs traceable implementation/documentation and verification
evidence appropriate to its claim. P12 is a recorded contract, not a tested
rebuild feature. Run relevant existing startup/offset, handler, ACID, and crash
suites as regression checks. A failed or unavailable required exercise remains
an open acceptance item; creation of the cycle is not acceptance of its outcome.
