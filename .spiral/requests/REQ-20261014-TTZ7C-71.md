# Request: queryable object and command history

## Operationalized intent

Developers querying SimplyStore need an inspectable audit trail built from the
store's successfully committed history. From a current object or its current ID,
they must be able to inspect every persisted version of its record, understand
which command caused each version, and inspect the other entity objects changed
by that same command/version.

This first slice makes the existing durable history useful through the query
worker. It must not invent a second history store or imply that a command
changeset is a complete historical snapshot.

## Upstream understanding

UND-20261014-TTZ7C-70 establishes that the verified ordered source catalogue,
command inspection and sparse offsets already contain the necessary evidence.
The missing behavior is a query-facing, version-aware view and live publication
of command/version metadata.

## Intended audience

Developers writing SimplyStore JavaScript queries and downstream developers who
will later present object history in their own interfaces.

## Observable desired outcomes

### object-history

Given a current stored object, or a string ID that currently resolves to one, a
query can obtain its history in ascending global version order. Each entry gives
the version number, dataset-file timestamp, successful command metadata, and an
immutable view of that record as it existed in that version.

The base source is version zero with no command. Each successfully committed
command is the next global version. The current version is the final history
entry and the previous version is the entry before it.

### command-history

A query can enumerate all successfully committed commands in durable order and
look one up by command ID. Command metadata includes ID, name, author, message,
dataset-file timestamp and version. The author and message are exposed as
submitted; SimplyStore does not authenticate or reinterpret them. Original
command input stays in the authoritative command log for separate tooling and
is not part of the query-worker interface.

Accepted, active, failed and unsafe commands are absent from queryable history.

### version-peers

Given a version number, a query can inspect the ID-bearing object records written
by that version. Those objects are historical views at that version, including
deleted records. Internal/root records without IDs do not appear as peers.

### stable-live-view

History reconstructed after restart and history published after a new successful
command have the same ordering and semantics. Query workers never expose a
command/version before its done status and changeset are durable.

### query-boundary-preservation

Historical objects are read-only and subject to the existing host access grants,
execution deadline, isolate memory limit and result-size limit. No file paths,
file handles, parser state or private record/source identifiers become visible.

## Assumptions / ambiguity

| Claim | Provenance | Evidence / question |
|---|---|---|
| Global version is the committed source position. | explicit/evidenced | Chosen during discourse and matches base-plus-ordered-changeset loading. |
| Dataset timestamp is filesystem modification time. | explicit/evidenced | Maintainer choice; already captured in each source identity. |
| Record number is object lineage identity. | evidenced | Changesets replace the same numbered record; sparse offsets retain every replacement. |
| A historical record's links should resolve at its version. | inferred | Required to avoid presenting a mixed historical/current object; verify against actual parser behavior. |
| A string ID identifies the record currently owning that ID. | explicit | Avoids ambiguous reuse semantics; callers can retain an object/history entry to follow older IDs. |

## Non-goals

- Switching an entire query or `data` root to a complete historical snapshot.
- A history or audit user interface.
- New authentication or authorization for history.
- Validation or replacement of a submitted author.
- New server-generated command timestamps.
- Treating file modification time as immutable commit proof.
- Disk-format changes, history duplication, migrations or command replay.
- REST API changes, curriculum-store integration or package publication.
- Original command-input inspection through the JavaScript query worker.

## Constraints already known

| Constraint | Source | Effect |
|---|---|---|
| Preserve disk formats and durable publication order. | Project context and accepted durability designs | Derive history from existing command/status/source artifacts. |
| Keep query host capabilities private. | DES-20260924-TTZ7C-59 | Extend the controlled query bridge; do not clone host objects or parser internals. |
| Keep large datasets file-backed and bounded. | DES-20260923-TTZ7C-47 | Historical records must be lazy; query workers receive only compact command metadata. |
| Keep SimplyStore simple and inspectable. | Active Muze cultures and project context | Add one history catalogue/view boundary, not an event-sourcing framework. |

## Important uncertainty / assumption

Historical record views need source/version-specific resolution while the
current parser retains only the winning location for each record. The chosen
implementation must demonstrate bounded lazy behavior and correct link
resolution without retaining a complete parser or full dataset copy for every
version. If the existing parser boundary cannot support that proportionately,
pause and re-plan before changing file formats or od-jsontag.

## Acceptance shape

Automated real-worker tests demonstrate base, edit, new, delete, restore, ID
change/reuse, multi-object command and no-op histories before and after restart
and live publication. Tests show old properties and links come from the selected
version, peers contain exactly the ID-bearing changed records, unsuccessful
commands remain absent, grants apply, views reject mutation, and query limits
remain effective. A representative multi-version probe records lookup cost,
memory/file-handle behavior and confirms that startup does not eagerly decode
historical records.
