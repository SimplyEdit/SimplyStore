## Analyze

### Goal

Make SimplyStore's open, command, query and close paths readable as a story at a
consistent abstraction level by introducing a cohesive store runtime and clear
mechanism boundaries. Preserve public/durable behavior and make the package
manifests match the implementation and supported dependencies.

### Baseline and gap

UND-20260919-TTZ7C-29 records the inspected baseline. `server.mjs` currently owns
Express, process lifecycle, store state, durable command sequencing and worker
mechanics in one nested closure. Behavior is strongly tested through processes,
but the command decisions have no small direct seam. Module state, repeated worker
mechanics and unused/outdated packages increase the cost of later changes.

### Plan continuity: deliberate deviation

Re-read SRC-001, REQ-001, DES-001 and the accepted 2026-09-19 recovery refinement.
This cycle deliberately precedes remaining randomized/soak and extension work.
The accepted durability cycle exposed coupling in the central runtime; correcting
it now lowers the risk of those later roadmap slices without replacing them.

### Shaping philosophy

The adopted Muze engineering and library stewardship profiles and the referenced
Programming for Wizards chapters favor explicit assumptions, small agreements,
late-bound mechanisms, plain data and replaceable application boundaries. The
maintainer adds a concrete code-reading rule: functions stay at one abstraction
level, extraction must lower cognitive load, related stateful operations should
be cohesive, and names optimize clarity rather than brevity.

## Plan

REQ-20260919-TTZ7C-30 defines acceptance. DES-20260919-TTZ7C-32 defines the
runtime, shell and mechanism boundaries.

### Work sequence

1. Add direct characterization tests around the runtime-facing command behavior
   where they cheaply protect the move.
2. Introduce `StoreRuntime`, move opened-store state and command/query lifecycle
   into story-level methods, and bind existing mechanisms explicitly.
3. Reduce `server.mjs` to the Express/listener/process shell while retaining its
   default application plus `run()` contract.
4. Consolidate one-shot worker mechanics only where load and command behavior can
   share one clear agreement; retain long-lived query pools separately.
5. Review the result for abstraction level, helper/name load, ownership and net
   complexity; correct the design rather than merely satisfying file boundaries.
6. Remove unused packages, apply compatible upgrades, regenerate lock data and
   resolve or explicitly bound audit findings.
7. Run focused, full durability/recovery and example verification, then present
   the integrated evidence for human acceptance.

### Non-goals

No new disk format, migration, REST/query/command redesign, VM2 replacement, full
rebuild, generic dependency framework, arbitrary large-file splitting, package
publication or deployment.

### Replan conditions

Return to discourse if the runtime boundary requires public or disk-format change,
weakens accepted command/durability semantics, needs a generic container to remain
testable, or creates more concepts than it removes. A dependency vulnerability
without a compatible supported resolution is reported rather than hidden through
an unsafe override.
