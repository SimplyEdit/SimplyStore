# Cycle: Command Update Crash Matrix And Reconstruction Oracle

Repository branch: `spiral/CYC-010-command-crash-matrix`
Branch verified: verified on 2026-08-17 with `git branch --show-current`. Branched from accepted CYC-009 context because local `master` does not yet contain the accepted Spiral metadata.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

SimplyStore's completed intake confirms that developer-evaluable production readiness is currently focused on bounded durability evidence while preserving simplicity and compatibility. Prior cycles added startup corruption classification, one process crash fault point, and repeated active-command crash safety. A critical review confirmed that durability remains the right first risk, but the risk should be sharpened from broad durability to the command update-cycle commit protocol.

Nearest important risk / uncertainty / desired movement:

The current command update lifecycle has several durable and in-memory boundaries. Only one injected process crash boundary is covered by process tests. Without a fuller matrix and an independent reconstruction oracle, SimplyStore may appear to recover correctly only because the normal startup/query path hides an ambiguous or partially committed state.

Relevant human direction / feedback:

The human agreed that the next cycle should prove the command update-cycle commit protocol across crash boundaries, with an independent reconstruction oracle, while respecting disk-format, JavaScript query API, and REST API compatibility.

## Plan

### Cycle goal

Add a focused command update crash matrix and an independent reconstruction oracle so SimplyStore can classify restart behavior across the next meaningful command lifecycle boundaries without silently changing the on-disk format or public query/REST APIs.

### Why now / why this cycle boundary

This is the next coherent proof boundary after accepted-command replay safety. The work can cover several related fault points and evidence steps under one evaluable outcome: whether the current command commit protocol is legible and falsifiable across process crashes.

### Current starting evidence

- `DES-001` defines committed-state recovery, no partial command visibility, command idempotency, deterministic reconstruction, laziness preservation, and detectable corruption.
- `EVD-006` proves the first process-level crash boundary at `before-command-done-status`.
- `EVD-007` proves repeatedly crashing accepted commands become `unsafe` instead of replaying forever.
- `src/server.mjs` currently has durable lifecycle boundaries around command log/status acceptance, active status, command-worker completion, query-worker update, and done status.
- `src/command-worker-module.mjs` writes the per-command changeset before the main thread marks the command `done`.

### Evaluation basis

The separate durability test run should prove a matrix of restart outcomes for newly added test-only fault points. The normal unit test run should remain focused and pass.

The tests should also include a reconstruction oracle that derives committed state from base data plus committed changesets independently of the server restart/query path.

Compatibility checks:

- do not rename existing endpoints;
- do not change the JavaScript query sandbox API;
- do not change existing durable record names or file naming except by adding test-only fault-point behavior;
- keep fault points inert outside `SIMPLYSTORE_ENV=test`.

### Likely work

- Add test-only fault points at meaningful command lifecycle boundaries.
- Add reusable durability test helpers where the current process tests are starting to duplicate server fixture setup.
- Add an independent reconstruction oracle for test assertions.
- Add matrix tests for crash/restart classification around acceptance, active marking, changeset visibility, query-worker update, and done status.
- Record evidence and any remaining uncovered boundaries.

### Explicit non-goals

- Replace VM2.
- Add a reset/repair tool.
- Add larger-system extension seams.
- Add hashing or integrity roots.
- Change public REST/query APIs.
- Change the durable on-disk format as part of this cycle.
- Prove filesystem behavior across power loss or directory fsync boundaries.

### Pause / re-plan conditions

- The crash matrix reveals that current durable record semantics are insufficient and require a format or API migration.
- The independent oracle cannot be built without depending on SimplyStore's normal startup behavior.
- Test-only fault points would create production-triggerable crash behavior.
