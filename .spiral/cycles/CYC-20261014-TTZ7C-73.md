## Analyze

Project state / prior evaluation that makes this cycle relevant:

Accepted file-backed retrieval, persisted indexes and isolated query execution
provide ordered immutable source files, current record identity and a controlled
host/guest query bridge. The accepted self-healing ownership cycle is integrated
on master. Queryable history is the next named roadmap target.

Important risk / uncertainty / desired movement:

The durable command log and changesets retain audit evidence, but queries cannot
inspect it. Adding history by copying snapshots or embedding metadata in domain
objects would change formats and scale poorly. The useful uncertainty is whether
existing sparse source indexes can support correct, lazy historical object views
and version-consistent links within the current query boundary.

Relevant human direction / feedback:

SRC-20261014-TTZ7C-69 retains the maintainer's settled choices: one dataset-file
timestamp, submitted author as-is, object command/version history, same-version
peer objects, no separate history authorization, and complete historical dataset
switching deferred. The maintainer explicitly instructed the project to start
this cycle with that intent and design.

Governing higher-level plan / direction:

`ROADMAP.md`, especially section 3, “Object versioning and audit trails,” plus
the accepted file-backed and isolated-query designs.

Current position in that plan:

Sections 2's file-backed retrieval and isolated-vm replacement are integrated.
This cycle begins section 3's queryable object audit trail. The UI remains later.

## Plan

### Cycle goal

Expose successful command/version metadata and immutable per-record object
history through the JavaScript query `meta` object, including dataset-file
timestamp, submitted author/message and the other ID-bearing objects written in
the same version, with correct historical link resolution and no disk-format
change.

### Commitment boundary

The maintainer confirmed the refined intent and design choices, then instructed:
“Lets start a cycle with this intent and design.” UND-20261014-TTZ7C-70 records
the confirmed interpretation and evidenced current gap; REQ-20261014-TTZ7C-71
operationalizes the outcome.

### Why now / why this cycle boundary

This is the next roadmap capability and directly reuses the recently integrated
file/query foundations. Command enumeration, version peers and object history
share one catalogue and one evaluation story. Whole-snapshot time travel would
add a materially different root-selection and capacity contract, so it remains
a later cycle.

### Plan continuity decision

Continue. The prior two cycles deliberately deviated to repair query identity
and ownership; both are integrated. Current evidence still supports roadmap
section 3, and the maintainer has now selected and bounded it explicitly.

### Current starting evidence

- inspection reconstructs exact commands/statuses and committed order;
- loading returns base plus committed changeset sources in that order;
- each source has sparse offsets and a captured file modification time;
- per-source ID sidecars are read but their entries are not retained;
- the active parser exposes only winning record locations;
- runtime discards committed command detail after startup;
- query `meta` exposes only current ID lookup and schema;
- live query updates contain source and current ID index, not version metadata.

### Evaluation basis

Real query-worker tests must demonstrate command enumeration and lookup, base and
command versions, historical record contents/links, same-version entity peers,
deletion/restoration and live/restart consistency. Existing grants, immutability,
resource limits, storage-failure classification, durability and current queries
must remain green. A representative history probe records latency, heap/file
handles and confirms historical payloads are not eagerly decoded at startup.

### Likely work

1. Add failing query/runtime fixtures covering the agreed public semantics.
2. Preserve command-log ranges and per-source ID entries after verified loading.
3. Add a committed-version catalogue and lazy version-aware record resolver.
4. Extend host query views and guest `meta` facades for commands, versions and
   object histories.
5. Publish new command/version metadata atomically with live source updates.
6. Document the query API, file-timestamp meaning and deferred snapshot boundary.
7. Run focused and full regressions, capacity probes and causal validation.

### Explicit non-goals

- Complete historical dataset/root switching.
- UI, REST API or curriculum-store changes.
- New history authorization, author validation or server commit timestamps.
- Replay/rebuild, workspaces, new persistent formats or migrations.
- Package version bump, publication, acceptance or integration.

### Pause / re-plan conditions

Pause if correct historical links require changing OD-JSONTag/disk formats; if
the only viable implementation retains complete datasets/parsers per version;
if command history cannot be read lazily without weakening log authority; or if
the query bridge cannot enforce existing grants and storage-failure semantics on
historical reads. Return to discourse before expanding into snapshot time travel
or a new authorization model.
