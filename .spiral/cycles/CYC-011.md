# Cycle: ACID Non-Durability Baseline

Repository branch: `spiral/CYC-011-acid-baseline`
Branch verified: verified on 2026-08-17 with `git branch --show-current`, branched from `master` after accepted CYC-010 was merged.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

CYC-010 strengthened durability evidence with a command crash matrix and reconstruction oracle. Before continuing deeper durability work, the human asked whether other ACID claims should be tested. A planning check found that durability remains the main risk, but the public ACID framing would be more credible if Atomicity, Consistency, Isolation, and duplicate command ID idempotency had focused smoke-level evidence.

Nearest important risk / uncertainty / desired movement:

SimplyStore could over-focus on durability while leaving the other ACID claims as design assertions only. A skeptical developer evaluating production readiness should see at least baseline tests that failed commands do not leak partial state, queries cannot mutate shared state, queries do not observe partial command state, and duplicate command IDs do not apply twice.

Relevant human direction / feedback:

The human accepted adding those tests before returning to durability.

## Plan

### Cycle goal

Add focused server-level ACID baseline tests for non-durability claims: atomic failed-command rollback, query isolation, narrow committed-state consistency, and normal duplicate command ID idempotency.

### Why now / why this cycle boundary

This is a small characterization cycle before deeper durability work. It improves the credibility of the overall ACID story without expanding SimplyStore into database-style machinery.

### Current starting evidence

- `design/acid.md` claims atomicity through sequential commands, consistency through internally consistent query snapshots, isolation through per-query VMs and immutable data, and durability through command log/replay.
- `DES-001` already includes durability-adjacent invariants for no partial command visibility and command idempotency.
- Existing tests focus on startup recovery and durability crash behavior, not normal ACID smoke coverage.

### Evaluation basis

Because these tests start full SimplyStore servers, they should run in a separate script rather than `npm test`.

Expected verification:

- `npm test` remains focused on non-server startup/unit durability tests.
- `npm run test:acid` passes focused ACID server tests.
- Existing `npm run test:durability` still passes.
- Targeted ESLint passes for changed files.

### Likely work

- Add a `test:acid` npm script.
- Extend durability server helpers only as needed for custom command fixtures.
- Add ACID baseline tests for atomicity, isolation, narrow consistency, and duplicate command ID idempotency.
- Record evidence.

### Explicit non-goals

- Prove broad domain consistency for arbitrary application command handlers.
- Prove serializability beyond SimplyStore's single command-worker model.
- Replace VM2.
- Change public REST/query APIs.
- Change durable on-disk formats.
- Add more durability crash boundaries.

### Pause / re-plan conditions

- A test reveals that the claimed API contract itself is ambiguous or incompatible with existing behavior.
- The tests require changing public endpoints or query semantics to express the claim.
