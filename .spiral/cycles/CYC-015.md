## Analyze

Project state / prior evaluation that makes this cycle relevant:

SimplyStore has completed baseline archaeology, process crash/fault evidence, independent reconstruction checks, adversarial storage classification, and retry/idempotency hardening. The original durability/extensibility plan now points to after-change handler contracts before integrity roots.

Nearest important risk / uncertainty / desired movement:

Current index/external file writes may define accidental commit boundaries, and handler mutation permissions are implicit. Before adding integrity roots as a finalizing capability, SimplyStore needs evidence about the current indexer lifecycle and a minimal contract direction for mutation, derived, and finalizing behavior.

`.spiral/sources/SRC-001.md`, `.spiral/requests/REQ-001.md`, and `.spiral/designs/DES-001.md` govern the durability/extensibility sequence.

Current position in that plan:

Continue after retry/idempotency hardening. The next planned slice is after-change handler contracts and handler failure evidence. Integrity roots remain deferred until replay/crash behavior and handler contracts are stable.

## Plan

### Cycle goal

Characterize the current indexer/after-change lifecycle and produce the smallest evidence-backed handler contract direction needed before broadening extension behavior.

### Why now / why this cycle boundary

This is the next useful boundary because handler behavior can affect commit safety, mutation permissions, derived files, and future integrity finalizers. The cycle should first establish current behavior and contract needs; implementation can stay minimal unless the tests expose a correction needed to make behavior explicit.

### Plan continuity decision

Continue. This follows the governing durability/extensibility plan after retry/idempotency and before integrity roots. The latest evidence does not justify revising or deviating from that plan.

### Current starting evidence

- `REQ-001` records index/external file writes as a near-term risk because they may define accidental commit boundaries.
- `DES-001` says handler-contract failure tests should happen before integrity-root tests.
- Existing command lifecycle evidence shows index updates happen before command outcome is marked done, but current mutation/failure semantics need focused characterization.

### Evaluation basis

- Current indexer lifecycle is documented from code and executable tests.
- Tests characterize whether index/update handlers can mutate canonical state.
- Tests characterize commit behavior when index creation/update fails.
- Any proposed handler contract is explicitly scoped and does not become a broad plugin/event framework.

### Likely work

- Inspect `src/index*.mjs`, command worker code, load worker code, and existing tests.
- Add focused characterization tests for indexer mutation and failure behavior.
- Record a design or understanding artifact for the minimal handler contract direction.
- Implement only small corrections if characterization exposes unsafe or misleading behavior within this cycle goal.
- Record evidence.

### Explicit non-goals

- Add integrity hashes or integrity roots.
- Implement a broad plugin framework.
- Implement Kafka, queues, webhooks, topics, or consumer offsets.
- Redesign the public REST or JavaScript query API.
- Change durable OD-JSONTag formats.
- Add post-commit extension observers.

### Pause / re-plan conditions

- Current indexer behavior contradicts the intended reconstruction model.
- Safe handler contracts require breaking existing extension behavior.
- A minimal correction starts resembling a general event or transaction framework.
- Current code lacks enough seams to test handler failure behavior without first doing broader refactoring.
