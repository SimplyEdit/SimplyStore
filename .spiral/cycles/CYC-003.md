# Cycle: Startup Recovery Repair

## Analyze

Project state / prior evaluation that makes this cycle relevant:

`CYC-002` was accepted with failing executable evidence for two startup/recovery durability gaps.

Nearest important risk / uncertainty / desired movement:

Startup recovery currently does not distinguish committed command changesets from non-committed command changesets, and does not fail when a committed command's changeset is missing.

Relevant human direction / feedback:

The human accepted `CYC-002` and asked to continue.

## Plan

### Cycle goal

Repair startup reconstruction so current tests establish:

- accepted-but-not-done changesets are not exposed as committed state;
- done commands with missing changesets produce explicit recovery failure.

### Why now

These are the first accepted executable counterexamples against D1, D2, and D6 from `DES-001`.

### Current starting evidence

- `EVD-002`: `npm test` fails with the two startup recovery counterexamples.
- Current server startup passes all status keys to the load worker.
- Current load worker silently skips missing command-named changeset files.

### Evaluation basis

`npm test` should pass the new durability startup tests, while preserving the existing skipped `test/produce.mjs` baseline.

### Likely work

- Add a small recovery helper that selects committed command IDs from status.
- Make the load worker require every supplied committed changeset file to exist.
- Keep behavior changes limited to startup reconstruction.
- Update evidence with the passing test result.

### Explicit non-goals

- Add full SIGKILL fault injection.
- Change command acceptance/outcome write ordering.
- Rename `done` to `committed`.
- Add integrity hashing.
- Add handler contracts or post-commit seams.

### Pause / re-plan conditions

- The repair requires changing durable log/status format.
- The repair requires rerunning command semantics during recovery.
- The repair reveals that `done` is not the right committed boundary.

## Act

Important artifacts / semantic commits produced:

- `IMP-001`: startup recovery command selection and committed changeset existence check.
- `EVD-003`: passing verification evidence for the repair.

Material implementation decisions or deviations from the initial likely work:

- Added `src/recovery.mjs` as a small shared helper for committed command selection and changeset path/existence checks.
- Kept `done` as the current committed status term.
- Made `load-worker.mjs` require every supplied committed changeset file.
- Updated `package.json#scripts.test` with explicit zero tap coverage thresholds so assertion success determines `npm test` status while coverage is still reported.

Out-of-scope discoveries retained for later:

- Command log/status append calls are still not awaited.
- Full server-process restart and `SIGKILL` fault injection remain unimplemented.
- Command status/log parsing still needs malformed/truncated-line tests.
- `runNextCommand()` contains an apparently unreachable `commandWorkerInstance` termination branch in the "no pending commands" path. The final `mainResolve(false)` still appears correct, but the preceding branch is redundant/dead and should be cleaned up in a later behavior-preserving maintenance slice.

## Evaluate

Integrated result against cycle goal:

The two accepted startup recovery failures are repaired.

Evidence / acceptance result:

`npm test` passes and targeted ESLint passes. Evidence is recorded in `EVD-003`.

Metric or risk movement:

The first two executable startup/recovery risks from `EVD-002` are resolved for the current harness. Broader durability risk remains.

What changed in our understanding:

The minimal repair can be made without changing durable status vocabulary or introducing broader transaction machinery.

Surprises / model mismatches:

Node-tap's effective default coverage thresholds were 100%, so passing assertions still returned exit code 1 until the test script made thresholds explicit.

Known compromises:

The harness still tests the load worker and recovery helper rather than driving a complete server restart.

Unresolved issues within current goal:

None known for the two targeted recovery cases.

Candidate next-cycle inputs:

- Extend the harness to full server startup with command-status and command-log files.
- Add crash/fault-injection points around command acceptance, changeset write, and outcome append.
- Repair unawaited durable appends if fault evidence confirms the expected risk.
- Clean up the unreachable `commandWorkerInstance` branch in `runNextCommand()` after preserving its intended behavior with a focused test or static check.
