# Cycle: Durability Baseline Archaeology

## Analyze

Project state / prior evaluation that makes this cycle relevant:

SimplyStore is being adopted into Spiral as a brownfield project. The human's first production-readiness priority is proving durability claims while preserving simplicity.

Nearest important risk / uncertainty / desired movement:

The current command update lifecycle may not have explicit, tested commit boundaries. Before implementation changes, the actual checked-out behavior must be documented.

Relevant human direction / feedback:

The human supplied the durability/extensibility direction captured in `SRC-001`.

## Plan

### Cycle goal

Establish baseline evidence for the current command/update/recovery lifecycle and create the initial durability request/design artifacts that will govern the first implementation slice.

### Why now

The requested plan explicitly says to perform baseline archaeology before behavior changes. Spiral also requires current effective behavior and an evidenced gap before consequential product modification.

### Current starting evidence

- README says SimplyStore is experimental and includes a roadmap item to stress test ACID compliance.
- ROADMAP says commands already create separate changeset files and startup merges changesets.
- No active durability tests were known before this cycle.

### Evaluation basis

This cycle can be evaluated when the repository contains:

- source/understanding/request/design artifacts for the durability direction;
- baseline evidence documenting current command lifecycle, statuses, changeset and status durability points, indexer behavior, startup reconstruction, and current test baseline;
- no product behavior changes.

### Likely work

- Inspect command, load, index, utility, roadmap, and existing test files.
- Run existing tests.
- Preserve baseline findings as `EVD-001`.
- Update project context with the ordered durability/extensibility direction.

### Explicit non-goals

- Implement crash/fault-injection hooks.
- Change command, status, changeset, index, or recovery behavior.
- Add hashing or integrity roots.
- Design the final after-change handler API.
- Implement post-commit integrations.

### Pause / re-plan conditions

- Current behavior contradicts the core reconstruction model enough that the first implementation slice should be redesigned.
- The evidence shows SimplyStore cannot reconstruct state from committed partial datasets without rerunning command semantics.
- Any proposed solution starts resembling a general transaction/event framework.

## Act

Important artifacts / semantic commits produced:

- `SRC-001`: human-provided durability and extensibility direction.
- `UND-001`: interpreted direction: durability proof first, minimal extensibility second.
- `REQ-001`: durability evidence request.
- `DES-001`: durability invariants and evidence order.
- `EVD-001`: baseline command/update/recovery archaeology.

Material implementation decisions or deviations from the initial likely work:

No product behavior was changed. This cycle intentionally stayed at baseline evidence and process/artifact setup.

Out-of-scope discoveries retained for later:

- The current command log/status append calls are not awaited by lifecycle callers.
- Startup reconstruction currently supplies all status keys to the loader, not only `done` commands.
- Missing per-command changeset files are silently skipped.
- Existing index writes occur before changeset write and command outcome append, without an explicit lifecycle contract.
- Existing automated tests do not currently exercise command durability.

## Evaluate

Integrated result against cycle goal:

The cycle established baseline evidence for the current command/update/recovery lifecycle and created the initial durability source, understanding, request, design, and evidence artifacts.

Evidence / acceptance result:

Evidence exists in `EVD-001`. Acceptance is incomplete until human review confirms this baseline is the right starting point for the first implementation slice.

Metric or risk movement:

The durability risk moved from broad concern to concrete test targets. No durability risk is resolved yet.

What changed in our understanding:

The checked-out behavior exposes sharper risks than the high-level roadmap alone:

- accepted/done/failed are the actual status terms;
- `done` is the closest current equivalent to committed;
- existing durable appends use `datasync` internally but are not awaited by command lifecycle callers;
- current startup can silently skip missing changesets and can load changesets for non-`done` status keys if matching files exist.

Surprises / model mismatches:

- The pasted plan assumed current public master has command-associated changesets; the example root has command logs/statuses but no observed per-command data changeset files.
- The loader's use of all status keys creates a likely mismatch with the intended committed-only reconstruction model.

Known compromises:

The companion Turtle resources are intentionally minimal in this first pass. Exact cross-artifact Git-version references should be added after artifacts are committed in semantic causal commits.

Unresolved issues within current goal:

- Human review should confirm whether the baseline evidence is sufficient.
- Turtle/RDF validation tooling is not yet available in this repository.

Candidate next-cycle inputs:

- Implement the first crash/fault-injection harness slice around actual command lifecycle boundaries.
- Add focused regression tests for missing changeset with `done` status and existing changeset with `accepted` status.
- Decide whether the first harness should exercise internals directly or drive a child SimplyStore process through HTTP.

Human evaluation / feedback:

On 2026-08-17, the human agreed with the assessment that CYC-001 established the baseline and that the next cycle should build the first executable durability harness around the highest-risk startup/recovery contradictions.

Cycle accepted, still open, or deliberately re-planned:

Accepted.

## Process learning

What context/constraint/evaluation helped:

The instruction to treat the checkout as authoritative prevented carrying the pasted lifecycle assumptions forward untested.

What bookkeeping was useless:

No conclusion yet.

What should the environment learn from this cycle:

For SimplyStore durability work, baseline archaeology must include actual status-key selection, changeset existence handling, and whether durable write promises are awaited.
