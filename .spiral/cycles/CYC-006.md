# Cycle: Durable Artifact Corruption Classification

## Analyze

Project state / prior evaluation that makes this cycle relevant:

`CYC-004` proved startup selection from real durable command-status and command-log files, but malformed or truncated records remained unclassified.

Nearest important risk / uncertainty / desired movement:

SimplyStore should fail explicitly instead of silently accepting corrupted durable startup artifacts. For developers evaluating SimplyStore, this failure behavior should be visible in tests and evidence.

Relevant human direction / feedback:

The human stated that the system should survive crashes at any point in the update cycle and recover, or fail instead of silently using corrupted data. The current production-readiness audience is primarily developers evaluating SimplyStore.

## Plan

### Cycle goal

Classify malformed and structurally invalid durable command-status and command-log records as explicit recovery integrity failures.

### Why now

This is a small D6 slice after full startup parsing was shared. It improves developer-evaluable durability evidence without requiring full process crash injection yet.

### Current starting evidence

- `EVD-004` showed real durable status/log startup parsing.
- `DES-001` defines D6 detectable corruption.
- `UND-001` recorded malformed log/status lines as an evidenced gap.

### Evaluation basis

`npm test` should pass tests showing that:

- malformed command-status lines raise an explicit recovery integrity error;
- command-status records missing required `command` fields raise an explicit recovery integrity error;
- malformed command-log lines raise an explicit recovery integrity error;
- command-log records missing required `id` fields raise an explicit recovery integrity error.

Targeted ESLint should pass for the changed recovery helper and durability tests.

### Likely work

- Add an explicit recovery integrity error type in `src/recovery.mjs`.
- Validate durable status/log records at parse time.
- Add TAP tests for malformed and structurally invalid durable records.
- Record evidence in `EVD-005`.

### Explicit non-goals

- Add `SIGKILL` or process-level crash injection.
- Define every cross-file durable artifact inconsistency.
- Change durable record format.
- Add integrity hashes.
- Clean up unrelated command-worker control flow.

### Pause / re-plan conditions

- Validation requires changing existing valid durable record shape.
- Tests require starting a full HTTP server process.
- Corruption handling broadens into automatic repair.

## Act

Important artifacts / semantic commits produced:

- `72b2ad9d675fd49032d8ed5be8fa998be6141f51`: `src/recovery.mjs` now exposes `RecoveryIntegrityError` and validates durable status/log records.
- `test/durability-startup.mjs` now covers malformed and structurally invalid command-status and command-log records.
- `IMP-001` revised with the new corruption-classification behavior.
- `EVD-005` records the passing verification.

Material implementation decisions or deviations from the initial likely work:

The implementation validates only record parseability and required structural fields. It does not yet define all cross-file consistency rules.

Out-of-scope discoveries retained for later:

- Full process crash injection remains unimplemented.
- Unawaited durable appends remain unresolved.
- Cross-file durable artifact consistency beyond missing committed changesets remains future work.

## Evaluate

Integrated result against cycle goal:

Malformed and structurally invalid command-status and command-log records now fail through `RecoveryIntegrityError` with file, line number, and record kind metadata.

Evidence / acceptance result:

`npm test` passes with 19 assertions and 1 existing skipped empty test file. Targeted ESLint passes. Evidence is recorded in `EVD-005`.

Metric or risk movement:

D6 detectable corruption now has executable coverage for malformed and structurally invalid durable status/log records. The broader crash-cycle durability risk remains open.

What changed in our understanding:

The shared recovery helper is the right boundary for durable startup artifact validation. This keeps the behavior visible to both server startup and direct recovery tests.

Surprises / model mismatches:

None material.

Known compromises:

This is not full corruption detection. It is a narrow structural classification slice.

Unresolved issues within current goal:

None known for malformed and missing-required-field status/log records.

Candidate next-cycle inputs:

- Add fault points and `SIGKILL` around command acceptance, changeset write, and outcome append.
- Classify additional cross-file artifact inconsistencies.
- Repair unawaited command log/status appends after fault evidence confirms the expected risk.
