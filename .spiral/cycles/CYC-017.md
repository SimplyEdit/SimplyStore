# Cycle: Command And Load Worker Timeout Semantics

Repository branch: `spiral/CYC-017-command-worker-timeouts`
Branch verified: verified on 2026-08-18 with `git branch --show-current`, branched from `master` after accepted CYC-016 was merged.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

SimplyStore has executable process-crash durability evidence for command acceptance, active marking, changeset write, durable `done`, query visibility, duplicate command-log replay, and unsafe replay classification. Query execution already has timeout guards through VM2, but command and load workers do not yet have equivalent timeout semantics.

Important risk / uncertainty / desired movement:

Timeouts are a high-leverage durability uncertainty because they can leave progress ambiguous while the server process survives. A command handler, command worker, or load worker may hang or run too long without triggering the crash/restart paths already tested. Late discovery would affect command lifecycle semantics, retry behavior, queue progress, recovery behavior, and developer-facing durability claims.

Relevant human direction / feedback:

The human accepted CYC-016 and agreed to pull timeout assessment forward before integrity roots. The human also proposed using the same broad timeout-guard idea as the query worker, while keeping the cycle goal broad enough to finish the timeout issue after analyzing current behavior and choosing intended semantics.

Governing higher-level plan / direction:

`.spiral/sources/SRC-001.md`, `.spiral/requests/REQ-001.md`, and `.spiral/designs/DES-001.md` govern the durability/extensibility sequence. `DES-001` requires committed-state recovery, no partial command visibility, command idempotency, deterministic reconstruction, laziness preservation, and detectable corruption.

Current position in that plan:

Revise the original order by pulling command/load worker timeout semantics ahead of integrity roots. This does not abandon the plan; it reduces a lifecycle ambiguity that integrity-root work would otherwise depend on.

## Plan

### Cycle goal

Finish the command/load worker timeout issue: characterize current behavior, choose explicit durability-safe timeout semantics, implement the smallest compatible timeout handling needed for command and load workers, and verify the result with focused tests.

### Commitment boundary

Human confirmed on 2026-08-18: "Agreed, but I'd keep that in the current cycle, make the goal to finish the whole timeout issue, after analyzing current behaviour and choosing intended semantics."

### Why now / why this cycle boundary

The timeout question has downstream leverage. If command or load workers can hang while the server remains alive, later integrity work may certify stored bytes while leaving command progress, replay, queue advancement, or startup recovery ambiguous. A single coherent cycle is appropriate because characterization, semantics choice, implementation, and verification need to agree.

### Plan continuity decision

Revise. The governing plan would next move toward integrity roots, but timeout semantics sit upstream of that work. Pulling them forward avoids building integrity metadata on an incomplete command lifecycle model.

### Current starting evidence

- Query timeout exists inside VM2 query execution.
- Command workers are dedicated worker threads started from `src/server.mjs#runNextCommand`.
- Load workers are dedicated worker threads started from `src/server.mjs#loadData`.
- Existing durability evidence covers process crashes, not surviving-process worker hangs/timeouts.
- Slow active-command retry is tested, but only as active-state/idempotency behavior; it does not exercise a command timeout.

### Evaluation basis

- Characterization demonstrates current command/load timeout behavior before implementation.
- The chosen timeout semantics are recorded before product behavior changes.
- Command timeout behavior has focused tests for status, queue progress, retry behavior, and committed-state safety.
- Load timeout behavior has focused tests for explicit startup/load failure.
- Existing durability and ACID tests still pass.
- No durable on-disk format, REST endpoint name, or JavaScript query API change is introduced without explicit evidence.

### Likely work

- Inspect current worker lifecycle and query timeout implementation.
- Add current-behavior characterization tests for hanging command and hanging load worker behavior.
- Record intended command/load timeout semantics in a design or implementation artifact before runtime changes.
- Implement the smallest timeout mechanism, likely at the main-thread worker boundary rather than by reusing VM2 internals.
- Add verification evidence.

### Explicit non-goals

- Replace VM2 or change query sandbox behavior.
- Add general job queues, schedulers, cancellation frameworks, or worker orchestration machinery.
- Add integrity roots or hashing.
- Change durable OD-JSONTag format.
- Redesign public REST endpoints or JavaScript query bindings.
- Solve reset/repair tooling for dirty datasets.

### Pause / re-plan conditions

- Current behavior shows that timeout semantics require a public API or durable format change.
- Worker termination cannot be made deterministic enough for the intended durability claim without broader architecture changes.
- Load timeout semantics conflict with current startup recovery assumptions.
- A minimal timeout mechanism starts resembling a general task orchestration framework.
