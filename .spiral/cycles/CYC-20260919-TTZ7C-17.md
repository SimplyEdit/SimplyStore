## Analyze

### Goal

Make command acceptance and completion durable across the supported power-loss
model, and provide an administrator with a tested, evidence-preserving recovery
route when committed storage cannot be reconstructed automatically.

### Current effective behavior and gap

The project has crash/retry, malformed-storage, handler, timeout, integrity, and
persisted-offset evidence. The latest offset cycle is accepted and merged.
Log appends already await `datasync`; changesets/final offsets already use file
sync plus rename. Directory entries, initial base/ID-index writes, sync-error
handling, and administrator recovery remain incomplete. Existing retry evidence
does not establish safety for secondary effects. The detailed inspected baseline
and input-completeness caveat are in UND-20260919-TTZ7C-19.

### Why this boundary and why now

A narrower sync-only change would leave administrators stranded after explicit
startup failure and would retain unsafe replay assumptions. One cycle therefore
covers failure evidence, persistence ordering, recovery decisions, and backup
restoration. Full rebuild has a separate evaluation boundary: intentionally
changed code and cooperative suppression of effects need their own workflow.

### Plan continuity: revise

Re-read SRC-001, REQ-001, and DES-001. After accepted crash/retry/handler and
integrity slices and the offset correction, bring file publication and
administrative recovery ahead of general randomized/soak testing. The new human
direction strengthens failure-only recovery expectations and preserves the
existing small architecture. It does not replace the remaining roadmap.

### Adopted profiles

The project's Muze engineering and library stewardship profiles apply: preserve
inspectability, small replaceable mechanisms, and explicit compatibility.
WPF-HUMAN-001 applies to acknowledgment evidence, administrator authority, and
recovery options. No new profile or independent veto is introduced. The concrete
scope is grounded in the maintainer's requirements.

## Plan

### Committed requirements

REQ-20260919-TTZ7C-20 is the acceptance matrix (P1-P12), interpreted from retained
human direction in SRC-20260919-TTZ7C-18 and UND-20260919-TTZ7C-19.

- Complete command inputs must be logged; demonstrated omissions are bugs.
- Ordinary rerun requires administrator approval and no later accepted command
  with a dataset. Recover the eligible trailing sequence in original order.
- Missing data is not proof that external effects did not happen. Existing
  corrupt/ambiguous data is not silently classified as missing.
- Automatic retries and ordinary queue activity cannot bypass recovery rules.
- Preserve original evidence, work on a copy, validate and explicitly promote.
- Provide a tested consistent backup/restore path for unsafe/disallowed reruns.
- Retain separate rebuild semantics: selected code/history, new output store,
  side-effect suppression context for commands/hooks; full workflow follows.

### Work sequence

1. **Failure matrix and baseline:** enumerate durable artifacts and dependencies,
   establish command ordering/ownership, model lost/reordered/partial writes and
   lost directory entries, and record acknowledgments independently of the store.
   Preserve failing evidence before correcting runtime behavior.
2. **Design:** specify acceptance/completion barriers, required versus rebuildable
   indexes, initial-file publication, I/O uncertainty handling, recovery preview
   and apply behavior, input completeness, and compatibility. Create DES/IMP/EVD
   artifacts when those decisions/results crystallize, not empty placeholders.
3. **Durable writes:** complete file/directory sync sequencing before acceptance
   or completion becomes visible; ensure errors cannot falsely report success
   or allow unsafe further mutations.
4. **Administrative recovery:** implement inspect/preview and explicitly authorized
   ordered recovery on a copy; enforce later-dataset guards, stop on uncertain
   effects, revalidate stale plans, and record outcomes without erasing history.
   Cover interruption of recovery itself and normal/automatic queue interactions.
5. **Inputs and backup/restore:** test normal versus recovered invocation inputs,
   correct demonstrated log omissions, diagnose incomplete legacy records, and
   exercise consistent backup creation and restoration with reported coverage.
6. **Filesystem validation and evaluation:** exercise a disposable block-level
   power-loss setup on a documented Linux/local filesystem, measure commit
   latency, run relevant regression suites and checks, and provide a runnable
   administrator guide with bounded durability claims and known limitations.

### Acceptance examples

| Scenario | Required result |
|---|---|
| Power cut after observed `accepted` | Complete accepted command survives under the supported model; replay safety is assessed separately |
| Power cut after observed `done` | Recovered state includes that completed transition, with no partial state, duplication, or silent rollback |
| Write/sync/rename failure | No false acknowledgment; uncertain outcomes prevent further mutation pending recovery |
| A has data, B missing, C has data | Rerunning B is blocked, even if C is not currently `done` |
| A has data, B missing, C waiting, D missing | Administrator can authorize B/C/D in order after judging external effects |
| Later dataset appears after preview | Stale recovery plan is rejected/recomputed before execution |
| Corrupt artifact or incomplete log evidence | Explicit diagnosis; do not infer eligibility from absence of valid parsing |
| Rerun unsafe or prohibited | Demonstrate backup restoration, disclose verified coverage, loss, and uncertainty |
| Interrupted administrative recovery | Original evidence remains intact; subsequent inspection can explain the partial recovery attempt |

All P1-P12 criteria remain open until evidenced; P12 is documentation of a
follow-up contract, not acceptance of an implemented rebuild feature. Existing
startup/offset, handler, ACID, and crash suites must remain green with any
intentional retry-policy changes reflected by justified new tests.

### Non-goals

Full rebuild tooling, broad randomized/soak campaigns, arbitrary external-effect
rollback or exactly-once delivery, sandbox replacement, general database/message
frameworks, remote-filesystem promises, package release, and production recovery
or deployment. The focused block-level fault exercise remains in scope.

### Material assumptions and replan conditions

The first envelope is a named Linux/local filesystem with storage honoring
flushes and one writer; exact environment and ownership checks are design work.
Destructive tests use disposable storage only. Missing test infrastructure leaves
the required exercise outstanding; it does not authorize a weaker claim.

Replan affected work if authoritative command order cannot be established,
necessary legacy inputs cannot be recovered, a breaking format/API change is
required without an accepted compatibility path, or the smallest safe solution
contradicts the stated architecture/administrator rules. Storage irrecoverability
must be reported honestly, not hidden by an invented replay outcome.

### Baseline slice — 2026-09-19

DES-20260919-TTZ7C-21 defines an independent observer and test-only I/O fault
harness. IMP-20260919-TTZ7C-22 implements 21 scenarios plus the matrix in
`docs/power-loss-baseline.md`; EVD-20260919-TTZ7C-23 records results and limits.

`npm run test:power-loss` passes its 21 scenario/control tests and explicitly
reports 10 violated invariant assertions as TODO. Strict mode exposes those
failures with exit 1. Existing regression suites pass 59/59. Runtime behavior
is unchanged; this is evidence of gaps, not a power-loss safety claim.

The failures cover lost log/status/changeset names, acknowledged partial writes,
repeated external effects, absent later-dataset rerun guards, configured-worker
request input loss, changed waiting-queue order after restart, and automatic
reclassification of uncertain work before failed startup. Positive directory-sync
and normal-restart controls distinguish the modeled barrier conditions.

### Durable-write and recovery design — 2026-09-19

DES-20260919-TTZ7C-24 specifies complete-write loops, file and directory barriers,
initial publication, ownership, serialized acceptance/status/outcome handling,
versioned input-complete command records, and a staged compatibility path.
OD-JSONTag datasets and public command payloads remain unchanged. The v2 log
format uses explicit initialization/migration into a separate store; legacy
behavior is not silently converted or advertised as satisfying the new guarantee.

DES-20260919-TTZ7C-25 specifies read-only inspection, source-bound recovery plans,
the exact later-accepted-dataset guard, explicit execution approval, preserved
source evidence, interruption handling, offline backup/restore, and separate
promotion. Rebuild remains a follow-up contract. Both designs map baseline gaps
and remaining acceptance tests to concrete implementation responsibilities.

Step 2 is recorded. Next executable work is step 3: implement byte-complete
durable publication/append primitives and directory barriers, including short
writes, errors, conversion, and integrity cases. Then implement ownership,
ordered records, and guarded recovery as specified. Runtime fixes, new passing
invariants, backup/restore tooling, latency, and real filesystem evidence remain
outstanding. No new test run or runtime guarantee is claimed by the design step.
