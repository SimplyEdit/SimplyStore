# Cycle: Retry And Idempotency Hardening

Repository branch: `spiral/CYC-013-retry-idempotency`
Branch verified: verified on 2026-08-17 with `git branch --show-current`, branched from accepted CYC-012.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

CYC-010 built process-crash evidence for the command update cycle, CYC-011 added baseline non-durability ACID tests, and CYC-012 classified malformed OD-JSONTag record framing. The original durability source orders retry/idempotency hardening after adversarial storage and before handler contracts and integrity roots.

Nearest important risk / uncertainty / desired movement:

A command may commit successfully while the client never receives the response, or a process may crash while a command is accepted/active. Retrying the same command ID must not produce more than one committed state transition, and unsafe repeatedly crashing commands must not trap an automatically restarted server in a death loop.

Relevant human direction / feedback:

The human asked to stick to the original durability plan and agreed that retry/idempotency hardening is next. Earlier human feedback clarified that accepted commands should be scheduled again rather than forced to fail, while repeatedly crashing accepted commands may need unsafe-command handling.

## Plan

### Cycle goal

Add focused retry/idempotency evidence and hardening for lost-response and crash/retry command paths so one logical command ID can produce at most one committed transition.

### Why now / why this cycle boundary

This follows the original durability sequence after adversarial storage classification and before after-change handler contracts and integrity roots. It keeps integrity work from hashing over retry semantics that have not yet been explicitly proven.

### Current starting evidence

- `DES-001` D3 says a command ID represents one logical command and retries must not create the transition twice.
- `REQ-001` identifies accepted-command partial apply/re-apply after crash as a blocker risk.
- `SRC-001` gives two explicit retry cases: committed command with lost response, and crash during processing followed by retrying the same command ID.
- CYC-010 includes unsafe replay handling for repeated active-command crashes, but the lost-response and retry API behavior still need focused evidence.

### Evaluation basis

Because retry/idempotency behavior is server-level and process-level, verification should use the separate server suites rather than `npm test` alone.

Expected verification:

- `npm test` remains focused on non-server unit/startup coverage.
- `npm run test:acid` still passes.
- `npm run test:durability` passes with retry/idempotency scenarios.
- Targeted ESLint passes for changed files.

### Likely work

- Add or extend durability server tests for same-command retry after a successful commit.
- Add or extend crash durability tests for retry after accepted/active crash boundaries.
- Preserve current intended behavior that accepted-but-uncommitted commands are scheduled again.
- Harden unsafe repeated-crash behavior only if focused tests expose a gap.
- Record evidence and implementation provenance.

### Explicit non-goals

- Add integrity hashes or integrity roots.
- Add after-change handler contracts.
- Change durable OD-JSONTag formats.
- Implement cleanup/reset tooling.
- Change public REST response semantics unless a correctness issue requires it.

### Pause / re-plan conditions

- Current command records do not contain enough information to retry safely without changing the durable command contract.
- A fix would require breaking current REST command submission semantics.
- Unsafe-command handling conflicts with the intended accepted-command retry behavior.
- A proposed solution starts to look like a general queue or transaction framework.
