# Cycle: Adversarial OD-JSONTag Storage Classification

Repository branch: `spiral/CYC-012-adversarial-od-jsontag`
Branch verified: verified on 2026-08-17 with `git branch --show-current`. Branched from accepted CYC-011 context because local `master` did not yet contain CYC-011.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

CYC-010 expanded process crash evidence for the command update lifecycle. CYC-011 added smoke-level tests for the other ACID claims. The next durability risk is adversarial durable storage: files on disk can be corrupt, truncated, stale, orphaned, or altered outside the normal command lifecycle.

Nearest important risk / uncertainty / desired movement:

The human is especially worried about corrupted or altered OD-JSONTag files. These files are the actual durable state material; if SimplyStore silently accepts invalid or inconsistent base data or changesets, the durability claim fails even if status/log parsing and crash recovery look good.

Relevant human direction / feedback:

The human agreed to tackle adversarial durable storage classification next and emphasized corrupted or altered OD-JSONTag files.

## Plan

### Cycle goal

Add focused adversarial startup/recovery tests for corrupted or altered OD-JSONTag durable files, especially committed changesets, so SimplyStore either recovers valid committed state or fails explicitly instead of silently using corrupt data.

### Why now / why this cycle boundary

This is the next coherent durability proof boundary after crash matrix and baseline ACID evidence. It avoids adding cleanup/repair tooling before we know which disk states are safe to ignore and which must stop startup.

### Current starting evidence

- `DES-001` requires detectable corruption and committed-state recovery.
- Existing startup tests cover missing committed changesets and malformed command log/status records.
- Existing crash tests cover process interruption boundaries, not altered OD-JSONTag content.
- The load worker parses the base OD-JSONTag file and committed changeset files during startup.

### Evaluation basis

`npm test` should cover focused non-server startup/recovery classifications for corrupted or altered OD-JSONTag files. Server-level durability and ACID suites should continue to pass because shared helpers may be touched.

Expected verification:

- `npm test`
- `npm run test:acid`
- `npm run test:durability`
- targeted ESLint for changed files

### Likely work

- Add startup tests for truncated/corrupt base OD-JSONTag file.
- Add startup tests for truncated/corrupt committed changeset file.
- Add startup tests for stale/uncommitted changeset files that should not affect committed state.
- Add startup tests for altered committed changesets that remain syntactically valid but do not correspond to command log/status expectations where detectable.
- Add explicit recovery error wrapping if current worker errors are too opaque for developer evaluation.

### Explicit non-goals

- Implement repair or reset tooling.
- Add hashing or integrity roots.
- Prove malicious syntactically valid data tampering without integrity metadata.
- Change OD-JSONTag durable format.
- Change public REST/query APIs.
- Add broader storage soak/property tests.

### Pause / re-plan conditions

- Detecting a class of altered-but-valid OD-JSONTag data requires adding integrity metadata or changing the durable format.
- Current parser behavior makes corruption failures impossible to classify without a broader loader redesign.

## Act

Important artifacts / semantic commits produced:

- `7d514568349d6a14ac494155549579533af68bf4`: adds OD-JSONTag framing validation for base data and committed changesets, plus adversarial startup tests.
- `IMP-006` records malformed OD-JSONTag record-framing classification.
- `EVD-011` records verification.

Material implementation decisions or deviations from the initial likely work:

The implementation validates OD-JSONTag record framing before parsing, including valid `+N` skip records used by changesets. This catches malformed, non-OD, and truncated record payloads before lazy parsing can hide them, without forcing full semantic materialization.

Out-of-scope discoveries retained for later:

Well-formed malicious changeset alteration is not detectable with the current durable format because changesets do not carry command IDs or integrity metadata. Detecting that class needs a future integrity root/hash/signature design.

## Evaluate

Integrated result against cycle goal:

SimplyStore now refuses base OD-JSONTag files and committed changeset files with malformed/truncated record framing during startup reconstruction. Uncommitted changeset files with malformed framing are ignored when their command is not committed.

Evidence / acceptance result:

`npm test` passes with 16 startup/unit durability tests. `npm run test:acid` passes with 4 ACID baseline server tests. `npm run test:durability` passes with 13 process durability tests. Targeted ESLint passes for the changed files. Evidence is recorded in `EVD-011`.

Metric or risk movement:

Corrupted OD-JSONTag storage risk is reduced for malformed-framing and truncated base/committed files. Altered-but-well-formed committed changesets remain a known integrity gap rather than a hidden claim.

What changed in our understanding:

OD-JSONTag parsing can be lazy enough for truncated referenced records to evade immediate parse errors. Framing validation gives a cheap corruption check without materializing every object.

Surprises / model mismatches:

Valid changeset files can include `+N` skip records for unchanged prior records. The first validator attempt was too strict until this OD-JSONTag patch syntax was accounted for.

Known compromises:

The validator checks byte framing, not semantic trust. It cannot detect a well-framed changeset whose payload was deliberately replaced with different valid OD-JSONTag content.

Unresolved issues within current goal:

None known for malformed/truncated OD-JSONTag record-framing classification.

Candidate next-cycle inputs:

- Decide whether to add integrity roots/hashes to detect well-formed tampering.
- Add adversarial cross-file tests for orphaned status/log/changelog relationships.
- Add developer cleanup/reset tooling for dirty datasets after explicit recovery failures.

Human evaluation / feedback:

On 2026-08-17, the human accepted the cycle with the caveat that "malformed" here means malformed framing. Actual OD-JSONTag syntax beyond record framing is not checked, and that narrower scope is acceptable.

Cycle accepted, still open, or deliberately re-planned:

Accepted.
