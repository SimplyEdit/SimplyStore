# Cycle: Process Crash Fault Harness

## Analyze

Project state / prior evaluation that makes this cycle relevant:

`CYC-006` made durable startup corruption failures explicit, and the human accepted that cycle. The human then asked how to build crash tests and rejected timing-dependent crash evidence. We agreed on explicit test-only fault points guarded by a general runtime environment mode.

Nearest important risk / uncertainty / desired movement:

SimplyStore still needs process-level evidence for command update-cycle crashes. The first useful boundary is after a command worker has written a changeset but before the server records the command as `done`.

Relevant human direction / feedback:

The human wants SimplyStore to survive crashes at any point in the update cycle and recover, or fail instead of silently using corrupted data. The human also requested a general non-production environment guard so production servers can never trigger test fault points accidentally.

## Plan

### Cycle goal

Add a deterministic process-level crash harness for the first command lifecycle boundary, guarded by `SIMPLYSTORE_ENV=test`.

### Why now

This is the next evidence-producing step after durable startup parsing and corruption classification. It starts real crash testing without depending on timing.

### Current starting evidence

- `EVD-004` proves startup selection and pending replay from real durable files.
- `EVD-005` proves explicit failure for malformed durable status/log records.
- `EVD-001` identified unawaited command log/status appends and implicit command lifecycle boundaries.

### Evaluation basis

The normal `npm test` path should stay limited to non-server tests. The separate `npm run test:durability` path should pass tests showing that:

- runtime environment defaults to `production`;
- `SIMPLYSTORE_FAULT_POINT` is ignored outside `SIMPLYSTORE_ENV=test`;
- invalid `SIMPLYSTORE_ENV` values are rejected;
- a real server child process can be killed at `before-command-done-status`;
- the command worker has written a changeset before the injected kill;
- restart replays the accepted command and reaches visible recovered state;
- durable status eventually records `done`.

Targeted ESLint should pass.

The test runner should stay simple and native-ESM friendly. During the cycle, the tests were moved from Tap to Node's built-in test runner after Tap showed confusing lifecycle/script behavior for the split durability run.

### Likely work

- Add runtime environment parsing and validation.
- Add a dormant fault-point helper.
- Await command log/status appends in the command path so the harness does not depend on append timing.
- Add a child-process TAP test that starts SimplyStore with temp data, commands, and index files.
- Record evidence in `EVD-006`.

### Explicit non-goals

- Cover every update-cycle crash boundary.
- Add fault points inside the command worker.
- Add integrity hashing.
- Add dataset reset/clean tooling.
- Decide future automatic recovery/repair behavior.

### Pause / re-plan conditions

- Fault points require a production-activatable mechanism.
- The harness requires modifying command semantics outside durable append ordering.
- Restart behavior differs nondeterministically because accepted command records are not durable before the crash.

## Act

Important artifacts / semantic commits produced:

- `da55e78ec53465e1b02aaac1bf69c25c409ed89d`: adds `src/runtime-environment.mjs`, `src/faults.mjs`, awaited command-path durable appends, and the process-level crash harness.
- `IMP-002` records the process crash fault harness and runtime environment guard.
- `EVD-006` records passing process-level crash evidence.

Material implementation decisions or deviations from the initial likely work:

The first fault point lives in the server process at `before-command-done-status`. That means the command worker has already written the changeset and returned, but the server has not yet appended the durable `done` status.

Command acceptance and outcome appends are now awaited. Without that, the crash test would depend on whether accepted log/status appends happened to finish before the fault point.

Out-of-scope discoveries retained for later:

- Query wildcard routing was not used as the test assertion path because it fell through to static serving in this environment; the test uses `POST /query/` with `data.persons`.
- Fault points inside the command worker remain future work.
- Filesystem directory sync assumptions remain future work.

## Evaluate

Integrated result against cycle goal:

The repo now has a deterministic process-level crash test for the first boundary. A child server process is killed by `SIGKILL` at `before-command-done-status`, restarted, and observed to replay the accepted command to a visible recovered state.

Evidence / acceptance result:

`npm test` passes with 8 non-server tests. `npm run test:durability` passes with 2 server-crash tests. Targeted ESLint passes. Evidence is recorded in `EVD-006`.

Metric or risk movement:

The durability proof now includes one real process kill/restart boundary instead of only startup helper tests. The broader "any point in the update cycle" claim remains unproven.

What changed in our understanding:

Awaiting durable append promises is necessary for deterministic crash evidence and is itself part of the durability boundary, not just test scaffolding.

Surprises / model mismatches:

The existing query wildcard route was not a good process-test assertion path; `POST /query/` was more reliable for this harness.

Known compromises:

The first boundary proves replay of an accepted command after a crash before `done`, not all crash classifications.

Unresolved issues within current goal:

None known for this first boundary.

Candidate next-cycle inputs:

- Add fault points and process tests before/after accepted command log/status appends.
- Add fault points inside the command worker around changeset writing.
- Add tests for crash after `done` status append and missing changeset.
- Add reset/clean tooling for dirty local/example datasets.

Human evaluation / feedback:

On 2026-08-17, the human accepted the cycle.

The human requested that normal `npm test` run only unit/non-server tests, with full-server durability tests in a separate run; this cycle was adjusted accordingly. The human also preferred Node's built-in test runner if it worked, so this cycle moved the current tests from Tap to `node:test`. The human clarified that production should ignore configured fault points rather than fail startup.

Cycle accepted, still open, or deliberately re-planned:

Accepted.

## Process learning

What context/constraint/evaluation helped:

The runtime environment discussion prevented test-only crash hooks from becoming accidentally production-activatable.

What bookkeeping was useless:

Pending.

What should the environment learn from this cycle:

For durability claims, prefer deterministic named fault points guarded by explicit test mode over timing-dependent crash attempts.
