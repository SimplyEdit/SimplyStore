# Cycle: Causal Provenance Graph Repair

Repository branch: `spiral/CYC-016-causal-provenance-repair`
Branch verified: verified on 2026-08-17 with `git branch --show-current`, branched from the CYC-015 tip because the required verification examples include the unmerged after-change/index characterization artifacts.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

An independent review found that early baseline artifacts `SRC-001`, `UND-001`, `REQ-001`, and `DES-001` were introduced in the same Git commit. Because Spiral historical causal references must point to strict ancestor commits, the original machine-readable graph could not legally encode the intended `source -> understanding -> request -> design` chain. Later implementation artifacts therefore often trace to designs/evidence/cycles but cannot mechanically traverse all the way back to original human intent. The review also found a shortened Git hash in `EVD-008.ttl`.

Nearest important risk / uncertainty / desired movement:

Spiral's core claim is that a maintainer or AI can inspect code and recover why it exists, including original human intent and later surviving contributions. If the causal graph cannot answer that mechanically for SimplyStore's durability work, the process evidence is weaker than the prose suggests.

Relevant human direction / feedback:

The human explicitly requested a new cycle that repairs this prospectively, without rewriting or rebasing existing history and without changing SimplyStore runtime behavior.

Governing higher-level plan / direction:

This is a process/provenance repair governed by Spiral's causal validation and implementation-lineage rules, especially the distinction between current effective provenance and historical transition provenance.

Current position in that plan:

The project has adopted Spiral and accumulated implementation/evidence artifacts. This cycle repairs the causal graph so existing durability implementation concerns can be traversed to current effective intent while preserving separate implementation history.

## Plan

### Cycle goal

Repair the machine-readable Spiral causal graph so representative implementation concerns can traverse through design, request, understanding, and retained/referenced source using full strict-ancestor Git references, without changing SimplyStore runtime behavior.

### Why now / why this cycle boundary

The gap directly affects Spiral's "why does this code exist?" claim. The work is coherent as a process/provenance repair cycle and should not be mixed with product behavior changes.

### Plan continuity decision

Revise local process artifacts, not the durability/product plan. This cycle temporarily interrupts the product durability sequence to repair the provenance substrate required to trust future and existing Spiral evidence.

### Current starting evidence

- `SRC-001`, `UND-001`, `REQ-001`, and `DES-001` were introduced together, so their first versions could not legally reference each other as strict ancestors.
- Current `UND-001.ttl`, `REQ-001.ttl`, and `DES-001.ttl` do not encode the source/understanding/request/design chain.
- `EVD-008.ttl` contains short hash `c8e55be`.
- Spiral core documentation distinguishes current effective provenance from `sd:transforms` and `sd:changeCausedBy` history.

### Evaluation basis

- New versions of `SRC-001`, `UND-001`, `REQ-001`, and `DES-001` are created in separate semantic commits.
- Current machine-readable links permit traversal `implementation -> design -> request -> understanding -> source`.
- Historical/change links remain separate from current effective justification.
- `EVD-008.ttl` uses a full resolving 40-character Git hash.
- Verification mechanically parses Turtle, resolves full Git references, checks strict ancestry, checks for short hashes in provenance data, checks branch/cycle consistency, and demonstrates representative traversals.

### Likely work

- Add prospective repair notes to the relevant provenance artifacts.
- Add strict-ancestor `sd:interprets` / `sd:derivedFrom` links across `SRC-001`, `UND-001`, `REQ-001`, and `DES-001` in separate commits.
- Update current implementation effective provenance where needed so representative implementations can traverse to `DES-001` or `DES-002` and onward.
- Repair `EVD-008.ttl`.
- Add mechanical graph validation/traversal tooling and evidence.

### Explicit non-goals

- Change SimplyStore runtime/product behavior.
- Rewrite, amend, rebase, squash, or otherwise alter existing published history.
- Falsely claim the original implementation history had links that did not exist at the time.
- Collapse implementation lineage/history into current effective justification.
- Complete every possible provenance path in the repository if representative traversal exposes remaining lower-priority gaps.

### Pause / re-plan conditions

- Mechanical traversal requires changing runtime/product code.
- Existing ontology cannot express the current-effective versus historical distinction without misleading semantics.
- Full strict-ancestor repair of representative paths would require rewriting published commits.
