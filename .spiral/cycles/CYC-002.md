# Cycle: First Durability Harness

## Analyze

Project state / prior evaluation that makes this cycle relevant:

`CYC-001` established baseline command/update/recovery evidence. The human accepted the baseline and agreed that the next cycle should build the first executable durability harness.

Nearest important risk / uncertainty / desired movement:

Startup/recovery behavior may silently expose ambiguous state when command status and changeset files disagree. The first executable tests should classify those cases before broader crash injection, hashing, or extensibility work.

Relevant human direction / feedback:

The human confirmed this assessment: build a small, test-only first harness focused on the highest-risk baseline contradictions.

## Plan

### Cycle goal

Create the first executable durability harness slice that can classify SimplyStore recovery behavior for command-status/changeset mismatch cases.

### Why now

The durability mission requires executable evidence. Baseline archaeology found concrete contradictions that can be tested without building the full random SIGKILL harness yet.

### Current starting evidence

- `EVD-001` found startup passes all status keys to the data loader, not only `done` commands.
- `EVD-001` found missing per-command changeset files are silently skipped.
- `EVD-001` found existing tests do not exercise command durability.

### Evaluation basis

The cycle can be evaluated when a focused test command demonstrates the current behavior for at least:

- `done` status exists but the changeset file is missing;
- `accepted` status exists and the changeset file exists.

The result may be failing tests if they preserve a true durability gap.

### Likely work

- Inspect current module seams for invoking startup reconstruction in tests.
- Add test fixture data in a temporary directory.
- Add focused TAP tests or helper scripts that exercise startup/recovery behavior.
- Preserve observed behavior in Spiral evidence.

### Explicit non-goals

- Add full SIGKILL fault injection across every boundary.
- Change recovery behavior merely to make tests pass.
- Add integrity hashing.
- Add after-change handler contracts.
- Add post-commit extension seams.

### Pause / re-plan conditions

- The current modules cannot be exercised without starting an HTTP server or changing public APIs.
- The test reveals deterministic reconstruction requires rerunning command or index semantics.
- The smallest useful test seam starts to require a general transaction/event framework.

## Act

Important artifacts / semantic commits produced:

- `test/durability-startup.mjs`: first focused startup/recovery durability harness.
- `EVD-002`: failing evidence for accepted-changeset visibility and missing done changeset recovery.

Material implementation decisions or deviations from the initial likely work:

The first harness exercises `src/load-worker.mjs` directly rather than the full HTTP server. This keeps the slice small and targets the startup reconstruction mismatch from `EVD-001` without changing public server behavior.

Out-of-scope discoveries retained for later:

- A fuller harness should parse command-status/command-log files and drive the same command selection logic as `server.run`.
- Later crash injection still needs real child-process `SIGKILL` fault points.

## Evaluate

Integrated result against cycle goal:

The cycle produced an executable harness for the two planned startup/recovery mismatch cases.

Evidence / acceptance result:

`npx tap test/durability-startup.mjs` and `npm test` fail against current behavior, preserving two durability counterexamples:

- an accepted command with an existing changeset becomes visible after startup;
- a done command with a missing changeset silently recovers instead of failing explicitly.

Metric or risk movement:

The risk moved from static evidence to executable failing regression tests. The risk is not resolved.

What changed in our understanding:

The direct loader harness confirms the startup reconstruction concern from `EVD-001`: command IDs supplied to the loader are treated as changesets to apply whenever matching files exist, and missing files are skipped.

Surprises / model mismatches:

No new mismatch beyond the expected failing behavior. The first test run exposed a test fixture syntax bug, which was fixed before recording evidence.

Known compromises:

The harness does not yet execute the full server startup path; it isolates the load worker behavior first.

Unresolved issues within current goal:

Human evaluation should decide whether to fix these two recovery behaviors next or broaden the harness to full server startup before changing behavior.

Candidate next-cycle inputs:

- Change startup/recovery so only committed command IDs are applied and missing committed changesets are explicit recovery failures.
- Extend the harness upward to parse command-status/log files and exercise the full server startup selection logic.
- Add real process-kill fault points around acceptance, changeset write, and outcome append.

Human evaluation / feedback:

On 2026-08-17, the human accepted this cycle's result: the first durability harness and its failing evidence are the right basis for the next repair cycle.

Cycle accepted, still open, or deliberately re-planned:

Accepted.
