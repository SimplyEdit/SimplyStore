# Cycle: Accepted Command Replay Safety

## Analyze

Project state / prior evaluation that makes this cycle relevant:

`CYC-007` added deterministic process crash testing and proved that a command accepted before a crash can be replayed on restart. The human clarified that accepted commands should continue to schedule again, because that is current and intended behavior.

Nearest important risk / uncertainty / desired movement:

An accepted command may itself trigger a process crash. If a supervisor restarts SimplyStore automatically, replaying that same accepted command can create a restart loop.

Relevant human direction / feedback:

The human identified the restart-loop risk and suggested keeping a durable entry for the active command, then marking a repeatedly crashing command unsafe and ignoring it.

## Plan

### Cycle goal

Keep accepted-command replay semantics, but add durable active-attempt tracking so repeatedly crashing active commands become `unsafe` instead of replaying forever.

### Why now

This is the next largest related durability step after the first process crash boundary. It directly hardens the intended accepted-command replay behavior.

### Current starting evidence

- `EVD-006` proves one process crash boundary and accepted-command replay.
- `loadCommandLog` intentionally schedules commands whose latest status is `accepted`.
- No durable record currently distinguishes a command that was accepted but never tried from a command that was active when the process died.

### Evaluation basis

The normal `npm test` path should pass tests showing that:

- an active command below the crash threshold is moved back to `accepted` and scheduled for replay;
- an active command at the crash threshold is marked `unsafe` and not scheduled.

The separate `npm run test:durability` path should pass a process test showing that:

- the first crash of an active accepted command is retried on restart;
- the second crash reaches the configured threshold;
- the next restart marks the command `unsafe`;
- the unsafe command is not committed and no longer replayed automatically.

Targeted ESLint should pass.

### Likely work

- Add active/unsafe command status constants.
- Add startup recovery for active command attempts.
- Mark a command active durably before starting its worker.
- Add unit-level recovery tests.
- Add process-level repeated-crash test.

### Explicit non-goals

- Add a cleanup/reset script.
- Add a UI or operator command for unsafe commands.
- Add fault points inside the command worker.
- Define the complete command lifecycle crash matrix.
- Automatically repair unsafe commands.

### Pause / re-plan conditions

- Tracking active attempts requires a new durable file format instead of status records.
- Accepted command replay semantics would need to be removed.
- Repeated crash detection cannot be made deterministic with the existing fault point.

## Act

Important artifacts / semantic commits produced:

- `0fa4c441e8e8cb27562486c225bb02e8038d564e`: adds active/unsafe status transitions, durable active attempt tracking, startup classification, and tests.
- `IMP-003` records accepted command replay safety.
- `EVD-007` records passing verification.

Material implementation decisions or deviations from the initial likely work:

The cycle uses `command-status.jsontag` as the durable active-attempt ledger instead of adding a separate file. Status remains the lifecycle authority, and command log remains replay material.

The default crash threshold is `2`. A command that crashes once while active is retried. A command whose latest active attempt reaches the threshold is marked `unsafe`.

Out-of-scope discoveries retained for later:

- `unsafe` commands are visible through command status, but no operator tooling exists yet for inspection, reset, or manual retry.
- A command log entry with no accepted/active status remains underdefined.
- Fault points inside the command worker remain future work.

## Evaluate

Integrated result against cycle goal:

Accepted command replay is preserved, and repeated active-command crashes are now stopped by marking the command `unsafe`.

Evidence / acceptance result:

`npm test` passes with 10 non-server tests. `npm run test:durability` passes with 4 server-crash tests when allowed to bind localhost. Targeted ESLint passes. Evidence is recorded in `EVD-007`.

Metric or risk movement:

The automatic restart-loop risk for repeatedly crashing accepted commands is reduced. The broader command lifecycle crash matrix remains incomplete.

What changed in our understanding:

Status records can serve as a simple active-attempt ledger without adding a new durable file. That keeps the implementation aligned with SimplyStore's simplicity constraint.

Surprises / model mismatches:

None material.

Known compromises:

The threshold is configurable but only through server options. There is no public documentation or operator workflow yet.

Unresolved issues within current goal:

None known for repeated crashes at `before-command-done-status`.

Candidate next-cycle inputs:

- Add operator/developer inspection and reset tooling for `unsafe` commands and dirty datasets.
- Add command lifecycle crash matrix boundaries around command log/status acceptance.
- Add command-worker fault points around changeset writing.
- Define behavior for command log entries without accepted status and accepted statuses without command log entries.

Human evaluation / feedback:

On 2026-08-17, the human accepted the cycle.

Cycle accepted, still open, or deliberately re-planned:

Accepted.

## Process learning

What context/constraint/evaluation helped:

The human's restart-loop scenario turned accepted-command replay from a generic matrix item into a concrete safety invariant.

What bookkeeping was useless:

Pending.

What should the environment learn from this cycle:

When replay is intended, also track whether replay itself repeatedly crashes the process.
