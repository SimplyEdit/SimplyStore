# Queryable object and command history evidence

Verifies implementation `e404a72` against DES-20261014-TTZ7C-72 at `6f847f0`.
Node 24.7.0 on Linux, 2026-10-14.

## Observable behavior

The real query-worker regression starts with linked identified records and then
executes a successful edit, a failed command, a no-op, ID removal and ID
restoration. Before and after reopening the runtime it verifies:

- `meta.commands.all` and `get(id)` expose only successful commands, in source
  order, with ID, name, author, message, version and source timestamp;
- command descriptors expose no original input or command-log access; those
  remain outside the query worker for purpose-built administrative tooling;
- version 0 contains base ID-bearing records, the edit version contains only
  its changed object, and the no-op version has no objects;
- object history is oldest first and carries version, source timestamp, command
  and immutable historical object;
- a historical link from Alice resolves Bob's base value instead of his current
  renamed value;
- an inline nested view follows Bob's owning-record history while a shared
  no-ID record retains established query identity;
- removing the current ID makes string history lookup unavailable but the
  current object view still reaches versions 0, 1 and 3; the removal version
  still lists that changed record, and restoring the ID restores lookup;
- the existing access module hides the protected historical property.

The unchanged query suite also covers immutability, reflection grants, schema
and record identity, hostile globals/imports, execution/serialization timeout,
result and isolate memory limits, worker replacement and storage-read failure.

## Representative history probe

`node --no-node-snapshot scripts/benchmark-query-history.mjs` created 1,000
identified records, committed 20 edits to one record, closed and reopened the
store, and queried all 21 object versions plus the last version peer and command
message. One local run reported:

| Observation | Result |
| --- | ---: |
| Reopen | 72.65 ms |
| History query | 11.26 ms |
| Worker heap before / after | 8,216,152 / 9,253,592 bytes |
| Process descriptors before / open / query | 19 / 63 / 83 |
| Ordered sources | 21 |
| Current-parser resident records before / after | 1 / 1 |

The stable current-parser residency shows that the query did not populate the
head parser with all historical bodies. Historical parsers exist only during
the query for requested versions and share already-open source readers. The
descriptor observations include asynchronous initialization of both configured
query pools; there is no per-query command-log handle in the compact design.

These figures are warm local observations, not capacity guarantees. Catalogues
for offsets, record-version locations, IDs and command descriptors still grow
with records and versions. A query touching many versions creates one temporary
parser and selected-location map per touched version. Complete historical
`data`/`root` switching remains deferred.

## Scope and size

No data, index, command-log or status format changed. There is no migration,
REST/UI change, separate authorization, author validation, package publication
or curriculum-store change. Source timestamps are dataset file mtimes and may
change when files are copied or restored.

Relative to the cycle base, product source is +407/-12 lines, the benchmark is
161 lines, tests are +137/-7, and runtime/file documentation is +72/-7. Most
product growth is the explicit host-side virtual query view for command,
version, peer and history objects; it keeps filesystem/parser authority outside
the isolate and reuses the existing immutable proxy protocol. Removing lazy
original-command input access cut the query surface and its storage machinery
without changing the object-history outcome.
