## Filesystem experiment

Run the command in `docs/power-loss-filesystem.md` with the packaged harness.
This evaluation used QEMU 10.2.1, Linux 7.0.0-31-generic, Node v24.7.0, ext4
`data=ordered,barrier=1`, virtio-blk with QEMU `cache=writeback`, and a purpose-built
volatile NBD backend honoring FLUSH/FUA. TCG used two CPUs and 1024 MiB RAM; no
KVM or host block-device writes. QEMU/kernel files were extracted under `/tmp`,
without installing host packages. Exact kernel digest and observed mounts/cache
are retained in the JSON evidence.

The host kills the whole guest on an observed boundary, discards volatile block
writes, then boots the same surviving image for ext4 recovery and engine
inspection. Results:

- Done: five completed commands A/L0/L1/L2/L3 survive in order; ready=true.
- Accepted: A's complete accepted record survives; no dataset; ready=false.
- Active: A remains active with no dataset; ready=false; inspection executes no handler.
- Unsynced filesystem control: an ordinary unsynced file disappears after the cut.
- Independent device control: flushed A persists, unflushed B is lost (one dirty page discarded).

At the engine boundaries no dirty device pages remained: completed flushes had
drained them. The separate device control verifies that the backend really loses
unflushed writes; the filesystem control demonstrates guest-cache loss. The
test does not fabricate deletion of acknowledged synced data. Output images,
initramfs and full serial logs were retained locally under
`/tmp/simplystore-vm-acceptance`; compact evidence is committed here, not images.

## Latency and practical bounds

On the ext4/TCG guest, the first cold command completed in 2520 ms. Four subsequent
commands accepted in 31.1–44.7 ms and completed in 755.6–872.9 ms. These include
emulation, fresh workers and polling and are too few for throughput or percentile
claims. Flush correctness, not production performance, is this experiment's aim.

A separate 30-command localhost/tmpfs sample measured startup 127.2 ms;
acceptance p50/p95 0.98/2.03 ms; completion p50/p95 39.88/44.08 ms. Maximums were
35.39/79.75 ms respectively. These are tmpfs timings, not disk measurements or a
before/after performance comparison. A deployment should measure its own storage.

Evidence is bounded: no physical power removal, random exhaustive campaign,
remote-filesystem promise, lying-device tolerance, or universal custom-hook
certification. The preload instruments the newly used async paths; synchronous
index helpers have functional/conversion coverage, not exhaustive injected faults
at every native call. Interrupted recovery boundaries combine real worker effects
with explicit fixtures; deployment promotion is documented and previewed, not
performed against a service manager. These are test limits, not stronger claims.

No canonical format change or migration is required. Pending/uncertain historical
work deliberately reduces automatic availability. Surviving files cannot prove
complete old history, original code/dependencies, missing business inputs or
external effects. Missing/corrupt unrecoverable state may require a disclosed
backup rollback. Full rebuild tooling and wider stress/platform testing remain
follow-up work within their separately recorded boundaries.

ESLint passed the new modules, changed server/worker/recovery/converter paths,
harness and revised tests. Full changed-file lint also exposes two pre-existing
undefined `meta` references in the untouched `load` methods of `index.id.mjs` and
`index.offset.mjs`, confirmed identical on master; this cycle changes their write
paths only. This is not represented as a clean repository-wide lint result.
