# Verification Evidence: Baseline Command Durability Archaeology

## Claim being verified

This evidence does not verify a durability claim yet. It documents the checked-out command/update/recovery behavior that future durability work must test or change.

## Why this evidence exists

`SRC-001` requires baseline archaeology before behavior changes. The purpose is to establish current effective behavior and contradictions before introducing a crash harness or hardening changes.

## Result

### Exact command lifecycle

Observed command path:

1. `POST /command` calls `checkCommand`.
2. `checkCommand` parses the command and creates an `accepted` status object.
3. If the command ID is new, `checkCommand` calls `appendFile(commandLog, ...)` and `appendFile(commandStatus, ...)`, sets in-memory status to `accepted`, sends HTTP 202, and returns the command ID.
4. `handlePostCommand` pushes the command onto the in-memory queue and calls `runNextCommand`.
5. `runNextCommand` starts a dedicated command worker.
6. The command worker initializes from current buffers/meta, imports the configured commands and index module, parses the command, and runs the command handler.
7. The worker collects changed OD-JSONTag objects from `meta.resultArray`, sets `changes.uuid` to the command ID, and calls `index.update(dataspace, meta, changes)` before serializing/writing the changeset.
8. The worker serializes only changes and writes `basefile + "." + commandId + "." + extension` with `writeFileAtomic`.
9. The worker posts the serialized changes and meta back to the main thread.
10. The main thread marks status `done`, pushes the changeset into in-memory `jsontagBuffers`, updates query worker pools, and calls `appendFile(commandStatus, ...)` with the `done` status.

### Exact status terminology

Observed durable/in-memory statuses:

- `accepted`: command accepted and eligible for execution/replay.
- `done`: command considered complete.
- `failed`: command failed.

No separate `committed` term exists in current code.

### When changesets become durable

Per-command changeset files are written by the command worker with `writeFileAtomic` before the main thread appends the `done` status.

The changeset filename is derived from the configured data file and command ID, for example `data.<command-id>.jsontag`.

### When command-log/status records become durable

`appendFile` opens the file with `a+`, appends one newline-terminated record, and calls `handle.datasync()` before closing.

However, current command lifecycle call sites do not `await` `appendFile`:

- command log append during acceptance;
- accepted status append during acceptance;
- failed status append in catch paths;
- done status append after worker success.

So current caller behavior does not guarantee that HTTP responses, in-memory status changes, or queue execution wait for durable append completion.

### Current indexer API

The configured index module exposes:

- `create(data, meta)`;
- `update(data, meta, changes)`;
- `load(meta, uuid = null)`.

The default `src/index.mjs` delegates to ID and offset index modules.

### Whether indexers may modify the dataset

No contract currently prevents mutation. `index.update(data, meta, changes)` receives the mutable dataspace and meta objects before the changeset is serialized.

The default ID/offset indexers appear intended to write external index files, not mutate canonical data, but this is convention rather than an enforced phase contract.

### Whether indexers may write external files

Yes. Current ID and offset indexers write JSON files using `fs.writeFileSync`:

- `index.id.json`;
- `index.id.<command-id>.json`;
- `index.offset.json`;
- `index.offset.<command-id>.json`.

These writes occur before the changeset file is written and before command outcome is appended.

### How startup determines which changesets to load

Startup:

1. loads command status into a map keyed by command ID;
2. calls `loadData(Array.from(status.keys()))`;
3. the load worker reads the base data file and then attempts to read `base.<command-id>.<extension>` for each command ID supplied;
4. the loader silently skips any missing file because it only reads a partial file when `fs.existsSync(datafile)` is true.

Important observed contradiction: the loader is given all command IDs present in status, not only `done` commands. That means a changeset file for an `accepted` or `failed` command can be applied during startup if it exists.

After data loading, startup calls `loadCommandLog(status, commandLog)`, which queues commands whose latest status is `accepted` and ignores `done` or other statuses.

### Which writes use atomic replace, append, fsync/datasync, or neither

| Durable artifact | Current write mechanism | Awaited by lifecycle caller | fsync/datasync evidence |
|---|---|---|---|
| Command log | `appendFile` helper | No | Helper calls `handle.datasync()`, but caller does not await it. |
| Command status | `appendFile` helper | No | Helper calls `handle.datasync()`, but caller does not await it. |
| Per-command changeset | `writeFileAtomic` | Yes, inside worker | External package behavior not inspected in this pass. |
| ID index files | `fs.writeFileSync` | Synchronous inside worker | No explicit fsync/datasync observed. |
| Offset index files | `fs.writeFileSync` | Synchronous inside worker | No explicit fsync/datasync observed. |

### Current behavior after interrupted commands

No crash/fault-injection tests exist yet.

Static evidence suggests these crash windows matter:

- crash after command log append starts but before accepted status is durable;
- crash after accepted status is durable but before worker writes changeset;
- crash after index files are written but before changeset is durable;
- crash after changeset is durable but before `done` status is durable;
- crash after `done` status is appended by the caller but before the append promise actually settles;
- startup with `done` status but missing changeset;
- startup with `accepted` status and existing changeset.

Current startup behavior appears to silently skip missing changesets, and appears capable of loading changeset files for non-`done` command IDs if such files exist.

### Malformed durable-line parse probe

A read-only `node --input-type=module` probe showed:

- valid JSONTag status line parses;
- truncated JSONTag line throws `Input stopped early`;
- non-JSONTag text throws a syntax error.

Current status/log loading does not classify malformed lines into documented recovery outcomes.

## Failure cases / limits

- This evidence is mostly static/manual; it does not yet prove runtime crash behavior.
- It did not inspect external `write-file-atomic` guarantees.
- It did not run a server integration scenario.
- It did not inspect OD-JSONTag laziness/materialization internals.
- It did not establish downstream compatibility expectations for command log/status files.

## Evidence quality

The evidence is sufficient to identify the first executable test targets and several current contradictions with the intended durability invariants. It is not sufficient to claim durability. The next evidence-producing step should be a crash/fault-injection harness that can reproduce or falsify these static concerns.
