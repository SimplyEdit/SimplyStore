# Verification Evidence: Command And Load Worker Timeout Semantics

## Claim being verified

`IMP-011` implements the timeout semantics in `DES-003`: command and load workers are bounded by parent-thread timeouts, timed-out commands become terminal `unsafe`, queued accepted commands can continue after a timed-out worker, and load timeout fails startup explicitly.

## Why this evidence exists

Timeouts were identified as a durability gap after crash testing. A process can survive while command or load work hangs, so crash/restart evidence alone cannot prove bounded recovery, queue progress, or explicit failure.

Behavior verified by the new durability tests:

- A hanging command returns initial HTTP `202 accepted`, becomes durable `unsafe` with code `504`, attempt `1`, and timeout diagnostics.
- Retrying the same timed-out command ID returns `unsafe` and does not enqueue duplicate work.
- A later accepted command commits after the timed-out command worker is terminated.
- Live query state and independent reconstruction include only the later committed command, not the timed-out command.
- A hanging load worker exits startup with code `1` and logs the load timeout; the server does not start listening.

## Failure cases / limits

- Server-process tests required permission to bind localhost ports in this environment.
- `scripts/validate-spiral-provenance.mjs` is still specialized for the completed CYC-016 graph repair cycle, so its branch/cycle consistency check is not reusable unchanged for CYC-017.
- The tests do not prove rollback of arbitrary external side effects from timed-out command code.
- The tests do not add reset/recovery tooling for uncommitted changesets left by failed, unsafe, or interrupted work.
