# Verification Evidence: Process Crash Fault Harness

## Claim being verified

`IMP-002` provides a test-only process fault harness and proves the first crash boundary: a crash before durable `done` status can restart and replay the accepted command to a visible recovered state.

## Why this evidence exists

The durability goal requires crashes at update-cycle boundaries to recover or fail explicitly. Prior evidence covered startup parsing and helper behavior, not a real killed server process.

npx eslint src/runtime-environment.mjs src/faults.mjs src/server.mjs src/recovery.mjs test/durability-crash.mjs test/durability-startup.mjs

Results:

- `npm test` passes with Node's built-in test runner: 8 non-server tests pass.
- `npm run test:durability` passes with Node's built-in test runner when allowed to bind localhost: 2 server-crash tests pass.
- Targeted ESLint passes.

Tap was removed from the active test path after the script split exposed confusing Tap runner behavior under `npm run test:durability`.

The new process test covers:

- default runtime environment is production;
- fault points are rejected outside `SIMPLYSTORE_ENV=test`;
- real child server process starts against temp durable files;
- valid command receives or starts from `202 Accepted`;
- process is killed with `SIGKILL` at `before-command-done-status`;
- command worker changeset exists after the crash;
- restart replays the accepted command;
- query after restart observes the expected person;
- durable status file records `done`.

## Failure cases / limits

- This proves one process crash boundary, not the full update cycle.
- The command worker itself does not yet contain named fault points.
- It does not prove crash behavior before/after accepted command appends.
- It does not prove crash behavior after `done` append.
- It does not settle filesystem directory sync requirements.
- It does not prove idempotent retry after a lost client response.

## Evidence quality

This evidence is stronger than timing-based crash attempts because the process is killed at a named boundary in the real server code path, guarded by test-only runtime configuration. It is intentionally narrow and should not be described as complete durability proof.
