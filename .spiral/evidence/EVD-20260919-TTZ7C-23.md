## Method and environment

Executed on 2026-09-19 using Node v24.7.0 on Linux with the installed dependencies.
Tests bind localhost on ephemeral ports and use disposable store/observer
directories. The server preloader traces actual current file API calls in both
main and worker threads. Client observations and side-effect witnesses remain
outside the copied crash images. No production data was changed.

The tests model selected permitted cache/namespace-loss outcomes after SIGKILL,
inject actual API failures/partial writes, and exercise explicit adversarial and
policy fixtures. They do not cut physical power or test the deployment filesystem.
`docs/power-loss-baseline.md` records each distinction and uncovered matrix rows.

## Reproduced gaps

1. **PL02 / P2:** after external observation of `done`, dropping the unsynced new
   status filename makes restart serve `[]` instead of independently expected
   `['A']`. The surviving log alone does not detect this silent rollback.
2. **PL03 / P1:** dropping the unsynced new command-log filename leaves accepted
   work without a reconstructible task; server still starts.
3. **PL04 / P2:** losing an unsynced changeset rename after `done` produces an
   explicit missing-changeset startup failure rather than recovery of the commit.
4. **PL10 / P3:** a callback write that writes only half the changeset succeeds;
   the installed atomic-write dependency does not complete the remaining bytes.
   The live server receives intact memory bytes and reports `done`, but startup
   subsequently rejects the truncated disk file. This is actual short-write
   injection, not post-commit tampering with a complete file.
5. **PL12 / P7:** after an external effect and a pause before done-status sync,
   restore the last synced status bytes and lose the unpublished changeset name.
   Restart automatically repeats the effect: witness `['A', 'A']` while the
   dataset contains one transition. No administrator authorized the second call.
6. **PL13 / P6 (two assertions):** synthetic B-accepted/missing and C-with-dataset
   policy fixtures still queue B whether C's current status is accepted or done.
7. **PL15 / P8:** a configured worker forwards request query input to its handler;
   live execution uses `name=from-request`, while reconstructed task request is
   null. The ordinary JSONTag command body itself passes the PL14 round-trip
   control. This qualifies the earlier FIXME speculation with actual evidence.
8. **PL16 / P4/P6:** controlled concurrent acceptance produces external acceptance
   and waiting-queue order B/A, but log order A/B. After a crash, recovery executes
   A/B. The observer's order is independent of the log being checked.
9. **PL17 / P7:** startup reclassifies uncertain active A as accepted before
   failing on missing committed C. Original records remain intact as an append
   prefix; the finding is unauthorized replay eligibility, not erased history.

## Passing controls and useful bounds

- PL01 traces real append/data-sync and worker temp-file-sync/rename order and
  verifies normal restart against independent expected values.
- PL21 supplies an explicit directory sync in a test-only finalizer. The trace
  observes it, the model preserves the published filenames, and restart matches
  the external expectation. The loss model distinguishes presence of a barrier.
- PL05 shows current default startup reconstructs without ID/offset sidecars;
  this does not classify custom consumers or future lazy-index loading.
- PL06 rejects a torn status tail while preserving the untouched original store.
- PL07/08/09 reject changeset fsync, rename, and write errors before completion.
- PL11 exits on done-status sync failure while written done bytes remain visible:
  an I/O failure is not proof that the command rolled back.
- PL18/19/20 return HTTP 500 rather than acceptance after log/status sync or
  post-close errors.
