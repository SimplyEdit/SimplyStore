# Verification Evidence: Accepted Command Replay Safety

## Claim being verified

`IMP-003` preserves accepted-command replay while preventing repeatedly crashing accepted commands from replaying forever.

## Why this evidence exists

Accepted commands are intentionally scheduled again on restart. Without active-attempt tracking, a poison command can crash the server, be replayed after automatic restart, and crash the server again indefinitely.

## Result

Commands run:

```text
npm test
npm run test:durability
npx eslint src/recovery.mjs src/server.mjs test/durability-startup.mjs test/durability-crash.mjs
```

Results:

- `npm test` passes with Node's built-in test runner: 10 non-server tests pass.
- `npm run test:durability` passes with Node's built-in test runner when allowed to bind localhost: 4 server-crash tests pass.
- Targeted ESLint passes.

The new tests cover:

- active command below crash threshold becomes accepted again and is scheduled;
- active command at crash threshold becomes unsafe and is not scheduled;
- a repeated process crash at `before-command-done-status` marks the command unsafe on the next restart;
- unsafe command state remains uncommitted and visible via command status.

## Failure cases / limits

- No operator cleanup/reset/manual retry tooling exists yet.
- This does not prove command-worker internal crash boundaries.
- This does not classify command log/status cross-file inconsistencies.
- This does not document `active` or `unsafe` as public durable status vocabulary.

## Evidence quality

This evidence covers both direct recovery classification and real process restarts. It specifically addresses automatic restart loops for repeatedly crashing accepted commands, while preserving the intended replay behavior for ordinary accepted commands.
