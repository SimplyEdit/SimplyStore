# Verification Evidence: Retry And Idempotency Status Reporting

## Claim being verified

`IMP-007` ensures retried command IDs do not enqueue duplicate transitions and report the current command status for normal committed, active, recovered, and unsafe retry paths.

## Why this evidence exists

The original durability source requires retry/idempotency hardening after adversarial storage classification. A command may commit while the client loses the response, or crash/recovery may leave a client uncertain. Retrying the same command ID must not create a second state transition or misleadingly claim that an unsafe/done command was newly accepted.

The new/expanded tests cover:

- normal duplicate command ID retry reports `done` and does not apply a second transition;
- retry while a slow command is `active` reports `active` and does not enqueue duplicate work;
- retry after accepted/active/changeset/done crash recovery reports `done` and does not apply a second transition;
- retry after a repeated active-command crash threshold reports `unsafe` and does not replay the unsafe command.

## Failure cases / limits

- Duplicate command bodies are not compared with the original command body.
- Existing-command retries still use HTTP 200 with status details in the JSON body.
- This does not add integrity roots, handler contracts, cleanup/recovery tooling, or filesystem power-loss evidence.

## Evidence quality

This evidence is strong for command-ID retry behavior within the current server/process harness. It does not prove generalized distributed exactly-once semantics; it proves SimplyStore's local command ID produces at most one committed transition across the tested retry paths.
