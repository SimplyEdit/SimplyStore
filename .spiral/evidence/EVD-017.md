# Verification Evidence: Current Command Timeout Behavior

## Claim being verified

Current SimplyStore command/load worker timeout behavior is not explicit enough for the durability model: query execution has a VM2 timeout, but command and load workers can hang at the worker-thread boundary without a durable timeout policy.

## Why this evidence exists

`CYC-017` pulls timeout semantics forward before integrity roots because a surviving-process worker hang can affect command lifecycle, retry behavior, startup replay, and queue progress. Those semantics should be characterized before implementation.

## Result

Source inspection:

- `src/query-worker-module.mjs` applies timeout through VM2 for query code.
- `src/server.mjs#loadData` starts a load worker and waits for `message` or `error`, with no timeout.
- `src/server.mjs#runNextCommand` starts a command worker and waits for `message` or `error`, with no timeout.
- `src/command-worker.mjs` initializes and runs the command without an outer timeout.

Disposable probe 1: command handler hangs while the server process survives.

Observed behavior:

```text
POST /command hang-1 -> 202 accepted
GET /command/hang-1 -> active attempt 1
POST /query/ -> previous committed state remains visible
POST /command after-hang -> 202 accepted response, then durable status becomes failed
```

Observed status/log material:

```text
hang-1: accepted -> active attempt 1
after-hang: accepted -> failed
```

Interpretation:

The hanging command remains `active` indefinitely while the server survives. A later command can be accepted and then marked failed internally because the existing command worker is still occupied; the HTTP response already reported `accepted`.

Disposable probe 2: restart after stopping a server with an active hung command.

Observed behavior:

```text
before stop: hang-restart active attempt 1
restart: server did not start listening
status file: accepted -> active attempt 1 -> accepted retry -> active attempt 2
```

Interpretation:

Startup recovery treats the active command as retryable, then replay re-enters the hanging command before the server begins listening. Because the process does not crash, the unsafe crash-attempt threshold is not reached by itself. Automatic restart can therefore stall startup rather than fail clearly or classify the command as unsafe.

## Failure cases / limits

- These were disposable probes, not committed regression tests.
- Load worker timeout behavior has been inspected in code but not yet exercised with a runtime probe.
- The probes do not decide the intended timeout semantics.
- External side effects from a hanging command or index hook remain a separate compatibility/contract concern.

## Evidence quality

This is sufficient evidence to justify a CYC-017 semantics/design step before implementation. It establishes that command timeout behavior is not merely theoretical and that the query-worker VM2 timeout mechanism does not currently cover command/load worker hangs.
