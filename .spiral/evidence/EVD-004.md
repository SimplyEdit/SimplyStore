# Verification Evidence: Full Startup Recovery Selection

## Claim being verified

`IMP-001` now shares durable command-status and command-log parsing between server startup and tests, and the startup recovery harness verifies committed selection and pending replay classification from real files.

## Why this evidence exists

`CYC-004` expands the accepted CYC-003 recovery proof from direct helper/worker tests to durable startup inputs: `command-status.jsontag`, `command-log.jsontag`, and command-named changeset files.

## Result

Commands run:

```text
npm test
npx eslint src/recovery.mjs src/load-worker.mjs src/server.mjs test/durability-startup.mjs
```

Results:

- `npm test` passes: 7 assertions pass, 1 existing empty test file remains skipped.
- Targeted ESLint passes.

The new harness covers:

- accepted command with existing changeset remains uncommitted;
- done command with missing changeset fails recovery;
- durable status file selects only latest `done` commands for startup changeset loading;
- durable command log replays only commands whose latest status is `accepted`.

## Failure cases / limits

- This still does not start a full HTTP server process.
- This does not inject `SIGKILL`.
- This does not classify malformed/truncated command-status or command-log records.
- This does not repair unawaited append calls.
- This does not prove idempotency after lost client response.

## Evidence quality

This evidence exercises the shared parsing and selection code used by server startup, with real temporary durable files. It can catch regressions where status/log parsing diverges from recovery behavior, without yet paying the cost of full process-level crash injection.
